# 2.1 应用层协议原理

### 核心概念

- 网络应用程序的核心是运行在不同**端系统 (End Systems)** 上的**进程 (Processes)**，通过网络**交换报文 (Messages)** 进行通信。
- 应用开发者只需关注端系统上的软件逻辑，无需编写运行在网络核心设备（路由器、交换机）上的代码。

![在应用层的端系统之间的网络应用的通信](image.png)

### 2.1.1 网络应用程序体系结构

应用程序体系结构由开发者设计，规定应用在端系统上的组织方式。主要有两种：

1.  **客户-服务器体系结构 (Client-Server Architecture)**

    - **服务器 (Server):** 始终在线；具有固定的、周知的 IP 地址；服务于客户请求。
    - **客户 (Client):** 与服务器通信，发起请求；客户之间不直接通信。
    - **数据中心 (Data Center):** 用于承载大型应用，提供强大的虚拟服务器。
    - **例子:** Web, FTP, Telnet, 电子邮件。

2.  **对等体系结构 (Peer-to-Peer, P2P Architecture)**
    - **特点:** 对专用服务器依赖最小化或没有；利用对等方 (Peers) 之间的直接通信；对等方通常是用户控制、间歇性连接的主机。
    - **优势:** 自扩展性 (Self-scalability)，成本效益 (Cost-effective)。
    - **挑战:** 安全性、性能、可靠性。
    - **例子:** BitTorrent, Skype (部分功能)。

### 2.1.2 进程通信

- **进程 (Process):** 运行在端系统中的程序实例，是通信的主体。
- **客户进程与服务器进程:**
  - **客户 (Client):** 发起通信会话的进程。
  - **服务器 (Server):** 等待被联系的进程。
  - _注意:_ 在 P2P 等应用中，一个进程可能在不同时间扮演不同角色。
- **进程接口 - 套接字 (Socket):**
  - 应用层与传输层之间的接口。
  - 应用程序与网络之间的 **应用程序编程接口 (API)**。
  - 进程通过套接字发送和接收报文。
- **进程寻址:**
  - 为了唯一标识一个接收进程，需要：
    1.  **IP 地址 (IP Address):** 标识主机。
    2.  **端口号 (Port Number):** 标识主机上的特定进程（套接字）。
  - **周知端口号:** 分配给标准应用的特定端口（如 HTTP: 80, SMTP: 25）。

### 2.1.3 可供应用程序使用的运输服务

应用程序根据需求选择传输协议，主要考虑以下服务维度：

1.  **可靠数据传输 (Reliable Data Transfer):** 保证数据无差错、按序、完整到达。对文件传输、邮件等关键。容忍丢失的应用（如流媒体）可能不严格要求。
2.  **吞吐量 (Throughput):** 数据传输的速率。
    - **带宽敏感型应用 (Bandwidth-sensitive):** 需要最低保证吞吐量（如某些实时视频）。
    - **弹性应用 (Elastic):** 能适应可用吞吐量的变化（如 Web, Email）。
    - 互联网协议通常不提供**保证**吞吐量。
3.  **定时 (Timing):** 数据传输的延迟。
    - 对实时交互应用（网络电话、游戏）很关键，需要低延迟保证。
    - 互联网协议通常不提供**定时保证**。
4.  **安全性 (Security):**
    - **机密性 (Confidentiality):** 加密。
    - **完整性 (Integrity):** 防止篡改。
    - **认证 (Authentication):** 身份验证。

### 2.1.4 因特网提供的运输服务

互联网主要提供两种传输协议：

1.  **UDP (User Datagram Protocol)**

    - 无连接 (Connectionless)。
    - 不可靠数据传输 (Unreliable)。
    - 无拥塞控制。
    - 轻量级，开销小，速度快（无连接建立延迟）。
    - 本身不提供安全。

2.  **TCP (Transmission Control Protocol)**

    - 面向连接 (Connection-oriented)，需要握手建立连接。
    - 可靠数据传输 (Reliable)，按序、无差错、不丢失、不重复。
    - 拥塞控制 (Congestion Control)，调节发送速率以适应网络状况。
    - 本身不提供安全。

3.  **TLS (Transport Layer Security)**
    - **不是**独立的传输协议，而是对 TCP 的**增强**，在**应用层**实现。
    - 提供加密、数据完整性、端点认证等安全服务。
    - 应用通过 TLS 库与 TCP 交互，实现安全通信。

- **总结:** 互联网 TCP/IP 协议栈本身**不提供**吞吐量或定时保证。TCP 提供可靠传输和拥塞控制，UDP 提供最小服务。安全通常由应用层（如 TLS）添加。

### 2.1.5 应用层协议 (Application-Layer Protocols)

- **定义:** 规定了运行在不同端系统上的应用程序进程如何相互传递报文。
- **规范内容:** 报文类型、报文语法、字段语义、进程收发报文的规则和响应方式。
- **类型:**
  - **公共域协议 (Public Domain):** 由 RFC 等标准定义 (如 HTTP, SMTP)。
  - **私有协议 (Proprietary):** 协议细节不公开 (如早期 Skype)。
- **区别:** 应用层协议是网络应用的一个组成部分（规定通信规则），网络应用包含协议以及其他组件（如用户界面、数据格式等）。

本章将重点讨论：Web (HTTP), 电子邮件 (SMTP), DNS, P2P 文件分发, 视频流与 CDN。

## 复习题 (R1-R9)

### R1

列出 5 种非专用的因特网应用及它们所使用的应用层协议。

#### A1

1.  **Web 浏览:** HTTP (HyperText Transfer Protocol)
2.  **电子邮件:** SMTP (Simple Mail Transfer Protocol), POP3 (Post Office Protocol version 3), IMAP (Internet Mail Access Protocol)

4.  **远程终端访问:** Telnet, SSH (Secure Shell)

### R2

网络体系结构与应用程序体系结构之间有什么区别？

#### A2

- **网络体系结构 (Network Architecture):** 指的是网络的分层结构模型，如 TCP/IP 五层模型或 OSI 七层模型。它定义了各层的功能和层间接口，是网络设计的基础框架，相对固定。
- **应用程序体系结构 (Application Architecture):** 指的是应用程序在各个端系统上的组织方式和交互模式，由应用程序开发者设计。常见的有客户端-服务器 (C/S) 架构和对等 (P2P) 架构。

### R3

对两进程之间的通信会话而言，哪个进程是客户，哪个进程是服务器？

#### A3

在一次特定的通信会话中，**发起**通信（即首先联系对方）的进程是**客户 (Client)**，而**等待**被联系以开始会话的进程是**服务器 (Server)**。

### R4

对一个 P2P 文件共享应用，你同意"一个通信会话不存在客户端和服务器端的概念"的说法吗？为什么？

#### A4

**不同意**。虽然 P2P 应用中的主机（对等方）通常既能下载（作客户端）也能上传（作服务器），但在**任何一次具体的文件块传输交互中**，角色是明确的：请求文件块的对等方是**客户端**，提供文件块的对等方是**服务器**。只是这个角色在不同的交互中可能会互换。

### R5

运行在一台主机上的一个进程，使用什么信息来标识运行在另一台主机上的进程？

#### A5

使用两部分信息来标识：

1.  目标主机的 **IP 地址 (IP Address)**。
2.  目标主机上接收进程的 **端口号 (Port Number)**。

### R6

假定你想尽快地处理从远程客户到服务器的事务，你将使用 UDP 还是 TCP？为什么？

#### A6

这取决于“尽快处理事务”的确切含义：

- **如果“尽快”主要指最小化初始延迟（例如，发送第一个请求包）并且可以容忍数据丢失或乱序：** 可能会选择 **UDP**。因为 UDP 是无连接的，不需要像 TCP 那样先进行三次握手来建立连接，可以立即发送数据，减少了连接建立的 RTT 延迟。
- **如果“尽快处理事务”隐含了可靠性要求（即事务必须成功完成，数据不能丢失或错误）：** 则必须选择 **TCP**。虽然 TCP 有连接建立的延迟（通常是 1 个 RTT），但它提供可靠的数据传输，确保事务数据正确送达。UDP 不提供可靠性保证，事务可能因数据丢失而失败，导致需要应用层重试，反而可能更慢或无法完成。

对于大多数需要确保完成的“事务”场景，**TCP** 通常是更合适的选择，尽管初始延迟可能略高。如果事务极其简单（例如，一次性查询且能容忍丢失），UDP 可能是理论上最快的，但不保证成功。

### R7

参见图 2-4，我们看到在该图中所列出的应用程序没有一个同时既要求无数据丢失又要求定时的。你能设想一个既要求无数据丢失又高度时间敏感的应用程序吗？

#### A7

是的，可以设想这样的应用。例如：

- **远程手术:** 手术指令必须精确无误地传输（无数据丢失），并且必须实时到达（高度时间敏感），操作的反馈（视觉、力反馈）也需要实时无误地传回。
- **某些工业控制系统:** 控制指令和传感器数据需要精确且及时地传输，以确保生产过程的安全和稳定。
- **高频金融交易:** 交易指令需要准确无误，并且在极短的时间内执行，纳秒级的延迟都可能影响交易结果。

### R8

列出一个运输协议能够提供的 4 种宽泛类型的服务。对于每种服务类型，指出是 UDP 还是 TCP（或这两种协议）提供这样的服务？

#### A8

1.  **可靠数据传输 (Reliable Data Transfer):** **TCP** 提供；UDP 不提供。
2.  **吞吐量 (Throughput):** **TCP 和 UDP 都不提供保证吞吐量**。TCP 有拥塞控制机制，会影响吞吐量并试图公平分配带宽；UDP 没有拥塞控制（由应用负责）。两者都能利用可变的网络吞吐量（弹性）。
3.  **定时 (Timing):** **TCP 和 UDP 都不提供定时保证**（即不保证延迟上限）。
4.  **安全性 (Security):** **TCP 和 UDP 本身都不提供**（如加密、认证）。但 **TCP** 可以通过 **TLS** (传输层安全，在应用层实现) 来增强，提供这些安全服务。对于 UDP，也有类似的 DTLS 协议。

### R9

前面讲过 TCP 能用 TLS 来强化，以提供进程到进程的安全性服务，包括加密。TLS 运行在运输层还是应用层？如果某应用程序研制者想要用 TLS 来强化 UDP，该研制者应当做些什么工作？

#### A9

- TLS (Transport Layer Security) 实际上运行在**应用层 (Application Layer)**。它位于应用程序和 TCP 层之间，利用 TCP 提供的可靠传输服务，并为上层应用程序提供加密、认证等安全功能。虽然名字带“传输层”，但它是一个应用层的安全协议/库。
- 如果开发者想用类似 TLS 的机制来强化 UDP，他们不能直接使用 TLS（因为 TLS 依赖 TCP 的可靠字节流）。他们需要使用 **DTLS (Datagram Transport Layer Security)**。DTLS 是 TLS 的一个变种，专门设计用于为 UDP 这种不可靠的数据报协议提供安全服务。开发者需要在他们的应用程序中集成 DTLS 库，并在应用层处理 DTLS 协议的握手、加密/解密等过程，然后通过 UDP 套接字发送/接收 DTLS 记录。

# 2.2 Web 和 HTTP

### 核心概念

- **Web 页面 (Web Page):** 由多个**对象 (Objects)** 组成（HTML 文件、图片、脚本等）。
- **URL (Uniform Resource Locator):** 用于定位 Web 上的对象，包含**主机名 (hostname)** 和**路径名 (path name)**。
- **HTTP (HyperText Transfer Protocol):** Web 的应用层协议，定义了浏览器（客户端）和 Web 服务器之间如何请求和传输 Web 对象。
- **底层协议:** HTTP 使用 **TCP** 提供可靠的数据传输。
- **无状态协议 (Stateless Protocol):** 服务器不保存关于过去客户端请求的信息。

## 2.2.1 HTTP 概述

- HTTP 定义了客户端和服务器之间交换的**报文结构**和**交互规则**。
- 客户端发起 TCP 连接（通常到服务器 80 端口），然后发送 HTTP 请求。
- 服务器通过 TCP 连接发送 HTTP 响应。
- HTTP 协议本身不关心数据丢失和重排（它们由 TCP 保证）。
- HTTP/1.0, HTTP/1.1 (主流), HTTP/2 (发展中), HTTP/3 (未来)。
  - 协议具体规范：
  - [[1945|RFC 1945]]规定了 HTTP/1.0
  - [[7230|RFC 7230]]规定了 HTTP/1.1
  - [[7540|RFC 7540]]规定了 HTTP/2

## 2.2.2 非持续连接和持续连接

描述客户端和服务器之间 TCP 连接的管理方式。

### 1. 非持续连接 (Non-Persistent Connections)

- 每个请求/响应对都需要建立一个新的 TCP 连接。
- 获取一个包含 N 个小对象的页面需要建立 N+1 个 TCP 连接。
- **缺点:** 开销大（连接建立/拆除），延迟高（每个对象至少 2 RTT 延迟）。
- HTTP/1.0 使用此方式。浏览器可能通过并行连接缓解延迟。

### 2. 持续连接 (Persistent Connections)

- 客户端和服务器之间可以复用同一个 TCP 连接来传输多个请求/响应。
- **流水线 (Pipelining):** 客户端可以连续发送多个请求，无需等待前一个响应。
- **优点:** 开销小，延迟低。
- HTTP/1.1 默认使用此方式。可通过 `Connection: close` 首部指定关闭。

## 2.2.3 HTTP 报文格式

HTTP 报文是人类可读的 ASCII 文本。

### 1. HTTP 请求报文

```plaintext
GET /somedir/page.html HTTP/1.1
Host: www.someschool.edu
Connection: close
User-Agent: Mozilla/5.0
Accept-Language: fr

```

- **请求行 (Request Line):** `方法 URL HTTP版本` (e.g., `GET /index.html HTTP/1.1`)
- **首部行 (Header Lines):** `名称: 值` (e.g., `Host: www.example.com`, `User-Agent: BrowserInfo`, `Accept-Language: en`)。`Host` 在 HTTP/1.1 中是必需的。
- **实体主体 (Entity Body):** 通常用于 POST 方法，包含提交的数据。

### 2. HTTP 响应报文

```plaintext
HTTP/1.1 200 OK
Connection: close
Date: Tue, 18 Aug 2015 15:44:04 GMT
Server: Apache/2.2.3 (CentOS)
Last-Modified: Tue, 18 Aug 2015 15:11:03 GMT
Content-Length: 6821
Content-Type: text/html

(data data data data data ...)
```

- **状态行 (Status Line):** `HTTP版本 状态码 短语` (e.g., `HTTP/1.1 200 OK`, `HTTP/1.1 404 Not Found`)
- **首部行 (Header Lines):** `名称: 值` (e.g., `Date: ...`, `Server: Apache`, `Last-Modified: ...`, `Content-Type: text/html`, `Content-Length: 1234`)
- **实体主体 (Entity Body):** 包含请求的对象数据（如 HTML 文件、图片）。

## 2.2.4 用户与服务器的交互：cookie

用于克服 HTTP 无状态性，让服务器能识别和跟踪用户。

- **工作原理:**
  1.  服务器通过响应中的 `Set-Cookie:` 首部向浏览器发送一个唯一的 ID。
  2.  浏览器在本地 Cookie 文件中存储服务器主机名和该 ID。
  3.  浏览器在后续向该服务器的请求中，通过 `Cookie:` 首部将 ID 发回。
  4.  服务器使用该 ID 查询后端数据库，获取用户状态信息。
- **用途:** 用户认证、购物车、个性化推荐、会话保持。
- **隐私:** 可能引发用户跟踪和隐私泄露担忧。

## 2.2.5 Web 缓存 (代理服务器)

代表原始服务器响应 HTTP 请求的网络实体。

- **功能:** 存储最近请求对象的副本，加速访问，减少网络流量。
- **工作流程:** 浏览器请求 -> 缓存检查 -> (命中) 直接返回 / (未命中) 请求原始服务器 -> 存储副本 -> 返回给浏览器。
- **部署:** 通常由 ISP、机构部署。
- **优点:** 降低延迟，减少带宽消耗。

> **我的思考:** 缓存服务器是一个实际存在的硬件设备还是 Redis 这类软件？
> **答:** Web 缓存既可以是**运行在通用服务器硬件上的软件**（如 Squid, Nginx），也可以是**专门设计的硬件缓存设备**。核心在于其缓存和代理功能，实现形式可以多样。

### 条件 GET 方法

用于验证缓存副本是否仍然有效，避免下载未改变的对象。

- **机制:** 缓存向原始服务器发送 GET 请求，并附加 `If-Modified-Since: <缓存对象的最后修改日期>` 首部。
- **响应:**
  - 若对象未修改，服务器返回 `304 Not Modified` (空响应体)。
  - 若对象已修改，服务器返回 `200 OK` 和新对象。
- **缓存处理:**
  - 收到 304: 缓存知道本地副本有效，将**本地副本**用 `200 OK` 响应发给浏览器。
  - 收到 200: 缓存更新本地副本，并将**新副本**用 `200 OK` 响应发给浏览器。

> **我的思考:** 如果原始服务器返回了 304 Not Modified，那么缓存服务器会向浏览器发送什么？
> **答:** 缓存服务器**不会**将 304 响应转发给浏览器。它会从自己的本地存储中读取那个未过期的对象副本，然后构建一个状态码为 `200 OK` 的新 HTTP 响应，并将**缓存的（确认是新鲜的）对象数据**放在响应体中，发送给浏览器。

## 2.2.6 HTTP/2

HTTP/1.1 的后继者，旨在提高性能和效率。

- **目标:** 降低延迟，通过单一 TCP 连接实现多路复用，支持优先级和服务器推送，压缩首部。
- **动机:** 解决 HTTP/1.1 的队头阻塞 (HOL Blocking) 问题，减少并行 TCP 连接的需求。
- **核心变化:** 不改变 HTTP 语义，改变数据传输方式。

### 1. HTTP/2 帧 (Framing)

- 将 HTTP 报文分解为更小的二进制**帧**。
- 在**单个 TCP 连接**上**交错 (Interleaving)** 发送来自不同请求/响应的帧。
- 接收端负责**重组**帧。
- 有效解决 HOL 阻塞。
- **二进制编码**取代文本编码，更高效。

### 2. 响应报文优先级和服务器推送

- **优先级 (Prioritization):** 客户端可指定请求资源的优先级，服务器据此优化发送顺序。
- **服务器推送 (Server Push):** 服务器可预测客户端需求，在客户端请求前主动推送相关资源（如 CSS, JS），减少 RTT。

### HTTP/3

- 设计运行在 **QUIC** (基于 UDP 的新传输协议) 之上。
- 将多路复用等特性移至 QUIC 层，简化 HTTP/3 本身。

## 复习题

### R10

握手协议的作用是什么？

#### A10

握手协议用于在实际数据传输开始之前，通信双方交换控制信息，以建立连接、同步状态或协商参数。例如，TCP 的三次握手用于建立可靠连接，SMTP 的握手用于客户端和服务器相互标识并确认邮件传输的发送方和接收方。

### R11

为什么 HTTP、SMTP 及 POP3 都运行在 TCP，而不是 UDP 上？

#### A11

因为这些应用（Web 页面传输、邮件发送和接收）都要求**可靠的数据传输**。它们需要确保所有数据（如网页内容、邮件正文、命令）都能完整、按序、无差错地到达目的地。TCP 提供了这种可靠性保证，而 UDP 不提供。

### R12

考虑一个电子商务网站需要保留每一个客户的购买记录。描述如何使用 cookie 来完成该功能？

#### A12

1.  当客户首次访问或登录时，服务器创建一个唯一的客户 ID，并在响应中通过 `Set-Cookie:` 首部发送给客户浏览器。
2.  浏览器将该 ID 与网站域名关联存储起来。
3.  客户后续访问该网站时，浏览器会在请求中通过 `Cookie:` 首部自动发送该 ID。
4.  服务器收到 ID 后，可以在其后端数据库中查找与该 ID 关联的客户信息，包括其历史购买记录。当客户进行新的购买时，将购买信息添加到该客户 ID 对应的记录中。

### R13

描述 Web 缓存器是如何减少接收被请求对象的时延的。Web 缓存器将减少一个用户请求的所有对象或只是其中的某些对象的时延吗？为什么？

#### A13

Web 缓存器通过将最近请求过的对象副本存储在本地（靠近用户的位置）来减少时延。当用户再次请求这些对象时：

- 如果对象在缓存中（缓存命中），缓存可以直接将对象返回给用户，避免了通过可能较慢或较拥塞的互联网链路从原始服务器获取对象所需的时间。
- Web 缓存器**只减少**那些**可以被缓存**且**在缓存中命中**的对象的时延。对于第一次请求的对象（缓存未命中）、不可缓存的对象（如某些动态内容）、或者缓存副本已过期且原始服务器确认已修改的情况，缓存无法减少时延（甚至可能因为多了一跳而略微增加时延）。

### R14

Telnet 到一台 Web 服务器并发送一个多行的请求报文。在该请求报文中包含 If-modified-since:首部行，迫使响应报文中出现"304 Not Modified"状态代码。

#### A14

要强制服务器返回 304 状态码，需要在 `If-Modified-Since:` 首部中提供一个**晚于或等于**该对象实际最后修改时间的日期。例如，可以先用普通的 GET 请求获取一个对象，记下其 `Last-Modified` 响应首部中的日期。然后再次 Telnet 连接，发送一个包含 `If-Modified-Since: <记录下的日期>` 的 GET 请求，如果该对象此后未被修改，服务器理论上应返回 304。
_(注：实际操作时，需要确切知道对象的最后修改日期，并确保 telnet 命令和首部格式正确。)_

# 2.3 因特网中的电子邮件

### 核心组件

- **用户代理 (User Agents, UA):** 用户用于读写、管理邮件的软件/应用 (如 Outlook, Gmail App/Web)。
- **邮件服务器 (Mail Servers):** 存储用户邮箱 (Mailbox)，负责接收、发送和管理邮件。包含消息队列 (Message Queue) 用于暂存待发送邮件。
- **SMTP (Simple Mail Transfer Protocol):** 应用层协议，用于将邮件从发送方邮件服务器**推送 (push)** 到接收方邮件服务器。

### 电子邮件流程概览

1.  发送方 UA 通过 SMTP 或 HTTP 将邮件交给其邮件服务器。
2.  发送方邮件服务器 (作为 SMTP 客户端) 使用 SMTP 与接收方邮件服务器 (作为 SMTP 服务器) 建立 TCP 连接（端口 25）。
3.  通过 SMTP 协议将邮件传输到接收方服务器，存入接收方邮箱。
4.  接收方 UA 通过邮件访问协议 (POP3, IMAP, HTTP) 从其邮件服务器**拉取 (pull)** 邮件。

## 2.3.1 SMTP

- 定义于 [[5321|RFC 5321]]。
- 使用 **TCP** 提供可靠数据传输。
- **限制:** 邮件主体必须是 **7 位 ASCII** 编码。二进制数据需先编码再传输。
- **工作模式:**
  - 客户端-服务器模式，运行在邮件服务器之间。
  - 使用**持久连接**，可在同一 TCP 连接上传输多封邮件。
- **主要命令:**
  - `HELO` / `EHLO`: 客户端标识。
  - `MAIL FROM:`: 指定发件人（用于错误返回）。
  - `RCPT TO:`: 指定收件人。
  - `DATA`: 表示开始传输邮件内容（首部+主体）。
  - `.` (单独一行): 邮件内容结束标记。
  - `QUIT`: 关闭连接。
- **交互过程:** 建立 TCP -> 握手 (HELO, MAIL FROM, RCPT TO) -> 传输数据 (DATA, 邮件内容, `.`) -> 关闭 (QUIT)。

## 2.3.2 与 HTTP 的对比 _(这部分在原文 2.3.1 节中有提及，在此单独列出)_

- **传输方向:** HTTP 主要用于从服务器**拉取**信息 (pull)；SMTP 主要用于向服务器**推送**信息 (push)。
- **编码:** SMTP 要求邮件主体为 7 位 ASCII；HTTP 无此限制。
- **报文组织:** HTTP 将每个对象封装在其自己的响应报文中；SMTP 将所有报文对象（包括多个对象，如附件，需编码）放在一个报文的主体部分。

## 2.3.3 邮件报文格式

- 邮件内容格式定义于 [[5322|RFC 5322]]。
- **结构:**
  - **首部行 (Header Lines):** 包含元信息 (e.g., `From:`, `To:`, `Subject:`, `Date:`, `Received:`)。
  - **空行:** 分隔首部和主体。
  - **主体 (Body):** 邮件实际内容 (7 位 ASCII)。
- **注意:** 邮件**首部行** (`From:`) 不同于 SMTP **命令** (`MAIL FROM:`)。前者是邮件内容一部分，后者是协议传输过程中的信封信息。

## 2.3.4 邮件访问协议

用于用户 UA 从邮件服务器获取邮件（拉取操作）。

- **POP3 (Post Office Protocol - Version 3)**
  - 定义于 [[1939|RFC 1939]]。
  - 极其简单，功能有限（下载并通常删除服务器副本）。
  - 跨会话**无状态**。
- **IMAP (Internet Mail Access Protocol)**
  - 定义于 [[3501|RFC 3501]]。
  - 功能强大，允许用户在服务器上管理邮件和文件夹。
  - 支持远程查看邮件部分内容。
  - 跨会话**有状态**。
- **HTTP**
  - 通过 Web 浏览器或 App 访问邮件服务（如 Gmail, Outlook.com）。
  - 极其流行，提供了丰富的用户界面和功能。

# 2.4 DNS: 因特网的目录服务

DNS (Domain Name System) 是互联网核心功能之一，作为应用层协议运行，主要提供将用户友好的**主机名 (hostname)** 解析为网络设备（如路由器）使用的**IP 地址**的服务。它像互联网的“电话簿”。

## 2.4.1 DNS 提供的服务

DNS 不仅仅是主机名到 IP 地址的翻译器，还提供以下关键服务：

1.  **主机名到 IP 地址转换:** 这是 DNS 最核心的功能。应用程序（如浏览器）通过 DNS 查询获取目标服务器的 IP 地址，才能建立连接。
2.  **主机别名 (Host Aliasing):**
    - 允许一个复杂难记的**规范主机名 (Canonical Hostname)** 拥有一个或多个易于记忆的**别名 (Alias)**。
    - 应用程序可以通过查询别名来获取其规范主机名和对应的 IP 地址。通过 **CNAME** 记录实现。
    - 例如，`server-farm-west.example.com` (规范名) 可以有别名 `www.example.com`。
3.  **邮件服务器别名 (Mail Server Aliasing):**
    - 允许电子邮件地址使用简单的域名（如 `user@company.com`），而实际处理邮件的服务器可以有不同的、可能更复杂的主机名。
    - 使得一个组织的 Web 服务器和邮件服务器可以使用相同的域名别名（如 `company.com`）。
    - 邮件客户端查询 **MX (Mail eXchange)** 记录来找到负责特定域名的邮件服务器的规范主机名。
4.  **负载分配 (Load Distribution):**
    - 对于部署在多台服务器上的繁忙网站（如大型门户网站），DNS 可以将一个主机名映射到**一组 IP 地址**。
    - 当收到查询时，DNS 服务器返回整个 IP 地址集合，但通常会**轮换**列表中地址的顺序。
    - 客户端通常尝试连接列表中的第一个 IP 地址，从而将请求流量**分散**到不同的服务器实例上。

## 2.4.2 DNS 工作机理概述

由于集中式 DNS 存在单点故障、流量瓶颈、高延迟和维护困难等问题，无法扩展，DNS 被设计为一个**分布式、层次化**的系统。

### 1. 分布式、层次数据库

DNS 数据库分布在全球范围的 DNS 服务器中，这些服务器按层次组织：

- **根 DNS 服务器 (Root DNS Servers):**
  - 处于层次结构的顶端。全球有 13 个逻辑根服务器，但有上千个物理实例。
  - 不直接解析具体主机名，而是**指向**相应的**顶级域 (TLD) 服务器**。
- **顶级域 (TLD) DNS 服务器 (Top-Level Domain Servers):**
  - 管理顶级域名（如 `.com`, `.org`, `.edu`）和国家顶级域名（如 `.cn`, `.uk`）。
  - 存储**权威 DNS 服务器**的地址信息。例如，`.com` TLD 服务器知道 `google.com` 的权威服务器在哪里。
- **权威 DNS 服务器 (Authoritative DNS Servers):**

  - 组织机构（公司、大学）自行管理或委托管理的服务器，包含其域内主机的**官方** DNS 记录（主机名到 IP 地址的最终映射）。
  - 是解析查询的最终目的地。

- **本地 DNS 服务器 (Local DNS Server):**

  - 不属于严格的层次结构，但对用户至关重要。
  - 通常由用户的 ISP 或机构提供。用户主机的 DNS 查询**首先**发送到本地 DNS 服务器。
  - 本地 DNS 服务器作为**代理**，负责在 DNS 层次结构中**迭代查询**，并将最终结果返回给用户主机。

- **查询过程 (典型):**
  - **主机 -> 本地 DNS (递归查询):** 主机请求本地 DNS 服务器代为解析。
  - **本地 DNS -> 根 -> TLD -> 权威 DNS (迭代查询):** 本地 DNS 逐级询问，每级服务器返回下一级服务器的地址，直到找到权威服务器获得最终 IP 地址。

### 2. DNS 缓存 (DNS Caching)

- **目的:** 提高查询效率，减少网络流量和根/TLD 服务器负载。
- **机制:** 当 DNS 服务器（尤其是本地 DNS 服务器）收到 DNS 响应时，会将响应中的映射信息（如主机名->IP 地址）**存储**在本地缓存中一段时间。
- **TTL (Time-to-Live):** 每个 DNS 记录都有一个 TTL 值，指示该记录可以在缓存中保留多长时间。过期后缓存记录被丢弃。
- **效果:** 对同一主机名的后续查询可以直接由缓存响应，避免了完整的层次查询过程。大多数查询实际上由本地缓存解决。

## 2.4.3 DNS 记录和报文

DNS 数据库存储**资源记录 (Resource Records, RR)**。

- **RR 格式:** `(Name, Value, Type, TTL)`
  - **Type=A:** IPv4 地址记录 (Name: 主机名, Value: IPv4 地址)
  - **Type=AAAA:** IPv6 地址记录 (Name: 主机名, Value: IPv6 地址)
  - **Type=NS:** 权威名称服务器记录 (Name: 域, Value: 该域的权威 DNS 服务器主机名)
  - **Type=CNAME:** 规范名称记录 (Name: 别名, Value: 规范主机名)
  - **Type=MX:** 邮件交换记录 (Name: 域, Value: 该域的邮件服务器规范主机名，还有一个优先级值)

### 1. DNS 报文

- 只有两种类型：**查询 (Query)** 和 **响应 (Reply)**，格式相同。
- **主要部分:**
  - **首部 (Header):** 包含查询 ID、标志位（查询/响应、权威性、递归期望/可用等）、各部分记录数。
  - **问题 (Question):** 包含正在查询的名称和类型。
  - **回答 (Answer):** 包含查询结果的 RR。
  - **权威 (Authority):** 包含指向其他权威服务器的 RR (NS 记录)。
  - **附加 (Additional):** 包含一些有用的附加信息，如回答/权威部分中服务器主机名的 IP 地址 (A 记录)。

### 2. 在 DNS 数据库中插入记录

- **注册域名:** 在**注册商 (Registrar)** 处注册，需提供权威 DNS 服务器的主机名和 IP 地址。
- **TLD 更新:** 注册商负责将该域的 NS 记录和权威服务器的 A 记录插入到相应的 **TLD 服务器**数据库中。
- **配置权威服务器:** 机构需要在自己的权威 DNS 服务器中配置其域内所有主机的 A, AAAA, MX, CNAME 等记录。

_(DNS 安全: DNSSEC 使用数字签名来验证 DNS 数据的真实性和完整性，防止缓存污染和欺骗。)_

### R19

一个机构的 Web 服务器和邮件服务器可以有完全相同的主机名别名（例如，foo.com）吗？包含邮件服务器主机名的 RR 有什么样的类型？

#### A19

**可以**。一个机构完全可以让其 Web 服务器和邮件服务器都使用 `foo.com` 这个别名。这是通过不同的 DNS 记录类型来区分的：

- 当浏览器查询 `foo.com`（想访问 Web 服务器）时，它会请求 **A** 或 **AAAA** 记录来获取 IP 地址。DNS 可能通过 CNAME 记录指向 Web 服务器的规范主机名，再返回其 A/AAAA 记录。

- 因此，包含邮件服务器信息的资源记录 (RR) 类型是 **MX** 记录。

# 2.5 对等方到对等方 (P2P) 文件分发

本节探讨使用 P2P 架构进行大规模文件分发的优势和具体实现（以 BitTorrent 为例）。

### P2P 文件分发的背景

- **场景:** 将一个大文件（如软件、视频）从单个源服务器分发给大量对等方 (Peers)。
- **C/S 架构的局限:** 服务器需向每个对等方发送完整副本，带宽需求和分发时间随对等方数量 N 线性增长，**可扩展性差**。
- **P2P 架构的思路:** 每个对等方在下载的同时也上传已接收的数据块给其他对等方，**协助服务器分发**，利用对等方的上传带宽。

### P2P 架构的可扩展性分析

通过定量模型比较 C/S 和 P2P 的最小分发时间。

- **参数定义:**
  - `F`: 文件大小 (bits)
  - `N`: 对等方数量
  - `u_s`: 服务器上传速率
  - `u_i`: 第 i 个对等方上传速率
  - `d_i`: 第 i 个对等方下载速率
  - `d_min`: 最小对等方下载速率
- **客户端-服务器 (C/S) 分发时间 `D_cs`:**
  - 受限于服务器总上传量 (`NF`) 和最慢下载者的下载时间 (`F/d_min`)。
  - `D_cs = max{ NF / u_s, F / d_min }`
  - 结论：随 N 线性增长（主要受 `NF / u_s` 限制）。
- **对等方到对等方 (P2P) 分发时间 `D_p2p`:**
  - 受限于服务器首次上传 (`F/u_s`)、最慢下载者 (`F/d_min`) 以及**系统总上传能力** (`NF / (u_s + Σu_i)`)。
  - `D_p2p = max{ F / u_s, F / d_min, NF / (u_s + Σu_i) }`
  - 结论：随着 N 增加，系统总上传能力也增加，分发时间增长远慢于 C/S，展现**自扩展性 (Self-scalability)**。

### BitTorrent 协议

一个流行的 P2P 文件分发协议。

- **核心术语:**
  - **Torrent:** 参与特定文件分发的所有对等方的集合。
  - **块 (Chunks):** 文件被分割成的固定大小（如 256KB）的数据片段，是交换的基本单位。
  - **Tracker:** 一个中心服务器，负责**跟踪** Torrent 中活跃对等方的 IP 地址列表。
- **工作流程:**
  1.  **加入:** 新对等方联系 Tracker，获取一部分活跃对等方的 IP 列表。
  2.  **邻居建立:** 与列表中的对等方建立 **TCP 连接**，形成**邻居 (Neighbors)** 关系（动态变化）。
  3.  **块信息交换:** 定期与邻居交换各自拥有的文件块列表。
  4.  **下载策略 - 最稀缺优先 (Rarest First):**
      - 识别自己缺少且在邻居中副本最少的块。
      - 优先向拥有这些“最稀缺”块的邻居请求下载。
      - 目的：加速稀有块在网络中的传播，提高整体完成度。
  5.  **上传策略 - 针锋相对 (Tit-for-Tat):**
      - 基于**互惠原则**，优先服务那些给自己提供数据最快的邻居。
      - **机制:**
        - 持续测量从各邻居的下载速率。
        - **定期（如 10s）疏通 (Unchoke):** 向下载速率最高的 **4 个**邻居上传数据。
        - **定期（如 30s）优化疏通 (Optimistically Unchoke):** 随机选择**另外 1 个**邻居进行上传，即使它当前没给自己提供数据（给新人机会/寻找更好伙伴）。
        - **阻塞 (Choke):** 其他所有邻居都被阻塞，不给它们上传数据。
      - 目的：激励对等方贡献上传带宽，抑制“搭便车”行为。
- **其他:** 还包括子块、流水线请求、随机初始块、残局模式、反怠慢等机制。
- **DHT (分布式哈希表):** 用于实现无 Tracker 的 Torrent，进一步去中心化。

## 复习题

### R21

在 BitTorrent 中，假定 Alice 向 Bob 提供一个 30 秒间隔的文件块吞吐量。Bob 将必须进行回报，在相同的间隔中向 Alice 提供文件块吗？为什么？

#### A21

**不一定必须。** Bob 是否会向 Alice 提供文件块取决于 BitTorrent 的 Tit-for-Tat 机制：

1.  **如果 Alice 是 Bob 下载速率最高的前 4 位邻居之一：** 那么 Bob **会**回报 Alice，对 Alice 进行疏通 (Unchoke) 并向她发送文件块。这是互惠原则的核心。
2.  **如果 Alice 不是 Bob 的前 4 位下载提供者，但 Bob 在其 30 秒一次的“优化疏通”中随机选择了 Alice：** 那么 Bob **也会**向 Alice 发送文件块。这是为了给新的或表现不佳的连接一个机会。
3.  **如果 Alice 既不是 Bob 的前 4 位提供者，也没有被 Bob 随机选中进行优化疏通：** 那么 Bob **不会**向 Alice 发送文件块，Alice 会被 Bob 阻塞 (Choke)。

所以，Alice 向 Bob 提供数据只是增加了 Bob 回报 Alice 的**可能性**（通过成为 Bob 的 Top 4 贡献者），但**并非绝对保证** Bob 会立即或在同一时间段内回报。

### R22

考虑一个新对等方 Alice 加入 BitTorrent 而不拥有任何文件块。没有任何块，因此她没有任何东西可上载，她无法成为任何其他对等方的前 4 位上载者。那么 Alice 将怎样得到她的第一个文件块呢？

#### A22

Alice 能够通过 **优化疏通 (Optimistically Unchoked)** 机制获得她的第一个文件块。

即使 Alice 没有任何块可以上传（因此无法成为任何邻居的前 4 位上传者），她仍然会与一些邻居建立连接。她的邻居们会**每隔 30 秒随机选择一个**被阻塞的邻居进行“优化疏通”，并向其发送数据块。Alice 有机会被她的某个邻居随机选中。一旦她通过这种方式接收到了第一个（或几个）文件块，她就可以开始将这些块上传给其他请求这些块的邻居，从而有机会凭借上传速率进入其他邻居的“Top 4”列表，获得更稳定的下载速率。

### R23

覆盖网络是什么？它包括路由器吗？在覆盖网络中边是什么？

#### A23

- **覆盖网络 (Overlay Network):** 是一个构建在**现有网络**（通常是底层 IP 网络）之上的**虚拟网络**。在这个网络中，节点是**应用层**的实体（例如 P2P 网络中的对等方主机、CDN 中的缓存服务器等）。
- **它包括路由器吗？** **不直接包括**。覆盖网络的节点是端系统或应用层设备。底层的 IP 路由器负责在物理网络上传输覆盖网络节点之间的数据包，但这些路由器本身**不是**覆盖网络的组成节点。
- **在覆盖网络中边是什么？** 覆盖网络中的**边 (Edge)** 代表了两个覆盖网络节点之间的**虚拟链路**或**逻辑连接**。这条“边”通常对应于底层网络中的一条或多条物理链路以及其间的路由器所构成的**路径**。例如，在 BitTorrent 中，Alice 和她的邻居 Bob 之间存在一条覆盖网络的边，这条边意味着它们之间存在一个活动的 TCP 连接，而这个 TCP 连接的数据包在底层 IP 网络中可能经过了多个路由器和物理链路。

# 2.6 视频流和内容分发网

本节探讨互联网视频流的特性、传输方法以及解决大规模分发挑战的内容分发网络 (CDN)。

## 2.6.1 因特网视频

- **主要类型:** 存储的流式视频 (点播)。
- **特性:**
  - 高比特率（压缩后从 kbps 到 Mbps 甚至更高）。
  - 对网络**吞吐量**要求高，需大于等于视频比特率以保证连续播放。
  - 可以通过压缩创建**多版本**（不同比特率/质量）。

## 2.6.2 HTTP 流和 DASH

视频通过 HTTP 传输的两种主要方式：

1.  **HTTP 流 (HTTP Streaming):**
    - 将视频作为普通文件存储在 HTTP 服务器上。
    - 客户端通过 HTTP GET 请求获取整个文件，边下载边缓冲边播放。
    - **缺点:** 无法适应客户端网络带宽变化，所有用户接收相同编码。
2.  **DASH (Dynamic Adaptive Streaming over HTTP):**
    - **原理:**
      - 服务器将视频预编码为**多个不同码率的版本**，并将每个版本切分成短**视频块 (Chunks)**。
      - 服务器提供**清单文件 (Manifest File)**，包含各版本和块的信息。
      - 客户端**动态地**根据当前测量的网络带宽，使用 HTTP GET 逐个请求**最适合码率**的视频块。
    - **优点:** 实现**动态码率自适应**，在不同网络条件下提供尽可能流畅和高质量的观看体验。利用现有 HTTP 基础设施。

## 2.6.3 内容分发网 (CDNs)

用于高效、大规模地向全球用户分发内容（尤其是视频）的分布式服务器网络。

- **解决的问题:** 集中式数据中心的延迟高、带宽浪费、单点故障。
- **核心机制:**
  - 在**多个地理位置**部署服务器（集群），存储内容**副本**。
  - 将用户请求**导向**到最佳的 CDN 节点（通常是最近或网络条件最好）。
- **部署策略:**
  - **深入部署 (Enter Deep):** 在接入 ISP 网络内部部署大量小型集群，靠近用户。
  - **放置 IXP (Bring Home):** 在少量 IXP 部署大型集群，高效连接多个 ISP。
- **内容复制策略:**
  - **拉取 (Pull):** 按需从源或其他节点获取内容并缓存（类似 Web 缓存）。
  - **推送 (Push):** 主动将内容（如热门视频）在非高峰期推送到 CDN 节点。
- **工作流程:**
  1.  **拦截请求:** 通常利用 **DNS** 拦截用户对原始内容 URL 的请求。
  2.  **选择集群:** CDN 的 DNS 系统根据用户来源（LDNS IP）等信息选择最佳 CDN 集群。
  3.  **重定向:** CDN 的 DNS 将选定集群中内容服务器的 IP 地址返回给用户。
  4.  **直接通信:** 用户直接与该 CDN 服务器通信获取内容。
- **集群选择策略考虑因素:** 地理位置、网络路径（延迟、丢包、带宽）的实时测量、负载均衡等。

## 2.6.4 学习案例: Netflix 与 YouTube

- **Netflix:**
  - **架构:** AWS (处理非流媒体业务、视频转码、CDN 上传) + 自建私有 CDN (Open Connect)。
  - **CDN 部署:** IXP + ISP 内部，使用**推送**缓存。
  - **流媒体:** 使用 **DASH** (专有版本) 实现自适应流。
  - **服务器选择:** 由 AWS 上的**中央控制逻辑直接分配** CDN 服务器 IP 给客户端，**不使用 DNS 重定向**。
- **YouTube (Google):**
  - **架构:** Google 全球基础设施 (数据中心、CDN、私有骨干网)。
  - **CDN 部署:** IXP + ISP 内部，使用**拉取**缓存。
  - **流媒体:** 主要使用**基本的 HTTP 流**，提供多版本供用户**手动选择**，不使用 DASH 自适应。
  - **服务器选择:** 使用 **DNS 重定向**将用户导向合适的 CDN 集群（通常考虑 RTT 和负载均衡）。

## 复习题

### R24

CDN 通常采用两种不同的服务器放置方法之一。列举并简单描述它们。

#### A24

CDN 服务器放置的两种主要哲学是：

1.  **深入部署 (Enter Deep):** 将大量（通常是数千个）规模较小的服务器集群部署到全球许多接入 ISP 网络**内部**。这种策略的目标是尽可能地将服务器靠近终端用户，以最大限度地减少网络延迟和跳数，提高用户感知的吞吐量。
2.  **放置 IXP (Bring Home):** 在全球较少数量（例如几十个）的**互联网交换点 (IXPs)** 处建立大型的服务器集群。这种策略通过将服务器置于网络的关键连接点，可以高效地与多个 ISP 进行互联，服务于这些 ISP 的用户。相比深入部署，管理维护更集中，成本可能更低。

### R25

除了如时延、丢包和带宽性能等网络相关的考虑外，设计一种 CDN 服务器选择策略时还有其他重要因素。它们是什么？

#### A25

除了网络性能指标（时延、丢包、带宽）外，设计 CDN 服务器选择策略时还需考虑以下重要因素：

1.  **负载均衡 (Load Balancing):** 需要将用户请求**均匀地**或**按能力地**分散到不同的 CDN 集群或服务器上，避免某个节点过载而影响性能。即使某个集群网络条件最好，如果它已经超负荷，也可能需要将用户导向次优但负载较轻的集群。
2.  **成本 (Cost):** 不同 CDN 节点或不同 ISP 之间的带宽成本可能不同。选择策略可能会考虑将流量导向成本较低的路径或节点，尤其是在满足基本性能要求的前提下。
3.  **用户来源的准确性:** 基于 LDNS IP 地址进行地理定位或网络测量可能不准确（LDNS 可能远离实际用户），选择策略需要考虑如何处理这种情况或使用其他信息（如客户端 IP 子网信息）来辅助判断。
4.  **内容的可用性:** 选择的 CDN 节点必须**实际存储**了用户请求的内容副本。
5.  **策略的复杂性与开销:** 更复杂的选择策略（如依赖大量实时测量）可能本身会带来额外的开销和管理复杂度。需要在性能提升和实现成本之间取得平衡。
