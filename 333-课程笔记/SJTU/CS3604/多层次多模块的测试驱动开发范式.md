# 多层次多模块的测试驱动开发范式

在《软件工程与项目管理》课程的 Nomad 项目中，我们组尝试了一套"多层次多模块的测试驱动开发范式"。这个决定源于两个初衷：一是希望通过严格的测试体系来应对复杂的业务逻辑，二是想探索如何利用 AI 辅助开发时仍能保证代码质量。然而，一学期的实践下来，我们发现理想与现实之间存在着巨大的鸿沟。这篇文章想和老师分享我们在这个过程中的真实困境、深刻反思，以及最终对 TDD 本质的重新认识。

## 我们组的测试框架

项目初期，我们参考业界最佳实践，设计了一套金字塔式的测试策略。最底层是单元测试，针对那些纯函数——比如价格计算逻辑、日期格式转换等工具类方法，确保最小单元的逻辑正确无误。往上一层是组件测试，我们希望通过它来验证前端组件的独立交互逻辑，比如表单验证规则、状态切换动画等是否按预期工作。再往上是集成测试，这一层聚焦于后端的 Service 层和 Server Actions，我们会在隔离的测试数据库上验证那些关键的业务规则，像库存扣减的原子性、事务的一致性保证等。金字塔的顶端是端到端测试，我们用 Playwright 模拟真实用户的完整操作路径，从搜索航班、选择座位到最终支付，确保整个业务链路能够闭环运行。

我们在项目初期还能够保持这一套 TDD 的流程与框架，但是随着后面更多需求的加入，我发现这套框架行不通。

## 我们的TDD为什么不行

第一个困境出现在需求转化阶段。我们手里有一份详细的需求文档，上面写着"用户应该能够搜索指定日期的航班""系统需要防止超售"这样的业务描述。但当我们坐下来准备把这些需求转化为测试代码时，却发现无从下手。需求文档描述的是业务意图——为什么要做、做什么，而测试代码需要的是实现细节——怎么做。这两者之间存在着一道难以跨越的鸿沟。

我们组遇到更大的困难是，在编写测试时，我们需要预先知道函数的命名、参数的数据结构、甚至可能抛出的异常类型。但这些信息在"还没开始写代码"的阶段根本不存在。我们陷入了一个悖论：要写测试，必须先知道实现细节；但 TDD 的精髓恰恰是"先测试后实现"。结果就是，需求文档没有办法转换成具体的测试代码。我们的解决办法就是让 AI 先按照需求直接实现第一版简单代码，然后对着第一版简单代码反过来补充测试代码，但是这个方案的弊端很多：需求文档必须描述准确，否则后期很多细节的代码都需要修复调整。

第二个更严重的问题出现在前端开发上。项目中后期，我们才意识到：**对 UI 进行 TDD 可能是个错误**。我们的项目是模仿携程官网的机票预订系统，没有专业的 UI 设计师，没有 Figma 原型，唯一的参照物就是携程的网站。在这种情况下，我们的前端开发本质上是一个不断试错、调整的探索过程。今天可能觉得用弹窗展示航班详情比较好，明天又觉得侧边Sidebar更符合用户习惯；这周定的是蓝色主题，下周又想改成橙色来更贴近携程的风格。

每一次这样的调整，都会导致大量的组件测试失败。我们发现自己陷入了一个恶性循环：修改 UI → 测试失败 → 修复测试 → 再次修改 UI → 测试又失败。有一次，我们仅仅是把一个按钮的位置从右上角移到了左下角，结果导致十几个测试用例需要重写。我们花在修复测试上的时间，远远超过了直接手动点击页面验证功能的时间。

## TDD 应该怎么做

下面是我们组目前对于 TDD 的思考，但是这些不一定准确，还没有经过完善的验证：

首先，我们重新思考了在 AI 辅助开发场景下，人和 AI 各自应该承担什么角色。我们发现，人类不应该去写那些琐碎的实现细节测试，比如"这个函数应该返回一个包含三个字段的对象"。这种测试既脆弱又没有太多价值，因为它们测试的是"怎么做"，而不是"做什么"。人类真正应该关注的是**行为测试**——定义系统对外的契约。比如，"当用户尝试预订一个已售罄的航班时，系统应该返回错误提示并阻止预订"，这才是我们需要用测试固化下来的业务规则。至于 AI 用什么算法、什么数据结构来实现这个规则，在一定程度上可以是黑盒的，只要最终行为符合预期即可。

其次，我们把前端测试的范围大幅收缩，只保留那些核心的状态机逻辑测试。比如，一个复杂的多步骤表单，其中有大量的字段联动关系(选择了国际航班就必须填写护照号，选择了儿童票就必须填写监护人信息)，这种逻辑用测试来保护是有价值的。但对于"这个按钮应该是圆角还是直角""这段文字应该是 14px 还是 16px"这类视觉细节，写测试就是浪费时间。

最后，我们遇到了一个更深层的问题：TDD 只能保证代码"是对的"，但不能保证代码"是好的"。在使用 AI 辅助开发时，这个问题尤为突出。AI 为了快速通过测试，经常会生成一些结构混乱的代码。比如，我们发现 AI 生成的某个 Service 函数里，直接编写 SQL 查询语句，完全绕过了我们精心设计的 Repository 层。测试通过了，功能也正常，但代码架构被破坏了。也就是说 TDD 不代表可以不用 code review。
