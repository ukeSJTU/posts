# 简答题

## 第一题

简述 TCP 和 UDP 的主要区别，并从以下场景中选择最适合的协议并说明原因：

1. 实时视频会议
2. 文件传输
3. 在线游戏
4. DNS 查询

### 答案

| 协议类型 | 连接方式             | 可靠性                         | 流量/拥塞控制 | 速度 | 适用场景                   |
| -------- | -------------------- | ------------------------------ | ------------- | ---- | -------------------------- |
| TCP      | 面向连接（三次握手） | 可靠，保证顺序、无差错、不丢失 | 有            | 较慢 | 对数据可靠性要求高的场景   |
| UDP      | 无连接               | 不可靠，可能丢失、乱序、重复   | 无            | 快   | 实时性高或能容忍丢失的场景 |

1. **实时视频会议**：推荐 **UDP**。实时性要求高，允许少量数据丢失，不需要每个数据包都可靠送达，UDP 延迟低，适合音视频传输。

2. **文件传输**：推荐 **TCP**。文件传输要求数据完整、可靠，不能丢失或出错，TCP 能保证数据顺序和完整性。

3. **在线游戏**：推荐 **UDP**。实时性高，部分数据丢失不会影响整体体验，UDP 延迟低，适合及时反馈操作。

4. **DNS 查询**：推荐 **UDP**。查询数据量小，响应快，允许偶尔重试，UDP 效率高。只有在数据量较大或需要可靠性时才用 TCP。

## 第二题

假设 TCP 的序号字段长度为 64 位（实际标准为 32 位），且初始序号为 0。

1. 若发送方以每秒 10 Gbps 的速率发送数据，需要多少时间才会发生序号回绕（wrap-around）？
2. 如果接收方最大报文段生存时间（MSL）为 2 分钟，这样的序号长度是否能避免序号混淆问题？

### 答案

1. 序号回绕所需时间

每秒钟发送的字节数：

$$
10\, \text{Gbps} = 10 \times 10^9\, \text{bit/s} = \frac{10 \times 10^9}{8} = 1.25 \times 10^9\, \text{byte/s}
$$

序号回绕所需时间：

$$
\text{回绕时间} = \frac{2^{64}}{1.25 \times 10^9} \approx \frac{1.8446744 \times 10^{19}}{1.25 \times 10^9} \approx 1.47573952 \times 10^{10}\,\text{秒}
$$

换算成年：

$$
\frac{1.47573952 \times 10^{10}}{60 \times 60 \times 24 \times 365} \approx 468.1\, \text{年}
$$

因此，以 10 Gbps 的速率，TCP 序号字段（64 位）需要约 468 年才会回绕一次。

2. 能否避免序号混淆

只要回绕时间远大于 MSL，就不会发生序号混淆。64 位序号长度完全可以避免序号混淆问题，远远大于 MSL 所需的安全范围。

## 第三题

假设一个 TCP 连接处于慢启动阶段，初始拥塞窗口（cwnd）为 1 MSS（最大报文段长度），阈值为 16 MSS。

1. 在第 1 到第 5 个 RTT 内，每次收到 ACK 后 cwnd 如何变化？请列出每个 RTT 结束时的 cwnd 值。
2. 若在第 6 个 RTT 时发生超时，阈值和 cwnd 将如何调整？
3. 若在第 7 个 RTT 改用拥塞避免阶段，此时 cwnd 增长方式有何不同？

### 答案

1. 第 1 到第 5 个 RTT 内 cwnd 变化

慢启动阶段，每收到一个 ACK，cwnd 增加 1 MSS。每个 RTT 结束时，cwnd 大致会翻倍（因为每发送一个数据包都能收到 ACK，下一 RTT 能发送的数据包数就是当前 cwnd 的两倍）。

| RTT | cwnd 变化过程（单位：MSS）    | RTT 结束时 cwnd（MSS） |
| --- | ----------------------------- | ---------------------- |
| 1   | 1 -> 收到 1 个 ACK，变为 2    | 2                      |
| 2   | 2 -> 收到 2 个 ACK，变为 4    | 4                      |
| 3   | 4 -> 收到 4 个 ACK，变为 8    | 8                      |
| 4   | 8 -> 收到 8 个 ACK，变为 16   | 16                     |
| 5   | 16 -> 收到 16 个 ACK，变为 32 | 32                     |

2. 第 6 个 RTT 发生超时时，阈值和 cwnd 调整

- 阈值（ssthresh）设置为发生超时时 cwnd 的一半：
  $$
  ssthresh = \frac{cwnd}{2} = \frac{32}{2} = 16\,\text{MSS}
  $$
- cwnd 重置为 1 MSS。

3. 第 7 个 RTT 进入拥塞避免阶段时 cwnd 增长方式

- 拥塞避免阶段，cwnd 以线性方式增长：每收到一个 RTT 的 ACK，cwnd 增加 1 MSS（而不是每个 ACK 增加 1 MSS）。

### 2. 理解代码

查看`examples/tcp/tcp-variants-comparison.cc`里面的代码，尤其是参数部分：

#### 传输协议与 TCP 变体

```cpp
cmd.AddValue("transport_prot", "Transport protocol to use: TcpNewReno, TcpLinuxReno, TcpHybla, TcpHighSpeed, TcpHtcp, TcpVegas, TcpScalable, TcpVeno, TcpBic, TcpYeah, TcpIllinois, TcpWestwoodPlus, TcpLedbat, TcpLp, TcpDctcp, TcpCubic, TcpBbr", transport_prot);
```

**含义**：选择要使用的 TCP 拥塞控制算法。NS-3 支持多种 TCP 变体，包括：

- **TcpNewReno**：经典的 TCP 实现，采用加性增加乘性减少(AIMD)策略 [1]
- **TcpCubic**：当前 Linux 默认的 TCP 算法，使用三次函数来控制拥塞窗口 [8]
- **TcpBbr**：Google 开发的基于瓶颈带宽和往返传播时间的拥塞控制算法 [9]
- 其他多种 TCP 变体，每种都有其特定的拥塞控制机制 [4]

#### 网络环境参数

```cpp
cmd.AddValue("error_p", "Packet error rate", error_p);
cmd.AddValue("bandwidth", "Bottleneck bandwidth", bandwidth);
cmd.AddValue("delay", "Bottleneck delay", delay);
cmd.AddValue("access_bandwidth", "Access link bandwidth", access_bandwidth);
cmd.AddValue("access_delay", "Access link delay", access_delay);
```

**含义**：

- **error_p**：数据包错误率，模拟网络中的随机丢包率 [2]
- **bandwidth**：瓶颈链路带宽，网络中最慢的链路速度，通常以 Mbps 为单位 [1]
- **delay**：瓶颈链路延迟，通常以 ms 为单位 [1]
- **access_bandwidth**：接入链路带宽，端节点连接到核心网络的链路速度 [2]
- **access_delay**：接入链路延迟，端节点到核心网络的传播延迟 [2]

#### 实验控制参数

```cpp
cmd.AddValue("tracing", "Flag to enable/disable tracing", tracing);
cmd.AddValue("prefix_name", "Prefix of output trace file", prefix_file_name);
cmd.AddValue("data", "Number of Megabytes of data to transmit", data_mbytes);
cmd.AddValue("mtu", "Size of IP packets to send in bytes", mtu_bytes);
cmd.AddValue("num_flows", "Number of flows", num_flows);
cmd.AddValue("duration", "Time to allow flows to run in seconds", duration);
cmd.AddValue("run", "Run index (for setting repeatable seeds)", run);
```

**含义**：

- **tracing**：启用/禁用跟踪功能，用于收集详细的网络行为数据 [5]
- **prefix_name**：输出跟踪文件的前缀名称 [5]
- **data_mbytes**：要传输的数据量，以兆字节为单位 [1]
- **mtu_bytes**：发送的 IP 数据包大小，以字节为单位 [7]
- **num_flows**：同时运行的 TCP 流数量，用于测试多流竞争情况 [2]
- **duration**：允许流运行的时间，以秒为单位 [4]
- **run**：运行索引，用于设置可重复的随机种子，确保实验可重复性 [5]

#### 监控与分析参数

```cpp
cmd.AddValue("flow_monitor", "Enable flow monitor", flow_monitor);
cmd.AddValue("pcap_tracing", "Enable or disable PCAP tracing", pcap);
```

**含义**：

- **flow_monitor**：启用流监控功能，收集流级别的统计数据，如吞吐量、延迟等 [5]
- **pcap_tracing**：启用或禁用 PCAP 跟踪，可以生成可用 Wireshark 等工具分析的数据包捕获文件 [5]

#### 队列与拥塞控制参数

```cpp
cmd.AddValue("queue_disc_type", "Queue disc type for gateway (e.g. ns3::CoDelQueueDisc)", queue_disc_type);
cmd.AddValue("sack", "Enable or disable SACK option", sack);
cmd.AddValue("recovery", "Recovery algorithm type to use (e.g., ns3::TcpPrrRecovery", recovery);
```

**含义**：

- **queue_disc_type**：网关使用的队列规则类型，例如 CoDel (Controlled Delay) 队列规则用于减少缓冲膨胀 [7]
- **sack**：启用或禁用选择性确认(SACK)选项，SACK 允许接收方确认非连续的数据块，提高重传效率 [3]
- **recovery**：使用的恢复算法类型，例如 PRR (Proportional Rate Reduction)，用于控制丢包后的恢复行为 [3]

### 5. 关键问题

1. 为什么 TCP 在拥塞避免阶段采用"加性增"策略？

因为“加性增”策略可以让 TCP 在网络没有出现拥塞时，慢慢地增加发送的数据量，这样可以逐步探测出网络的最大承载能力，避免一下子增加太多导致网络拥塞。这样做既能提高网络利用率，又能减少丢包概率。

2. 当多个 TCP 流共享链路时，如何通过竞争实现长期公平性？

当多个 TCP 流共享链路时，每个流都会根据自己的丢包情况调整发送速率。如果某个流占用太多带宽，它就更容易丢包，窗口就会变小；而占用少的流，窗口会慢慢变大。这样大家都会根据网络状况自动调整，最后每个流都能获得差不多的带宽，实现长期的公平。

3. 新型 TCP 变体（如 BBR）如何解决传统算法的公平性问题？

BBR 这种新型 TCP 变体，会主动测量网络的最大带宽和最小延迟，然后根据这些测量结果来决定自己的发送速率。它不是像传统 TCP 那样，只有在发生丢包或者延迟变大时才减少速率，而是持续调整，尽量让自己既不占用太多带宽，也不浪费带宽。

这样做的好处是：当有多个 BBR 流同时在一个链路上传输时，每个流都会根据实际测量到的可用带宽来分配自己的速率，而不是因为某个流先抢到带宽就一直占着。所以，BBR 能让每个流更公平地分享链路资源，避免传统 TCP 那种“谁先占用谁就有优势”的问题。
