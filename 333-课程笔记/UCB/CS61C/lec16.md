## Building a RISC-V Processor

从上次的最基础的logic circuits向上面移动一层，这样更接近构建我们自己的CPU。我们的核心目标就是设计一套硬件 (Hardware, HW)，能够忠实地执行Reference Card上定义的每一条RISC-V指令。

为了实现这个目标，我们必须理解软件和硬件是如何对话的。第 4 页的“抽象层级图”完美地展示了这一点。

- **顶层**是我们人类编写的**高级语言 (High Level Language)**，比如 C 语言。这里举的例子是一个简单的交换数组元素的 C 代码片段。
- **编译器 (Compiler)** 是第一个翻译官，它将 C 代码翻译成**汇编语言 (Assembly Language)**。汇编语言更接近硬件，但我们人类仍然可以读懂。PPT 中展示了对应的 RISC-V 汇编代码，如 lw (load word) 和 sw (store word)。
- **汇编器 (Assembler)** 是第二个翻译官，它将汇编代码翻译成**机器语言 (Machine Language)**，也就是 CPU 唯一能直接理解的一串串 0 和 1。
- **底层**就是我们即将要设计的**硬件架构 (Hardware Architecture)**。它包含了**逻辑电路 (Logic Circuit)**，这些电路最终由晶体管等物理器件实现。

- **传统视角 (S5, "Old-school")**: 计算机系统被清晰地划分为**软件 (Software)** 和**硬件 (Hardware)**。两者之间的接口被称为**指令集架构 (Instruction Set Architecture, ISA)**。ISA 就像是硬件和软件之间签订的“合同”，它规定了硬件必须能执行哪些操作，软件可以调用哪些指令。我们的课程 **CS61C** 正是聚焦于这个核心接口以及其下的硬件实现，包括**数据通路与控制 (Datapath & Control)** 和**数字设计 (Digital Design)**。
- **现代视角 (S6, "New-school")**: 随着对性能的极致追求，软件和硬件的界限变得模糊，**并行计算 (Parallelism)** 成为了核心思想。无论是云端的“仓库级计算机 (Warehouse Scale Computer)”还是你手中的智能手机，都在利用并行来提升效率。这种并行存在于各个层面：
  - 软件层面：并行请求、并行线程。
  - 指令层面：我们后面会学到的流水线技术，可以同时处理多条指令。
  - 数据层面：同时处理多个数据项。
  - 硬件层面：所有的逻辑门在同一时刻都在并行工作。

一个处理器（CPU）主要包含两个部分：

1. **数据通路 (Datapath)**: 这是 CPU 的“肌肉”和“骨骼”，负责所有的数据处理工作。它内部包含：
   - **算术逻辑单元 (ALU)**: 进行数学和逻辑运算。
   - **寄存器 (Registers)**: 包括存放下一条指令地址的 **PC (Program Counter)** 和存放临时数据的通用寄存器堆。
   - 这部分是数据流动和被操作的地方。
2. **控制单元 (Control)**: 这是 CPU 的“大脑”，负责指挥数据通路如何工作。它会根据从内存中取出的指令，生成一系列控制信号，告诉 ALU 该做什么运算，告诉寄存器该读还是该写，等等。

## CPU Elements and Stages

CPU 电路可以被分为两种基本类型：

1. **组合逻辑模块 (Combinational Logic Blocks)**:
   - 它们是 CPU 的“计算器”，负责处理数据。
   - 特点是**无记忆性**：其输出完全由当前的输入决定。
   - 你可以把它们想象成一个函数 output = f(input)。
   - 它们是**即时响应**的，一旦输入信号稳定下来，经过一小段固有的**传播延迟 (propagation delay)**，输出信号就会稳定在新的值上。
2. **状态元件 (State Elements)**:
   - 它们是 CPU 的“记事本”，负责**存储数据和状态**。
   - 特点是**有记忆性**：它们能保存信息，直到被明确指示更新为止。
   - 它们的工作由一个全局的**时钟信号 (clock)** 来同步。只有在时钟的**上升沿 (rising clock edge)** 这个特定时刻，它们才会根据输入更新自己存储的状态。

### One-Instruction-per-Cycle RISC-V Machine

我们的 CPU 遵循一个 **“一指令一周期” (One-Instruction-Per-Cycle)** 的模型。这意味着，每一个时钟周期，CPU 完整地执行一条指令。这个过程如下：

1. 在一个时钟周期的开始（上升沿之后），所有**状态元件**的输出是稳定的。这些输出作为**组合逻辑模块**的输入。
2. 数据流过组合逻辑模块（比如 ALU、Mux 等），进行各种计算。这需要一定的时间（延迟）。
3. 在下一个时钟上升沿**到来之前**，所有组合逻辑的输出必须稳定下来，并成为状态元件的新的输入。
4. 当时钟的下一个**上升沿**到来时，状态元件“咔嚓”一下，捕获它们面前的输入信号，更新自己的状态。
5. 然后，新一轮的周期开始。

### Combinational Logic Blocks

- **基本构成**: 理论上，任何复杂的逻辑功能都可以由最基础的与门(AND)、或门(OR)、非门(NOT)搭建而成。我们课程中会把一些常用的功能模块化，比如**加法器 (Adder)** 和**多路选择器 (Multiplexer)**。
- **工作方式**: 组合逻辑模块是**永远在线**的。只要通电，它们就在不停地根据输入计算输出，不管这个输出我们当前是否需要。
- **延迟**: 每个逻辑模块都有自己的**延迟**，也就是从输入变化到输出稳定所需的时间。
- **抽象表示**: 为了简化设计，我们会用抽象的方框来表示这些模块。在上一节课我们的adder会具体到每一个bit怎么处理上一个bit的进位，但是这节课开始我们只需要用一个带有加号的小方框就可以

### State Elements

#### Register 寄存器

- 这是最基本的状态元件，可以存储一个 32 位的数据。
- **输入**: 32位数据输入(D) 和一个写使能(Write Enable)控制位。
- **输出**: 32位数据输出(Q)。
- **行为**: 只有在时钟的上升沿，并且写使能为 1 时，输出 Q 才会更新为输入 D 的值。在所有其他时间，Q 都保持不变。**读取寄存器的值是即时的，不消耗时钟周期；但写入需要等待下一个时钟沿。**

#### RegFile 寄存器堆

- 它其实就是**32个寄存器的集合体**，并配有专门的读写管理电路。
- **输入 (S17)**:
  - rs1, rs2: 两个 5 位的地址，用于选择要**读取**哪两个寄存器的数据。
  - rsW: 一个 5 位的地址，用于选择要**写入**哪个寄存器。
  - dataW: 要写入的 32 位数据。
  - RegWEn: 写使能信号。
- **输出 (S17)**: data1 和 data2，分别对应从 rs1 和 rs2 地址读出的数据。
- **时钟行为 (S19)**: 写入操作同样发生在时钟的上升沿。一个重要的概念是 **“写后读”**。在一个周期 N 中计算出的数据，是在周期 N 和周期 N+1 之间的那个时钟上升沿才被真正写入寄存器堆的。

#### Memory 内存

- 内存用于存储大量的指令和数据。
- **输入 (S20)**: 地址 addr，要写入的数据 dataW，以及一个内存读写控制信号 MemRW。
- **输出 (S20)**: 从 addr 读出的数据 dataR。
- **行为 (S22)**: 它的行为和寄存器堆非常相似。读取是组合逻辑行为（有延迟，但不需要时钟触发），写入是同步行为，由时钟触发。
- **IMEM vs DMEM (S23)**: 在我们的设计中，为了避免冲突（比如同时又要取指令又要读数据），我们将内存逻辑上分为两个部分：
  - **IMEM (Instruction Memory)**: 指令内存，只读。
  - **DMEM (Data Memory)**: 数据内存，可读可写。  
     在物理上，它们通常是高速缓存 (Cache) 的不同部分。因为 IMEM 是只读的，所以它不需要写端口、写数据线和时钟触发。

### Stages 指令执行的五个经典阶段

任何一条指令在 CPU 中执行时，逻辑上都会经历的五个阶段。对于我们正在构建的**单周期数据通路**来说，这五个阶段都发生在**一个时钟周期内**。

1. **取指 (Instruction Fetch, IF)**: 将 PC 送入 IMEM，取出指令。
2. **译码 (Instruction Decode, ID)**: 解读指令，读取寄存器堆。
3. **执行 (Execute, EX)**: 使用 ALU 进行计算。
4. **访存 (Memory, MEM)**: 对 DMEM 进行读或写操作（如果需要）。
5. **写回 (Write Back, WB)**: 将结果（来自 ALU 或 DMEM）写回寄存器堆。

### Datapath 设计哲学

> **做所有事，但只采纳需要的结果。**

也就是说，数据通路的每个部分（加法器、ALU等）在每个周期都在工作，计算出各种可能的结果。但我们通过**控制逻辑 (Control Logic)** 和**多路选择器 (MUX)**，来确保只有当前指令所**期望**的那个结果，最终能够影响到状态元件（PC、寄存器堆、DMEM），完成正确的状态更新。

## R-Type: add Datapath

我们先假设目前只有一个add指令需要实现，add指令和DMEM没有关系，暂时用不到，但是需要其他所有元件。下面让我们一步一步分析。

### 取指 IF

一切的开始是 **PC (程序计数器)**。假设程序刚开始，PC 的值为 0。

- PC 寄存器输出它的当前值 0。
- 这个值 0 作为地址，被送入 **IMEM (指令内存)** 的地址端口 addr。
- IMEM 像一个字典，根据地址 0 查找到对应的 32 位机器指令，并通过 dataR (数据读出)端口输出。

我们成功地从内存中取出了 add x5, x6, x7 这条指令的机器码（PPT中显示为 0x007302B3）。

![image.png](https://pub-cc2ebc8a43754210aa734d07c4898ad1.r2.dev/2025/07/20250726165926448.webp)

### 译码 ID

从 IMEM 传来的 32 位指令码。

- 这 32 位指令码被“肢解”，送往不同的地方。
- 指令中的 rs1 字段（bits 19-15，对应 x6 的编号 6）和 rs2 字段（bits 24-20，对应 x7 的编号 7）被送入 **Register File (寄存器堆)** 的两个读地址端口 rs1 和 rs2。
- 指令中的 rd 字段（bits 11-7，对应 x5 的编号 5）被送入寄存器堆的**写地址端口 rsW**。
- 寄存器堆接收到读地址 6 和 7 后，立刻将 x6 和 x7 寄存器中存储的数据输出到 data1 和 data2 端口。这里 PPT 假设 x6 存的是 100，x7 存的是 61。

**结果**: 我们成功地解码了指令，并准备好了两个需要相加的操作数：100 和 61。同时，我们也知道了结果最终要写回哪个寄存器：x5。

![image.png](https://pub-cc2ebc8a43754210aa734d07c4898ad1.r2.dev/2025/07/20250726170115937.webp)

### 执行 EX

从寄存器堆输出的 data1 (100) 和 data2 (61)。

- 这两个数据被送入一个**加法器 (Adder)** 的两个输入端。
- 加法器是组合逻辑，它立刻进行计算 100 + 61。

加法器输出最终的计算结果 161。

![image.png](https://pub-cc2ebc8a43754210aa734d07c4898ad1.r2.dev/2025/07/20250726170323704.webp)

### 写回 WB

现在，我们需要处理指令执行的两个最终结果：更新寄存器堆和更新 PC。

#### 更新寄存器堆

- 加法器输出的结果 161 被连接到寄存器堆的**写数据端口 dataW**。
- 之前在 ID 阶段，我们已经把 rd 的编号 5 送到了写地址端口 rsW。
- 同时，**控制逻辑**会生成一个写使能信号 RegWEn 并设为 1（图中用一个值为 1 的方框表示）。
- 在下一个时钟上升沿到来时，寄存器堆就会把数据 161 写入到 x5 寄存器中。

#### 更新 PC

- 我们需要计算 PC + 4。
- 我们引入一个新的加法器，它的一个输入是当前 PC 的值 0，另一个输入是一个**常数 4**。
- 这个加法器计算出结果 4。
- 这个结果 4 被连接回 PC 寄存器的输入端。
- 在下一个时钟上升沿到来时，PC 寄存器的值就会从 0 更新为 4。

![image.png](https://pub-cc2ebc8a43754210aa734d07c4898ad1.r2.dev/2025/07/20250726170343994.webp)

至此，add 指令的一个完整执行周期就完成了！数据就像水流一样，从 PC 出发，流经 IMEM、寄存器堆、ALU，最终兵分两路，一路带着计算结果返回寄存器堆，另一路带着 PC+4 的值返回 PC，为下一条指令的执行做好了准备。

## R-Type: sub Datapath

在上一节，我们成功为 add 指令搭建了数据通路。现在我们要思考一个问题：如何用最小的代价，让我们的 CPU 也能处理 sub (减法) 指令？

发现 sub 和 add 的 opcode 和 funct3 字段是**完全一样**的！它们唯一的区别在于 funct7 字段。这个细节对于我们设计控制逻辑至关重要。

sub 和 add 的数据通路几乎是相同的，唯一的区别在于“执行 (EX)”阶段的运算。我们当然不希望为此再搭建一套全新的电路。一个更聪明、更高效的办法是：

> **同时执行加法和减法，然后使用一个多路选择器 (MUX) 来选择正确的结果。**

这个思想是计算机体系结构中的一个核心理念：**硬件复用**。

下面将这个想法付诸实践：

1. **扩展执行单元 (S35)**:
   - 我们保留原来的加法器。
   - 在它的旁边，我们再增加一个**减法器**。
   - 将从寄存器堆读出的 data1 和 data2 **同时**送给加法器和减法器。
   - 这样，在每个周期，我们都会同时得到 rs1 + rs2 和 rs1 - rs2 两个结果。

2. **引入 MUX (S35)**:
   - 在加法器和减法器的输出端，我们放置一个 2-to-1 的**多路选择器 (MUX)**。
   - 加法器的输出连接到 MUX 的 0 号输入端。
   - 减法器的输出连接到 MUX 的 1 号输入端。
   - MUX 的输出端连接到寄存器堆的写数据端口 dataW。

3. **增加控制信号 (S35)**:
   - 这个 MUX 由一个新的控制信号来选择。这个信号会来自我们的“大脑”——**控制逻辑 (Control Logic)**。
   - 当控制信号为 0 时，MUX 选择加法结果。
   - 当控制信号为 1 时，MUX 选择减法结果。

![image.png](https://pub-cc2ebc8a43754210aa734d07c4898ad1.r2.dev/2025/07/20250726191614524.webp)

这个 MUX 的选择信号从何而来？控制逻辑是如何知道当前是 add 还是 sub 的？

如前所述，add 和 sub 的唯一区别是 funct7 字段。add 的 funct7 是 0000000，而 sub 是 0100000。它们的第 30 位（inst[30]）是不同的（add 为 0，sub 为 1）。

因此，控制逻辑的设计可以非常简单：**直接将指令的第 30 位连接到这个 MUX 的选择信号端！** 这就是硬件设计的精妙之处——利用指令编码的规律来简化控制电路。

![image.png](https://pub-cc2ebc8a43754210aa734d07c4898ad1.r2.dev/2025/07/20250726191746839.webp)

但 R-Type 指令还有 and, or, sll 等等。为每一种运算都放一个独立的计算单元和一个更大的 MUX 显然不是个好办法。

因此，我们把所有这些算术和逻辑运算功能都集成到一个更强大的模块中，这个模块就是**算术逻辑单元 (Arithmetic Logic Unit, ALU)** (S42)。

- ALU 有两个数据输入端（例如 A 和 B）。
- 它有一个**操作选择 (ALUSel)** 输入端，这是一个多位的控制信号。
- 根据 ALUSel 的不同值，ALU 会对 A 和 B 执行不同的操作（如加、减、与、或等）并输出结果。

我们的数据通路也随之演进 (S39)。原来的加法器、减法器和 MUX 被一个单独的 ALU 模块所取代。控制逻辑现在需要生成的不再是简单的 0 或 1，而是对应不同运算的 ALUSel 信号。

## Datapath with immediates: addi

我们的数据通路已经能够处理R-Type指令，下面我们让它更加灵活，能够处理I-Type指令。

addi 和 add 的核心操作都是“加法”，都由 ALU 来完成。它们的主要区别在于，ALU 的第二个操作数来源不同：

- add：第二个操作数来自寄存器 rs2。
- addi：第二个操作数来自指令中的立即数 imm。

我们可以在 ALU 的第二个输入端前放置一个 MUX，用它来选择数据来源。

![image.png](https://pub-cc2ebc8a43754210aa734d07c4898ad1.r2.dev/2025/07/20250726192640710.webp)

让我们看看具体的改造步骤，从我们已有的 R-Type 数据通路 (S45) 出发：

1. **引入立即数生成器 (ImmGen) (S47)**:
   - 我们需要一个新的组合逻辑模块，叫做 **ImmGen (Immediate Generator)**。
   - 它的输入是 32 位的指令码。
   - 它的任务是从指令码中**提取**出立即数字段（对于 addi，就是 imm[11:0]），并将其**扩展**成一个完整的 32 位数值，以便送入 ALU 进行运算。

2. **符号扩展 (Sign Extension) (S50)**:
   - addi 的立即数是**有符号**的。这意味着一个 12 位的立即数可以表示从 -2048 到 +2047 的范围。
   - 为了将 12 位的有符号数正确地扩展成 32 位，我们需要进行**符号扩展**。规则很简单：**将立即数的最高位（符号位，即 imm[11]）复制填充到新生成的所有高位（从第 12 位到第 31 位）**。
   - 第 50 页的图清晰地展示了这个过程。imm[11:0] 被直接复制到输出的低 12 位，而 imm[11] 的值被“广播”到了输出的高 20 位。这个工作就由 ImmGen 模块来完成。

3. **添加 MUX (BSel) (S46)**:
   - 我们在 ALU 的第二个输入端口前增加一个 2-to-1 MUX。这个 MUX 在 PPT 中被命名为 **BSel** (选择 B 输入源)。
   - 寄存器堆的 data2 输出（即 rs2 的值）连接到 BSel MUX 的一个输入端。
   - ImmGen 模块的输出连接到 BSel MUX 的另一个输入端。
   - BSel MUX 的输出则连接到 ALU 的第二个输入端。

4. **更新控制逻辑**:
   - 控制逻辑现在需要生成一个新的控制信号，我们称之为 BSel 信号，用来控制这个新的 MUX。
   - 如果当前是 add 指令，控制逻辑就输出 BSel = 0（假设 0 代表选择寄存器），让 rs2 的值进入 ALU。
   - 如果当前是 addi 指令，控制逻辑就输出 BSel = 1（假设 1 代表选择立即数），让 ImmGen 的输出进入 ALU。

## Implementing Loads

我们已经有了一个可以处理算术和逻辑运算的数据通路。现在，我们要赋予它与内存交互的能力，这对于任何有用的程序来说都是必不可少的。我们将从 lw (Load Word) 指令开始。

首先，我们必须深刻理解 lw 指令的含义。它是一种 I-Type 指令。

- **语义 (Description)**: `rd = Memory[rs1 + imm]`。这句话包含了两个核心操作：
  1. **地址计算**: 首先，它需要计算出要去内存的哪个位置取数据。这个地址由**基址寄存器 rs1 的值**加上一个**有符号的立即数偏移量 imm** 得到。这个加法操作，我们的 ALU 正好可以胜任！
  2. **内存读取与写回**: 计算出地址后，CPU 需要从该地址对应的**数据内存 (DMEM)** 中读取一个字 (word, 4 bytes) 的数据，然后将这个数据写入到**目标寄存器 rd** 中。
- **对数据通路的新要求**:
  - 我们需要引入 **DMEM (数据内存)** 模块。
  - ALU 的输出（计算出的地址）需要连接到 DMEM 的地址输入端。
  - DMEM 的数据输出端需要有办法连接回寄存器堆的写数据端口。
  - 这意味着，在数据流的路径上，**DMEM 必须位于 ALU 之后，但在写回寄存器堆之前**。

下面具体看例子：`lw x8 24(x2)`

### 取指 IF

PC 指向 lw 指令，IMEM 取出指令码。

### 译码 ID

- 控制逻辑识别出这是一条 lw 指令。
- 指令中的 rs1 字段 (x2) 和 rd 字段 (x8) 被解析出来。
- x2 的编号被送到寄存器堆，其值被读出并送往 ALU 的第一个输入端。（PPT 假设 x2 的值为 0x7FFF FFEO）。
- 指令中的 imm 字段 (24) 被 **ImmGen** 模块提取并进行**符号扩展**，准备送往 ALU 的第二个输入端。

### 执行 EX

- **BSel MUX** 选择 ImmGen 的输出 (24) 作为 ALU 的第二个操作数。
- **ALU** 执行加法运算，计算内存地址：0x7FFF FFEO + 24 = 0x7FFF FFF8。

![image.png](https://pub-cc2ebc8a43754210aa734d07c4898ad1.r2.dev/2025/07/20250726193739196.webp)

### 访存 MEM

- 这是 lw 指令最关键的新增步骤！
- ALU 计算出的地址 0x7FFF FFF8 被送入 **DMEM** 的地址端口 addr。
- 控制逻辑此时会告诉 DMEM 执行**读操作** (MemRW 信号设为 Read)。
- DMEM 接收到地址后，从该位置读取 32 位的数据，并通过 dataR 端口输出。 (PPT 假设读出的数据是 0xDEADBEEF)。

### 写回 WB

现在，我们需要处理指令执行的两个最终结果：更新寄存器堆和更新 PC。

#### 更新寄存器堆

- 现在，我们面临一个新的选择：应该写回寄存器的是 ALU 的计算结果（地址 0x7FFF FFF8）还是从 DMEM 读出的数据 (0xDEADBEEF)？
- 为了解决这个选择问题，我们必须引入一个新的 2-to-1 MUX，它位于数据通路的末端，就在寄存器堆的写数据端口 dataW 之前。我们称之为 **写回 MUX (Write Back MUX)**，由 **WBSel** 信号控制。
- ALU 的结果连接到 WBSel MUX 的一个输入端。
- DMEM 的 dataR 输出连接到 WBSel MUX 的另一个输入端。
- 对于 lw 指令，控制逻辑会设置 WBSel 信号，来**选择来自 DMEM 的数据**。
- 最终，0xDEADBEEF 通过 WBSel MUX，被送往 dataW 端口，准备在下一个时钟沿写入 x8 寄存器。

![image.png](https://pub-cc2ebc8a43754210aa734d07c4898ad1.r2.dev/2025/07/20250726193928436.webp)

### 硬件的限制及其影响

理论上我们的通路已经完整了，但物理世界的硬件总有一些限制，这些限制会反过来影响软件（指令集的设计）和我们的电路设计。

#### 对其访问 Aligned Access

- 为了简化电路，我们设计的 DMEM 规定：访问一个字 (word, 4 bytes) 时，地址**必须是 4 的倍数**。这就是所谓的**对齐访问**。如果你试图用 lw 去访问一个不是 4 的倍数的地址（比如地址 5），硬件就会报错。
- 这个硬件限制被写入了 RISC-V 的“软件合同”(ISA) 中，要求编译器生成的代码必须遵守这个规则。这也是为什么你在 C 语言中学到的 struct 可能会有“内存对齐”和“填充”现象的原因——为了迎合底层硬件的这个要求！

#### 如何处理`lb`和`lh`呢？

- 一个棘手的问题是：如果 DMEM 每次都只能读写 32 位，那 lb 和 lh 这种只读 8 位或 16 位的指令该怎么办？
- 通用处理流程是：
  1. 硬件仍然读取包含目标字节/半字的**整个 32 位字**。
  2. 在 CPU 内部，用额外的逻辑电路（比如 MUX 和移位器）从这个 32 位数据中**提取**出所需的那个字节或半字。
  3. 最后，根据指令是 lb 还是 lbu（无符号加载字节），对提取出的数据进行**符号扩展**或**零扩展**，将其变为 32 位数，再写回寄存器。
- 这部分的具体电路实现比较复杂，在课程中是 Project 3 的内容

## Implementing Stores

我们已经让 CPU 能够从内存中读取数据 (lw)，现在我们要赋予它向内存写入数据的能力。我们将以 sw (Store Word) 指令作为代表。

首先，我们来深入分析 sw 指令。它是一条 **S-Type** 指令。

- **语义 (Description)**: Memory[rs1 + imm] = rs2。这句话的含义是：
  1. **地址计算**: 和 lw 一样，它需要计算出目标内存地址，地址由**基址寄存器 rs1 的值**加上一个**立即数偏移量 imm** 得到。
  2. **数据写入**: 将**源寄存器 rs2** 中的数据，写入到上一步计算出的内存地址中。
- **与 lw 的关键区别**:
  - lw 是**内存 -> 寄存器**的数据流动；而 sw 是**寄存器 -> 内存**的数据流动。
  - sw **不写回**任何寄存器。它的最终目的是改变内存的状态，而不是寄存器堆。
  - sw 的指令格式 (S-Type) 与 lw (I-Type) 不同，立即数被拆分成了两部分。

我们的数据通路 (S62) 已经很接近能够支持 sw 了，只需要一些小的改动。

**1. 处理新的立即数类型 (S63)**

- S-Type 指令的立即数被分成了两段，分别位于指令的不同位置。
- 我们的 **ImmGen (立即数生成器)** 模块需要再次升级。它必须能够识别 S-Type 格式，从指令码中正确地拼接出完整的 12 位立即数，并进行符号扩展。
- 控制逻辑需要向 ImmGen 提供一个新的控制信号，我们称之为 **ImmSel**，用来告诉 ImmGen 当前应该按 I-Type、S-Type 还是其他类型来解析立即数。

![image.png](https://pub-cc2ebc8a43754210aa734d07c4898ad1.r2.dev/2025/07/20250726195056778.webp)

**2. 提供写入内存的数据 (S64)**

- sw 指令需要将 rs2 寄存器的值写入内存。
- 在我们的现有通路中，从寄存器堆读出的 rs2 的值（即 data2 输出）并没有连接到 DMEM。
- 因此，我们必须**添加一条新的连线**：将寄存器堆的 data2 输出端，连接到 **DMEM** 的**写数据输入端 dataW**。

**3. 控制内存的读写 (S64)**

- DMEM 既可以读也可以写，它由 MemRW 这个控制信号决定。
- 对于 lw 指令，控制逻辑需要将 MemRW 设置为**读**。
- 对于 sw 指令，控制逻辑需要将 MemRW 设置为**写**。

**4. 禁用寄存器写回**

- sw 指令不应该改变任何寄存器的值。
- 因此，当执行 sw 指令时，控制逻辑必须将**寄存器堆的写使能信号 RegWEn 设置为 0 (禁用)**。

我们以 sw s0, 24(sp) 为例，追踪这条指令的执行过程。

- **IF & ID**: 取指，译码。rs1 (sp) 和 rs2 (s0) 的值被从寄存器堆读出。
- **ImmGen (S63)**: 控制逻辑发出 ImmSel 信号，告诉 ImmGen 按照 S-Type 解析。ImmGen 输出立即数 24。
- **EX (S64)**: ALU 计算地址 sp + 24，得到目标地址。
- **MEM (S64)**:
  - ALU 输出的地址送往 DMEM 的 addr 端口。
  - 从寄存器堆 data2 端口读出的 s0 的值，顺着我们新增的连线，送往 DMEM 的 dataW 端口。
  - 控制逻辑将 MemRW 信号设置为**写 (Write)**。
- **WB (S69)**:
  - 控制逻辑将 RegWEn 设置为 **0**。这确保了寄存器堆不会被写入任何数据。
  - 由于寄存器堆不写入，WBSel MUX 的选择是什么其实都无所谓，这个信号是一个 "Don't Care" (\*)。
  - 在下一个时钟上升沿，DMEM 会将 s0 的值写入目标地址，而寄存器堆和 PC 保持应有的更新（PC+4）。

![image.png](https://pub-cc2ebc8a43754210aa734d07c4898ad1.r2.dev/2025/07/20250726195113151.webp)

### 硬件的限制：处理 sb 和 sh

和 load 类似，store 也面临着如何处理 sb (store byte) 和 sh (store halfword) 的问题。如果 DMEM 每次只能按 32 位写入，我们该如何只修改其中的 8 位或 16 位呢？

- **通用处理流程**:
  1. 这通常需要一个“读-改-写”的过程，或者使用更复杂的内存接口。
  2. 一种方法是，硬件先**读取**目标地址所在的整个 32 位字。
  3. 然后在 CPU 内部，用新的字节/半字**替换**掉这个 32 位字中的相应部分。
  4. 最后，将修改后的**整个 32 位字**写回到内存中。
- 这部分的具体实现也同样留给了 Project 3。

## Implementing Jumps

我们已经让 CPU 能够进行计算和内存访问。现在，我们要赋予它改变执行流程的能力，这对于实现循环、函数调用等高级程序结构至关重要。我们将以 jal (Jump And Link) 指令作为核心代表。

**目标指令分析：jal rd, label**

jal 是一条 J-Type 指令，它的功能非常独特，需要同时完成两项重要任务：

1. **链接 (Link)**: 将**返回地址**，也就是紧随 jal 指令的下一条指令的地址 (PC + 4)，保存到目标寄存器 rd 中。这为函数调用后的返回提供了“路标”。
2. **跳转 (Jump)**: 将程序计数器 **PC** 更新到一个新的地址，这个新地址由**当前 PC** 的值加上一个从指令中提取的**立即数偏移量 (offset)** 得到 (PC = PC + offset)。

到目前为止，我们的datapath长这样：

![image.png](https://pub-cc2ebc8a43754210aa734d07c4898ad1.r2.dev/2025/07/20250726195721458.webp)

- **数据来源冲突**: 我们需要 ALU 计算 PC + offset，但同时又需要 PC + 4 的值来写入寄存器。
- **ALU 输入扩展**: ALU 的一个输入端需要能够接收来自 PC 的值，而不仅仅是来自寄存器堆的 rs1。
- **PC 更新来源扩展**: PC 的下一个值不再只有 PC + 4 这个选项，还需要有 PC + offset 这个选项。
- **写回来源扩展**: 写入寄存器堆的数据来源，除了 ALU 的结果和内存数据，现在还需要增加 PC + 4 这个来源。

### 改造现有数据通路

我们将从现有的数据通路 (S73) 出发，一步步添加新组件。

**1. 处理 J-Type 立即数 (S74)**

- J-Type 指令的立即数编码方式非常“奇特”，比特位被打乱分布在指令中。
- **ImmGen** 模块必须再次升级！控制逻辑通过 ImmSel 信号告诉它当前是 J-Type，然后 ImmGen 负责从指令码中正确地重组、拼接并符号扩展出 20 位的跳转偏移量。

![image.png](https://pub-cc2ebc8a43754210aa734d07c4898ad1.r2.dev/2025/07/20250726200257352.webp)

**2. 解决 ALU 输入问题 (S75)**

- 为了计算 PC + offset，我们需要把 PC 的值送入 ALU。
- 我们在 ALU 的**第一个输入端**前增加一个 2-to-1 MUX，命名为 **ASel** (选择 A 输入源)。
  - 寄存器堆的 data1 输出 (即 rs1 的值) 连接到 ASel 的一个输入。
  - **PC 的输出**连接到 ASel 的另一个输入。
- 控制逻辑生成 ASel 信号：对于 add, lw, sw 等指令，选择 rs1；对于 jal，则选择 **PC**。

![image.png](https://pub-cc2ebc8a43754210aa734d07c4898ad1.r2.dev/2025/07/20250726200309543.webp)
**3. 解决 PC 更新问题 (S76)**

- PC 的下一个值可能是 PC + 4（顺序执行）或 PC + offset（跳转）。
- 我们引入一个 **PC Mux**，它位于 PC 寄存器的输入端。
  - 计算 PC + 4 的加法器输出连接到 PC Mux 的一个输入。
  - **ALU 的输出** (它刚刚计算了 PC + offset) 连接到 PC Mux 的另一个输入。
- 控制逻辑生成 **PCSel** 信号来控制这个 MUX，决定 PC 的下一个值。

![image.png](https://pub-cc2ebc8a43754210aa734d07c4898ad1.r2.dev/2025/07/20250726200531959.webp)

**4. 解决写回来源问题 (S77)**

- 现在有三种可能的数据需要写回寄存器堆：ALU 的结果、从 DMEM 读出的数据、PC + 4。
- 我们需要将之前的 2-to-1 **WBSel MUX** 升级为一个 **3-to-1 MUX**。
  - ALU 的输出、DMEM 的 dataR 输出保持连接。
  - 新增一条连线，将计算 PC + 4 的那个加法器的输出，连接到 WBSel MUX 的第三个输入端。
- 控制逻辑现在需要生成一个多位的 WBSel 信号来做三选一。对于 jal，它会选择 PC + 4 这个输入。

![image.png](https://pub-cc2ebc8a43754210aa734d07c4898ad1.r2.dev/2025/07/20250726200548096.webp)

**支持 jalr 指令 (S78)**

jalr rd, rs1, imm 指令与 jal 类似，但它的跳转地址是 rs1 + imm。有了我们刚才为 jal 设计的通路，支持 jalr 变得易如反掌！控制逻辑只需要：

- 设置 **ASel**，让 ALU 选择 rs1 的值作为输入。
- 设置 **BSel**，让 ALU 选择立即数作为输入。
- 剩下的流程和 jal 完全一样！
