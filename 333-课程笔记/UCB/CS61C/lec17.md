## Implementing Branches

在lec16结束的时候，我们的datapath已经可以执行算术、逻辑、访存和跳转指令。但它还缺少一个关键能力：**决策能力**。我们的 CPU 还不能根据数据的条件来改变执行流程，而这正是分支指令的核心功能。

我们的新目标：`beq rs1, rs2, label` (Branch if Equal)

- **它的工作**: 如果寄存器 rs1 和 rs2 的值相等，程序就跳转到 label 处；否则，就顺序执行下一条指令 (PC+4)。
- **带来的问题**: 这条指令要求 CPU 同时做两件事：
  1. **比较**：判断 rs1 和 rs2 的值是否相等。
  2. **计算**：计算出如果分支成功，要跳转的目标地址。这个地址是通过 PC + offset 计算得到的。

我们现有的 ALU 只有一个，它已经被用来计算 PC + offset 了。因此，我们**不能再用它来做比较**。这就意味着，我们必须引入一个新的硬件模块来专门负责比较操作。

这个新模块：**The Branch Comparator** (分支比较器)。

- **功能**: 它的唯一使命就是比较输入的两个数值。
- **输入**:
  - 两个 32 位的数据总线 A 和 B，分别连接 rs1 和 rs2 的值。
  - 一个控制位 BrUn，用于决定是进行有符号比较还是无符号比较。对于 beq 来说，是否相等与有无符号无关，但对于 blt (小于则分支) 和 bltu (无符号小于则分支) 就很重要了。
- **输出**:
  - BrEq: 如果 A 等于 B，这个信号就为 1。
  - BrLt: 如果 A 小于 B，这个信号就为 1。
- **关键点**: 这个比较器的输出并**不直接**控制 PC 的走向。它更像一个“侦察兵”，把比较结果（BrEq 和 BrLt）作为情报，发送给我们的总指挥——**控制逻辑 (Control Logic)**。由控制逻辑综合指令类型和比较结果，最终做出决策。

让我们把新的分支比较器放进datapath里面去：

![image.png](https://pub-cc2ebc8a43754210aa734d07c4898ad1.r2.dev/2025/07/20250726204208919.webp)

- **分支成功的情况 (S7)**: 假设我们执行 beq x5, x6, 16，并且 x5 和 x6 的值确实相等。
  1. **ID 阶段**: x5 和 x6 的值从寄存器堆读出后，兵分两路：一路送往 ALU（虽然对于 beq 来说 ALU 的 A 输入端没用），另一路送往**分支比较器**。
  2. **EX 阶段**: 分支比较器发现两个值相等，于是输出 BrEq = 1。这个信号被送到控制逻辑。
  3. **控制逻辑决策**: 控制逻辑接收到 BrEq = 1，并且知道当前指令是 beq，于是它发出 PCSel 信号，指示 PC MUX 选择来自 **ALU 的输出**（ALU 此时已经算好了跳转地址 PC + offset）。
  4. **PC 更新**: 在下一个时钟沿，PC 的值就被更新为跳转目标地址。图中粉红色的高亮线路清晰地展示了这条“分支成功”的数据流。

![image.png](https://pub-cc2ebc8a43754210aa734d07c4898ad1.r2.dev/2025/07/20250726204452056.webp)

- **分支失败的情况 (S8)**: 假设 x5 和 x6 的值不相等。
  1. **ID & EX 阶段**: 流程类似，但这次分支比较器输出 BrEq = 0。
  2. **控制逻辑决策**: 控制逻辑接收到 BrEq = 0，知道分支条件不满足，于是它发出 PCSel 信号，指示 PC MUX 选择 **PC+4** 这条路径。
  3. **PC 更新**: 在下一个时钟沿，PC 的值被更新为 PC+4，程序顺序执行。图中橙色的高亮线路展示了这条“分支失败”的数据流。
  4. **重要细节 (S8 左侧文字)**: beq 指令既不写寄存器，也不写内存。因此，控制逻辑必须同时将 RegWEn 和 MemRW 信号设置为无效（RegWEn=0, MemRW=Read），防止对状态元件造成错误的修改。

## Implementing U-types

第一个 U-Type 指令：lui rd, immu (Load Upper Immediate)。

- **语义 (Description)**: rd = immu << 12。这条指令的作用是，将指令中编码的 20 位立即数 immu，加载到目标寄存器 rd 的**高 20 位** (bits 31-12)，而 rd 的低 12 位 (bits 11-0) 全部置为 0。
- **对状态元件的影响**:
  1. **寄存器堆**: rd 寄存器的值被更新。
  2. **程序计数器 (PC)**: 顺序执行，PC = PC + 4。

另一个 U-Type 指令：auipc rd, immu (Add Upper Immediate to PC)。

- **语义 (Description)**: rd = PC + (immu << 12)。它和 lui 非常相似，也是将 20 位的立即数左移 12 位，但之后不是直接存入 rd，而是要**加上当前 PC 的值**，再存入 rd。
- **对状态元件的影响**: 与 lui 相同，更新 rd 和 PC。

我们的数据通路 (S12) 已经相当复杂了，我们能否在不增加太多新硬件的情况下，实现这两条新指令呢？答案是肯定的，通过巧妙地**复用**现有路径。

### 实现 lui 指令

- **ImmGen**: 我们的立即数生成器 ImmGen 需要再次升级，它要能够识别 U-Type 格式，并正确地生成 immu << 12 的 32 位立即数。
- **ALU 复用**: 如何把这个立即数送入寄存器 rd 呢？我们可以利用 ALU！
  - **控制逻辑**发出 ASel 信号，选择一个**常数 0** (或者选择 x0 寄存器，其值恒为 0) 作为 ALU 的第一个输入。
  - **控制逻辑**发出 BSel 信号，选择来自 ImmGen 的立即数作为 ALU 的第二个输入。
  - **控制逻辑**发出 ALUSel 信号，让 ALU 执行**加法**操作。
  - 这样，ALU 的输出就是 0 + (immu << 12)，正好是我们想要的结果！
- **写回**: ALU 的结果通过 WBSel MUX (选择ALU通路) 被写回到寄存器 rd。

lui x5 0x12345

### 实现 auipc 指令

- 实现 auipc 更加巧妙！我们甚至不需要做任何硬件改动。
- 回想一下，为了实现 jal 指令，我们已经在 ALU 的第一个输入端 (ASel MUX) 添加了 PC 这条通路。
- 现在 auipc 正好需要计算 PC + (immu << 12)。
- **控制逻辑**只需：
  - 发出 ASel 信号，选择 **PC** 作为 ALU 的第一个输入。
  - 发出 BSel 信号，选择来自 ImmGen 的立即数作为 ALU 的第二个输入。
  - 发出 ALUSel 信号，让 ALU 执行**加法**操作。
- ALU 的输出就是我们想要的结果，然后通过 WBSel MUX 写回 rd。

## Implementing ImmGen

在前面的学习中，我们多次提到 ImmGen 这个模块。它就像一个多功能翻译器，能根据不同的指令格式，从 32 位的指令码中提取并转换出正确的立即数。现在，我们就来揭开它神秘的面纱，看看它的内部是如何设计的。

![image.png](https://pub-cc2ebc8a43754210aa734d07c4898ad1.r2.dev/2025/07/20250726210435440.webp)

- 仔细观察和分析不同指令格式中，立即数的各个比特位是如何分布在指令码中的。
- 寻找其中的共性和规律，用更少的逻辑门来巧妙地实现转换。
- 这样的好处是硬件效率比较高

现在，我们逐个分析这些比特位，寻找规律：

- **Imm[0] (S21)**: 这一位非常特殊。对于 I-Type，它来自 inst[20]；对于 S-Type，它来自 inst[7]。但对于 B, U, J-Type，它**永远是 0**！这是因为这些指令的偏移量都要求是 2 字节或 4 字节的倍数，所以最低位总是 0。
- **Imm[4:1] (S22)**: 观察这 4 位，你会发现一个惊人的规律！在所有使用它们的格式中（I, S, B, J），它们总是**作为一个整体**出现。要么是来自 inst[24:21]，要么是来自 inst[11:8]。它们从未被拆散！
- **Imm[10:5] (S23)**: 同样的奇迹再次发生！这 6 位在所有使用它们的格式中（I, S, B, J），都只来自**一个地方**：inst[30:25]。即使四种不同的格式都用到了它们，设计者也把它们放在了指令码的同一个位置。
- **符号位 Imm[31] (S24)**: 这是最优雅的设计之一！对于所有需要符号扩展的立即数（I, S, B, J），它们的**符号位**都巧妙地被放在了指令码的**最高位 inst[31]**。这意味着，无论是什么格式，我们的 ImmGen 电路进行符号扩展时，只需要**无脑地把 inst[31] 复制到 Imm 的所有高位**即可！
- **高位 Imm[30:21] 和 Imm[19:12] (S25)**: 这些位只在 U-Type 和 J-Type 中出现。规律是：如果格式中定义了这些位，就从指令码中取；如果没定义，它们的值就等于符号位（也就是 inst[31]）。
- **最“混乱”的位 Imm[20] 和 Imm[11] (S26)**: 只有这两位看起来像是被“随机”塞在了指令码的空隙里。Imm[20] 需要一个 3-way MUX 来选择，Imm[11] 需要一个 4-way MUX。

这种优化的效果：

- 如果用“简单粗暴法”，为 6 种格式（包括 R-Type 输出0）做一个 32 位的 MUX，大约需要 640 个逻辑门。
- 而利用我们发现的规律，为每一组有共同规律的比特位单独设计 MUX，总共只需要大约 **160 个逻辑门**！

## Datapath and Control

在这一部分，我们将正式聚焦于 CPU 的“大脑”——控制逻辑。我们会看到，一旦数据通路（“身体”）搭建完成，CPU 的所有行为都可以通过生成正确的控制信号来精确指挥。

回顾了指令执行的五个逻辑阶段，并将它们与数据通路上的主要硬件单元对应起来：

1. **IF (Instruction Fetch)**: 核心是 **IMEM** 和 **PC**。
2. **ID (Instruction Decode)**: 核心是**寄存器堆 (`Reg[]`)**。
3. **EX (Execute)**: 核心是 **ALU**。
4. **MEM (Memory Access)**: 核心是 **DMEM**。
5. **WB (Write Back)**: 数据写回到**寄存器堆 (`Reg[]`)**。

我们来具体看看如何将这张真值表变成实际的电路。

### Control Logic Design: ROM

通过只读存储器来实现控制逻辑

- **原理 (S38)**: 这种方法非常直观。我们把整个真值表预先计算好，烧录到一个 **ROM (Read-Only Memory)** 里面。
  - **地址输入**: 使用指令码中能够区分不同指令的关键比特位（如 opcode 和 funct3/7 的部分位）作为 ROM 的地址。
  - **数据输出**: ROM 在这个地址中存储的内容，就是对应那条指令所需的一整套控制信号，我们称之为**控制字 (control word)**。
  - 当一条指令到来时，控制逻辑就用它的关键位去 ROM 里“查表”，瞬间得到所有需要的控制信号。
- **RV32I 的情况 (S42)**: 对于 RV32I 指令集，经过分析可以发现，只需要 **9 个比特位** (inst[30], inst[14:12], inst[6:2]) 就足以区分所有需要不同控制信号的指令。这 9 位被称为 **"9-bit ISA"** 的精华。因此，我们的 ROM 只需要 2^9 = 512 个条目。
- **ROM 控制的局限性 (S43)**: **第 43 页** 指出了一个 ROM 控制的重大问题。控制信号 PCSel 的决策，在执行分支指令时，依赖于**分支比较器**的输出 (BrEq, BrLt)。但分支比较器的输出是数据通路在 **EX 阶段**才产生的结果！而控制逻辑在 **ID 阶段**就需要根据指令码生成信号。这种“时空错位”导致我们无法将 PCSel 的逻辑完全固化在 ROM 里。
  - **解决方案**: 将控制逻辑分为两部分。**Control Logic Part 1** 由 ROM 实现，生成所有仅依赖于指令码的信号。**Control Logic Part 2** 是一个额外的组合逻辑电路，它接收来自 Part 1 的信号和分支比较器的结果，共同决定最终的 PCSel。
- **ROM 的底层实现 (S44)**: ROM 本身在底层也是由逻辑门（一个大的解码器和一堆与门或门阵列）实现的，它本质上是以一种规整的、易于编程的方式实现了“积之和 (Sum of Products)”的布尔逻辑。

### Control Logic Design: Combinational Logic

通过组合逻辑电路来实现控制逻辑

- **原理 (S46)**: 与 ROM 的“大一统”查表法不同，这种方法为**每一个控制信号**（如 RegWEn 一个，ASel 一个）都**单独设计一个**组合逻辑电路。
- **设计过程 (S50)**:
  1. 从控制逻辑真值表 (S35) 中，单独拿出目标信号的那一列。
  2. 以指令的关键位（那 9 位）为输入，构建该信号的真值表。
  3. 利用卡诺图或计算机辅助的逻辑综合工具，对真值表进行化简，得到最简的布尔表达式。
  4. 用与门、或门、非门搭建出这个表达式对应的电路。
- **优点 (S46)**: 相比 ROM，这种方法可以利用逻辑化简和“无关项”，最终得到的电路**速度更快、尺寸更小、功耗更低**（PPT 中提到可能只需要 25 个门，而 ROM 需要 1000+）。这是现代高性能处理器的首选。
- **实践：为 BrUn 写布尔表达式 (S47-S49)**: PPT 用 BrUn 信号（决定有符号还是无符号比较）作为例子。通过观察 S48 的分支指令表，我们发现 bltu 和 bgeu 这两条无符号分支指令的 funct3 字段的中间一位 (inst[13]) 是 1，而其他有符号分支是 0。更重要的是，对于所有非分支指令，BrUn 信号都是无关项 \* (S49)。这意味着我们根本不需要去检查 opcode 来判断是不是分支指令！BrUn 的逻辑可以被惊人地简化为：**BrUn = inst[13]** (仅当指令是B-type时)。

## Instruction Timing 指令时序

核心问题：对于我们设计的 CPU，完成一条指令所需的最长延迟时间是多少？这个最长延迟路径，我们称之为**关键路径 (Critical Path)**，它直接决定了我们的 CPU 时钟频率的上限。

时钟周期 T 必须大于等于关键路径的延迟。时钟频率 f = 1/T。因此，**关键路径越短，时钟频率就能越高，CPU 性能就越好**。

这里的延迟时间由两部分组成：

- **组合逻辑延迟**: 如 tALU (ALU 延迟), tIMEM (访存延迟), tmux (MUX 延迟)。
- **状态元件时序参数**: 如 tclk_q (时钟到 Q 端的输出延迟) 和 tSetup (建立时间)。

### **add 指令的关键路径 (S53)**:

1. 时钟触发 PC，PC 值输出 (tclk_q)。
2. PC 值进入 IMEM，取出指令 (tIMEM)。
3. 指令进入寄存器堆，读出 rs1, rs2 的值 (tReg)。
4. rs2 的值经过 BSel MUX (tmux)。
5. 两个操作数进入 ALU，计算结果 (tALU)。
6. ALU 结果经过 WBSel MUX (tmux)。
7. 最终结果在下一个时钟沿到来前，必须在寄存器堆的输入端稳定下来 (tSetup)。

![image.png](https://pub-cc2ebc8a43754210aa734d07c4898ad1.r2.dev/2025/07/20250726213159099.webp)

- **总延迟**: tclk_q + tIMEM + tReg + tmux + tALU + tmux + tSetup

### **lw 指令的关键路径 (S54)**:

1. 时钟触发 PC，PC 值输出 (tclk_q)。
2. PC 值进入 IMEM，取出指令 (tIMEM)。
3. 指令进入寄存器堆读 rs1 (tReg)，**同时** ImmGen 计算立即数 (tImm)。这两者是**并行**的，所以我们取其中较慢的一个，即 max{tReg, tImm}。
4. rs1 的值和立即数分别进入 ALU，计算地址 (tALU)。
5. 地址进入 DMEM，读取数据 (tDMEM)。
6. DMEM 读出的数据经过 WBSel MUX (tmux)。
7. 最终结果在下一个时钟沿到来前，必须在寄存器堆的输入端稳定下来 (tSetup)。

![image.png](https://pub-cc2ebc8a43754210aa734d07c4898ad1.r2.dev/2025/07/20250726213239215.webp)

- **总延迟**: tclk_q + tIMEM + max{tReg, tImm} + tALU + tDMEM + tmux + tSetup

### 更高层次的视角分析时序

将指令执行的五个阶段与主要的硬件单元延迟关联起来：

- **IF (IMEM)**: 200 ps
- **ID (Reg read)**: 100 ps
- **EX (ALU)**: 200 ps
- **MEM (DMEM)**: 200 ps
- **WB (Reg write)**: 100 ps

那么不同指令的总延迟：

- add (IF+ID+EX+WB): 200+100+200+100 = 600 ps
- beq (IF+ID+EX): 200+100+200 = 500 ps
- sw (IF+ID+EX+MEM): 200+100+200+200 = 700 ps
- lw (IF+ID+EX+MEM+WB): 200+100+200+200+100 = 800 ps

#### **结论**:

- **时钟周期由最慢的指令决定**。在这个例子中，lw 是最慢的，耗时 800 ps。所以，我们的时钟周期必须至少是 800 ps。
- **最高时钟频率**: f_max = 1 / 800 ps = 1.25 GHz。
- **巨大的性能浪费**: 这意味着，当 CPU 在执行一条只需要 500 ps 的 beq 指令时，它仍然要占用一个完整的 800 ps 的时钟周期。其中有 300 ps 的时间，CPU 和数据通路都在“闲置”，白白地等待时钟结束。

## Summary

- 我们成功地搭建了一个可以**在一个周期内执行完一条 RISC-V 指令**的处理器 (S60)。
- 我们理解了指令执行的 5 个逻辑阶段 (IF, ID, EX, MEM, WB)。
- 我们为这个处理器设计了“大脑”——控制器 (Controller)，它可以通过 ROM 或组合逻辑实现。
- 我们发现了单周期设计的**致命弱点**：**性能受限于最慢的指令**，导致硬件单元在大部分时间里都是空闲的，造成了巨大的资源浪费。

这个弱点，正是我们下一章要学习**流水线 (Pipelining)** 技术的根本动力。流水线技术将彻底改变“一次只做一件事”的模式，通过让不同指令的不同阶段重叠执行，来极大地提升 CPU 的**吞吐率 (Throughput)**。
