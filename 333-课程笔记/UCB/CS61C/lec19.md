## Pipelined RISC-V Datapath

先回顾一下我们熟悉的、完整的单周期数据通路图。这张图是我们进行流水线改造的“蓝图”。在单周期模型里，数据在一个周期内从左到右贯穿整个电路。

![image.png](https://pub-cc2ebc8a43754210aa734d07c4898ad1.r2.dev/2025/07/20250726235543549.webp)

以及五个阶段：

- **IF (Instruction Fetch)**: 取指阶段
- **ID (Instruction Decode)**: 译码与读寄存器阶段
- **EX (Execute)**: 执行阶段
- **MEM (Memory Access)**: 访存阶段
- **WB (Write Back)**: 写回阶段

**流水线寄存器 (Pipeline Registers)**:

- 这五个阶段之间，被四组巨大的**流水线寄存器**隔开了。它们分别是 **IF/ID**, **ID/EX**, **EX/MEM**, **MEM/WB** 寄存器。
- **作用**: 它们就像是流水线上的“托盘”。每个时钟周期结束时（上升沿），前一阶段的所有计算结果和必要的控制信号，都会被“锁存”到这组寄存器中，然后作为下一阶段在新周期里的稳定输入。
- **核心功能**: 它们**隔离**了各个阶段，使得五个阶段可以**并行**处理五条**不同**的指令，而不会相互干扰。

![image.png](https://pub-cc2ebc8a43754210aa734d07c4898ad1.r2.dev/2025/07/20250727000004517.webp)

下面我们来逐个分析流水线寄存器：

### IF/ID reg

![image.png](https://pub-cc2ebc8a43754210aa734d07c4898ad1.r2.dev/2025/07/20250727000144532.webp)

1. 从 IMEM 中取出的**完整指令码**。
2. PC + 4 的值。这个值有两个潜在用途：作为分支/跳转失败时的下一条 PC 地址，或者作为 jal 指令需要写回 rd 的返回地址。

### ID/EX reg

![image.png](https://pub-cc2ebc8a43754210aa734d07c4898ad1.r2.dev/2025/07/20250727000351878.webp)

1. 从寄存器堆读出的**数据 rs1 和 rs2**。
2. 经过 ImmGen 处理后的**立即数**。
3. PC + 4 的值（继续向后传递）。
4. 需要写入的目标寄存器编号 rd。
5. **来自控制逻辑的、将在 EX, MEM, WB 阶段使用的所有控制信号！** (这一点非常重要，我们后续会讨论)。

### EX/MEM reg

![image.png](https://pub-cc2ebc8a43754210aa734d07c4898ad1.r2.dev/2025/07/20250727000505593.webp)

1. **ALU 的计算结果**。
2. 对于 sw 指令，需要写入内存的**rs2 的数据**也要被传递过来。
3. 目标寄存器编号 rd (继续传递)。
4. **将在 MEM 和 WB 阶段使用的控制信号** (如 MemRW, RegWEn 等)。

### MEM/WB reg

![image.png](https://pub-cc2ebc8a43754210aa734d07c4898ad1.r2.dev/2025/07/20250727000721670.webp)

1. **ALU 的计算结果** (继续传递，用于 R-Type 指令的写回)。
2. 对于 lw 指令，从 **DMEM 中读出的数据**。
3. 目标寄存器编号 rd (最终传递到这里)。
4. **将在 WB 阶段使用的控制信号** (如 RegWEn, WBSel)。

### 控制信号的流水化

![image.png](https://pub-cc2ebc8a43754210aa734d07c4898ad1.r2.dev/2025/07/20250727000659529.webp)

一个关键细节：**控制信号也必须和数据一起在流水线中传递！**

- 那些在 EX 阶段就需要用的信号 (如 ALUSel, ASel, BSel)，会被存入 ID/EX 寄存器。
- 那些在 MEM 阶段才需要的信号 (如 MemRW)，会从 ID/EX 寄存器原封不动地传递到 EX/MEM 寄存器。
- 那些在 WB 阶段才需要的信号 (如 WBSel, RegWEn)，会一路从 ID/EX -> EX/MEM -> MEM/WB 寄存器传递下去。

### RISC-V ISA 对流水线的友好设计

1. **所有指令定长 32 位**: 使得 IF 和 ID 阶段非常规整和快速。
2. **规整的指令格式**: rs1, rs2 等字段位置相对固定，使得 ID 阶段可以在不知道具体指令的z情况下，就先去读取寄存器，节省时间。
3. **Load/Store 寻址方式简单**: 基址+偏移量 的模式，可以很自然地放在 EX 阶段由 ALU 完成。
4. **内存对齐**: 强制内存对齐访问，使得 MEM 阶段可以简化为单周期完成。

## Hazards Introduction

首先，我们来看一个不会出任何问题的“完美”代码序列，来感受一下流水线是如何工作的。

```text
addi t0, x0, 50
addi t1, x0, 100
addi t2, x0, 150
```

- 这三条指令之间**没有任何数据依赖关系**，t0, t1, t2 都是独立的。
- **初始状态**: PC 和所有寄存器都为 0。流水线初始时充满了 nop (空操作) 指令。

### 逐周期追踪

- **Cycle 0 (S17)**: 第一条 addi 指令进入 **IF** 阶段。
- **Cycle 1 (S18)**: 第一条 addi 进入 **ID** 阶段；同时第二条 addi 进入 **IF** 阶段。
- **Cycle 2 (S19)**:
  - 第一条 addi 进入 **EX** 阶段，ALU 计算 0 + 50。
  - 第二条 addi 进入 **ID** 阶段。
  - 第三条 addi 进入 **IF** 阶段。
- **Cycle 3 (S20)**:
  - 第一条 addi 进入 **MEM** 阶段（虽然它不做任何事）。ALU 的结果 50 被锁存在 EX/MEM 寄存器中。
  - 第二条 addi 进入 **EX** 阶段，ALU 计算 0 + 100。
  - 第三条 addi 进入 **ID** 阶段。
- **Cycle 4 (S21)**: 这是关键的一刻！
  - 第一条 addi 进入 **WB** 阶段，ALU 结果 50 被准备写入寄存器 t0。
  - 第二条 addi 进入 **MEM** 阶段。
  - 第三条 addi 进入 **EX** 阶段。
  - **在 Cycle 4 结束的时钟上升沿，t0 的值才会被真正更新为 50！**
- **Cycle 5 (S22)**:
  - 第二条 addi 进入 **WB** 阶段，t1 准备被更新为 100。
  - 在时钟上升沿，t0 的值**已经**是 50 了。
- **Cycle 6 (S23)**: t1 的值变为 100。第三条 addi 进入 WB 阶段。
- **Cycle 7 (S24)**: t2 的值变为 150。所有指令执行完毕。

### Three types of Pipeline Hazards

1. **结构冒险 (Structural Hazard)**:
   - **原因**: 硬件资源不足。两条不同的指令在**同一个时钟周期**，试图**使用同一个硬件单元**。
   - **例子**: 假设我们的内存是统一的（IMEM 和 DMEM 是同一个物理部件）。那么当一条指令在 IF 阶段需要访问内存取指时，另一条四周期前的 lw 指令可能正好在 MEM 阶段需要访问内存读数据，冲突就发生了。
2. **数据冒险 (Data Hazard)**:
   - **原因**: 指令之间存在**数据依赖**。后一条指令需要用到前一条指令尚未计算完成的结果。
   - **例子**:
     ```
     add t0, t1, t2
     sub t3, t0, t4  // sub 需要用到 add 刚刚计算出的 t0
     ```
     在流水线中，当 sub 指令在 ID 阶段需要读取 t0 时，add 指令可能还在 EX 或 MEM 阶段，t0 的新值还没有被写回到寄存器堆里。sub 就会读到一个旧的、错误的值。
3. **控制冒险 (Control Hazard)**:
   - **原因**: 执行流程的依赖。分支或跳转指令的结果尚未确定，但流水线已经取入了后续的指令。
   - **例子**: beq t0, t1, L1  
      流水线不知道分支是否会成功，它会默认去取 PC+4 位置的指令。但如果分支最终是成功的，那么已经取进来的 PC+4 指令就是错误的，必须被丢弃。

### nop

一种通用但低效的解决方案——**停顿 (Stalling)**，也叫插入**气泡 (bubble)** 或 nop- **原理**:

- 当检测到冒险可能发生时，让后续的指令在流水线中“暂停”一个或多个周期，原地等待，直到冒险的条件消失（例如，等前一条指令的数据写回寄存器）。
- **实现**: 通过在流水线中插入 nop (空操作) 指令来实现。
- **缺点**: 停顿会牺牲性能。如果每次数据依赖都停顿，我们的流水线性能就会急剧下降，甚至退化回单周期处理器的水平。

## Structural Hazards

结构冒险是三种冒险中最“纯粹”的一种，因为它完全是由硬件资源的设计所决定的。

假设我们的流水线存在两个潜在的硬件缺陷：

1. **寄存器堆**不支持在同一个周期内同时进行读和写操作。
2. **内存**是统一的，即指令内存 (IMEM) 和数据内存 (DMEM) 使用的是同一个物理端口。

```
addi t0, x0, 50 // inst 1
sw t2, 16(x0) // inst 2
nop
addi t0, x0, 11 // inst 4
nop
```

- **Cycle 4 时刻的冲突 (S34-S35)**:
  - 此时，第一条 `addi` 指令 (`inst 1`) 已经走到了流水线的末端——**WB (写回) 阶段**。它需要**写入**寄存器堆，更新 `t0` 的值。
  - 同时，第四条 `addi` 指令 (`inst 4`) 刚刚进入流水线，处于 **ID (译码) 阶段**。它需要**读取**寄存器 `x0` 的值。
  - **冲突发生 (S35)**: `inst 1` 和 `inst 4` 在同一个时钟周期 4，都试图访问**寄存器堆**。如果我们的寄存器堆只有一个读写端口，无法同时满足一个读请求和一个写请求，那么**结构冒险**就发生了。

- **另一个潜在的冲突 (S36)**:
  - 假设我们有一条 `lw` 指令，当它处于 **MEM (访存) 阶段**需要读**数据内存**时，另一条新指令正好处于 **IF (取指) 阶段**需要读**指令内存**。
  - 如果 IMEM 和 DMEM 是同一个物理部件，那么这两条指令就会争抢唯一的内存端口，同样会产生结构冒险。

### RISC-V 如何避免结构冒险

RISC-V 的设计者们早已预见到了这些问题，并在其 ISA (指令集架构) 规范中提出了明确的硬件要求，从根本上杜绝了这些常见的结构冒险。

**1. 避免寄存器堆的结构冒险 (S38)**

- **问题**: 如果寄存器堆不支持同时读写，就会发生结构冒险。
- **RISC-V 解决方案**: 硬件设计**必须**支持同时的读和写操作。
  - **实现方式**: 寄存器堆内部通常设计为**独立的读端口和写端口**。具体来说，它有两个读端口（`rs1`, `rs2`）和一个写端口（`rsW`）。
  - **巧妙的时序设计**: 写入操作发生在时钟周期的**前半段**（例如下降沿），而读取操作发生在时钟周期的**后半段**。这样，即使是同一条指令在同一个周期对同一个寄存器先写后读（虽然不常见），也能保证读到的是新写入的值。这种设计被称为**“写后读 (write-then-read)”**或**“旁路 (bypassing)”**逻辑。
  - 因此，寄存器堆在一个周期内支持**三次访问**（两次读，一次写），完美解决了冲突。

**2. 避免内存的结构冒险 (S39)**

- **问题**: 如果指令内存和数据内存是同一个硬件，IF 阶段的取指和 MEM 阶段的访存就会冲突。
- **RISC-V 解决方案**: 硬件设计**必须**将指令内存和数据内存**分离**。
  - **实现方式**: 在现代处理器中，这通常通过设置两个独立的、高速的 **一级缓存 (Level 1 Cache)** 来实现：一个 **L1 指令缓存 (I-Cache)** 和一个 **L1 数据缓存 (D-Cache)**。
  - **第 40 页** 的图清晰地展示了这种**哈佛架构 (Harvard Architecture)** 的思想（指令和数据有独立的存储和通路），与之对应的是指令和数据混合存储的**普林斯顿架构 (Princeton Architecture)**。
  - 将 I-Cache 和 D-Cache 分离，使得 CPU 的 IF 单元和 MEM 单元可以在每个周期都**并行地、无冲突地**访问内存（缓存）。

## Data Hazards

我们将先理解**什么是数据冒险**，然后学习解决它的两种技术——**转发 (Forwarding)** 和处理特殊情况的**加载冒险 (Loads)**。

### What are data hazards

我们来看一段非常简单的代码：

```text
addi t0, x0, 50   // 指令1: t0 = 0 + 50
addi t1, t0, 100  // 指令2: t1 = t0 + 100
```

这两条指令存在明确的**数据依赖**：指令 2 需要使用指令 1 的计算结果 t0。

- **Cycle 2 (S45)**:
  - 指令 1 (addi t0...) 处于 **EX** 阶段，正在计算 0 + 50。
  - 指令 2 (addi t1...) 处于 **ID** 阶段，它需要去**读取**寄存器 t0 的值作为自己的操作数。
- **冲突发生**: 在这一刻，指令 1 的结果 50 还存在于 ALU 的输出端，**尚未被写回 (Write Back)** 到寄存器堆的 t0 中。寄存器堆里的 t0 仍然是它的旧值（比如 0）。因此，指令 2 读取到了一个**错误的、过时的数据**！
- **根本原因**: 寄存器的**写操作**发生在流水线的第 5 阶段 (WB)，而**读操作**却发生在第 2 阶段 (ID)。这种“先读后写”的时序错乱，导致了数据冒险。

如何解决？

#### 笨办法：停顿 (Stalling)

如果我们什么都不做，就只能依靠停顿。

- **需要停顿多少周期？(S45)** t0 的新值要到 Cycle 4 的**末尾**才会被写入寄存器堆。而指令 2 在 Cycle 2 就需要它。
- **1 个停顿 (S46)**: 在 Cycle 3，我们让指令 2 停在 ID 阶段，让指令 1 继续前进到 MEM 阶段。此时，t0 的新值 50 位于 EX/MEM 流水线寄存器中，但**仍然没有被写入**寄存器堆。指令 2 去读，读到的还是旧值。所以 1 个停顿不够。
- **2 个停顿 (S47)**: 在 Cycle 4，我们让指令 2 再次停顿。此时，指令 1 走到了 WB 阶段。现在问题来了：
  - **如果**寄存器堆的设计是“写优先”，即在一个周期内，写操作发生在前半周期，读操作发生在后半周期 (write-then-read)。那么在 Cycle 4，指令 1 将 50 写入，指令 2 就能读到新值。只需要 **2 个停顿**。
  - **如果**寄存器堆是“读优先”，那指令 2 还是会读到旧值，就需要 **3 个停顿**，等到 Cycle 5 开始时才能读到新值。

#### 优化：写后读 Write-then-Read

为了减少停顿，RISC-V 硬件规范要求寄存器堆必须实现 **“写后读”** 。这能为我们节省一个停顿周期，但对于 add-use（加法结果立刻被使用）这样的场景，仍然需要 **2 个周期的停顿**。这会严重影响性能！

### Forwarding

在 Cycle 2 的末尾，指令 1 的结果 50 其实**已经**在 ALU 的输出端计算出来了。这个正确的值是存在的，只是不在它“应该”在的地方（寄存器堆）。

我们能不能搭建一条“近路”或“旁路”，直接将 ALU 的计算结果，从 **EX 阶段的输出端**，“转发”回 **EX 阶段的输入端**，供下一条指令使用？

这个技术就叫做**转发 (Forwarding)** 或**旁路 (Bypassing)**。

#### 实现转发

1. **增加硬件**:
   - 添加从 **EX/MEM 流水线寄存器**（存放上一条指令的 ALU 结果）到 ALU 输入端的**数据通路**。
   - 添加从 **MEM/WB 流水线寄存器**（存放上上条指令的 ALU 结果或内存数据）到 ALU 输入端的**数据通路**。
   - 在 ALU 的每个输入端前，增加一个**转发 MUX**，用于在“从寄存器堆读取的值”和“从后续阶段转发回来的值”之间进行选择。

2. **增加控制逻辑 (Forwarding Unit)**:
   - 需要一个专门的“转发单元”来控制这些新的 MUX。
   - 它会比较当前在 ID/EX 寄存器中的 rs1, rs2 编号，和在 EX/MEM、MEM/WB 寄存器中的 rd 编号。
   - 如果发现匹配（例如 ID/EX.rs1 == EX/MEM.rd），并且 EX/MEM 寄存器中的指令需要写回，它就会设置转发 MUX，选择来自 EX/MEM 的数据，而不是来自寄存器堆的数据。

### Loads

上面实现的转发技术能解决大部分数据冒险，但有一个经典的例外。

```text
lw  t0, 0(sp)  // 指令1: 从内存加载数据到 t0
addi t1, t0, 100 // 指令2: 立刻使用 t0
```

- **Cycle 2**: 指令 1 在 EX 阶段计算地址，指令 2 在 ID 阶段准备读取 t0。
- **Cycle 3**:
  - 指令 1 进入 **MEM** 阶段，**此时才开始真正从 DMEM 中读取数据**。
  - 指令 2 进入 **EX** 阶段，它**此刻**就需要 t0 的值作为 ALU 的输入。
- **冲突发生 (S63)**: t0 的新值在 Cycle 3 的**末尾**才能从 DMEM 中拿到。而指令 2 在 Cycle 3 的**开头**就需要它。数据根本来不及从 MEM 阶段“穿越”回 EX 阶段。

#### load-use解决方案：停顿一周期 + 转发

- 这是唯一无法完全通过转发解决的数据冒险。
- 硬件必须这么做：
  1. 当“转发单元”检测到这种“加载-使用”冒险时（即 EX 阶段的指令源寄存器，匹配了 MEM 阶段的 lw 指令的目标寄存器）。
  2. 它必须强制让流水线**停顿 (stall) 一个周期**。
  3. 在停顿后的下一个周期，lw 的数据已经到达了 MEM/WB 寄存器，此时就可以**转发**给处于 EX 阶段的 addi 指令了。

这个在 lw 指令之后必须空出来的一个周期的位置，被称为**加载延迟槽 (Load Delay Slot)**。

#### Code scheduling 代码调度

从软件层面进行优化？

- **编译器**可以进行**代码调度 (Code Scheduling)**。
- **原理 (S66)**: 编译器会尝试找到一条与 lw 和 addi **不相关的**指令，把它从代码的其他地方移动到这个“加载延迟槽”中。
- **效果**:
  - **naïve 编译 (S65)** : lw -> add -> **stall**。完成任务需要多个周期。
  - **优化编译 (S66)**: lw -> (不相关指令) -> add。那个 stall 周期被用来执行有用的工作，停顿被完美地隐藏了，性能得到了提升！

## Control Hazards

控制冒险源于分支 (branch) 和跳转 (jump) 指令的特性，它们会改变程序正常的顺序执行流程，这对提前取指的流水线来说是个巨大的挑战。

我们先来看示例代码：

```text
jal x0, 8      // 指令1: 跳转到地址 8
addi t0, x0, 50  // 指令2: 位于地址 4
addi t1, x0, 50  // 指令3: 位于地址 8
```

jal 指令的意图是跳过指令 2，直接去执行指令 3。

- **Cycle 0 (S69)**: jal 指令进入 **IF** 阶段被取出。
- **Cycle 1 (S70)**:
  - jal 指令进入 **ID** 阶段。
  - **问题出现**: 流水线的 IF 阶段并不知道 jal 是一条跳转指令，它的唯一任务就是根据当前的 PC (PC=4) 去取下一条指令。于是，它**错误地**将指令 2 (addi t0...) 取入了流水线。
- **Cycle 2 (S72)**:
  - jal 指令进入 **EX** 阶段，此时 ALU 正在计算跳转的目标地址 (PC+offset，即 0+8=8)。
  - 错误的指令 2 进入 **ID** 阶段。
  - IF 阶段继续根据 PC=8，取入了指令 3。
  - **决策点**: 在 **ID 阶段的末尾**，控制逻辑终于“意识”到 jal 是一条无条件跳转指令。但为时已晚，错误的指令 2 已经污染了 ID 阶段。

### 解决方案：Flush（重刷流水线）与Stall（停顿）

**1. ID 阶段的修复：冲刷 (Flush) (S73)**

- 一旦控制逻辑在 ID 阶段识别出跳转/分支指令，它必须采取行动，**废除 (nullify)** 掉那个被错误取入的指令。
- **实现**: 控制逻辑强制将 IF/ID 寄存器中的指令码替换为一个 nop (空操作) 指令。这个操作被称为**冲刷 (flushing)** 或**注入气泡 (injecting a bubble)**。

**2. IF 阶段的修复：更新 PC (S74-S76)**

- 仅仅冲刷掉错误的指令还不够，我们还需要告诉 IF 阶段，接下来应该去**正确的地址**取指令。
- **问题**: 跳转的目标地址是在 **EX** 阶段才由 ALU 计算出来的。
- 这意味着，在 ID 阶段发现需要跳转后，流水线必须**停顿 (stall)**，等待 jal 指令在 EX 阶段算出新地址。
- **过程**:
  - **Cycle 2**: jal 在 EX，ID 阶段的错误指令被 flush 为 nop。IF 阶段暂停取指。
  - **Cycle 3 (S75)**: jal 进入 MEM 阶段，其计算出的目标地址 8 位于 EX/MEM 寄存器中。现在，这个新地址可以被**转发 (forward)** 回 PC。
  - **Cycle 4 (S76)**: IF 阶段终于可以使用正确的地址 8，去取指令 3。

#### 性能代价

- 对于 jal 和 jalr，跳转地址在 EX 阶段末尾才知道，这意味着我们需要**停顿 2 个周期** (jal 在 ID 发现，EX 计算，MEM 转发回 PC)。
- 对于分支指令 (如 beq)，情况更糟。我们不仅需要 EX 阶段的 ALU 计算 PC+offset，还需要**分支比较器**的结果。为了简化，设计者通常将分支决策放在 EX 或 MEM 阶段。
- **结论**: 在我们这个简单的五级流水线中，每一次控制流的改变（成功的跳转或分支），都会导致 **1-3 个周期的停顿惩罚 (stall penalty)**。这是一个巨大的性能损失！

### 优化：分支预测 Branch Prediction

**1. 解决控制冒险的思路 (S80)**

- **思路一：提早计算**: 能不能在 ID 阶段就算出跳转地址？可以！通过增加一个专门的加法器。这可以减少停顿周期。
- **思路二：分支预测**: **猜测**分支会不会跳转。
  - 如果猜对了，流水线继续全速运行，**没有任何惩罚**。
  - 如果猜错了，才需要停顿、冲刷流水线并从正确的地址重新取指。

**2. 最简单的分支预测：预测不跳转 (S82)**

- 我们设计的这条流水线，其默认行为——总是去取 PC+4 的指令，本身就是一种**隐式的分支预测**。它总是在**预测分支不成功 (predict not taken)**。
- **优点**:
  - 对于**不跳转**的分支，预测 100% 正确，流水线没有任何停顿，性能完美。
- **缺点**:
  - 对于**跳转成功**的分支，预测 100% 错误。我们仍然需要承受那 3 个周期的停顿惩罚来纠正错误。

**目标**: 分支预测的目标就是**提高猜测的准确率**，从而**降低平均的惩罚**。现代 CPU 拥有极其复杂和精准的分支预测器，其准确率可以达到 95% 以上，这是提升流水线性能的关键技术之一。

## Superscalar Processors and Calculating CPI

超标量处理器与 CPI 计算

我们已经通过流水线技术，将 CPU 的吞吐率从远小于 1 GIPS 提升到了接近 5 GIPS (理想情况下)。现在我们要思考一个问题：性能的提升之路到此为止了吗？还有没有办法让 CPU 在一个时钟周期内完成**超过一条**指令？

三条主要路径：

1. **提高时钟频率 (Increase clock rate)**: 这是最直接的方式，但我们已经知道，它受限于制造工艺和“功耗墙”，这条路已经越来越难走。
2. **增加流水线深度 (Increase pipeline depth)**:
   - **原理**: 将经典的五级流水线进一步切分，变成 10 级、15 级甚至更多级的“超长流水线 (deeper pipeline)”。
   - **优点**: 每个阶段的逻辑更少，使得**时钟周期可以变得更短**，从而提高时钟频率。
   - **缺点**:
     - **冒险的代价更大**: 一次数据冒险或控制冒险可能需要停顿更多的周期，导致 CPI 惩罚增加。
     - **流水线寄存器开销**: 更多的寄存器会增加延迟和功耗。
3. **设计超标量处理器 (Design a superscalar processor)**:
   - 这是今天要介绍的核心概念。它的目标是实现 **CPI < 1**，也就是 **IPC (Instructions Per Cycle) > 1**。

### 超标量处理器

#### 核心思想：多路并行执行 (Multiple-issue)

- 超标量处理器在一个时钟周期内，可以**同时取指、译码、发射 (issue) 多条指令**。
- 为了实现这一点，它内部拥有**多个并行的执行单元 (Execution Units)**，比如多个整数 ALU、多个浮点运算单元、多个加载/存储单元等。
- 每种执行单元都有自己专属的“等候区”，称为**保留站 (Reservation station)**。

![image.png](https://pub-cc2ebc8a43754210aa734d07c4898ad1.r2.dev/2025/07/20250727102208696.webp)

#### 乱序执行 (Out-of-Order Execution)

- 指令被取入后，并**不严格按照**程序原有的顺序执行。
- 控制逻辑会动态地分析指令间的数据依赖关系。一旦某条指令的操作数都准备好了（无论这些操作数是来自寄存器还是由前面的指令刚刚计算出来），它就可以被**提前发射**到空闲的执行单元去执行，即使它前面的某条指令因为数据未就绪还在等待。
- **目的**: 通过动态地重新排序指令，来最大程度地**隐藏**由数据冒险（特别是 load-use 冒险）带来的停顿，从而“填满”所有的执行单元，提升并行度。
- 所有指令在执行完毕后，会有一个**提交单元 (Commit unit)** 来确保它们的结果最终**按照程序原有的顺序**更新到寄存器和内存中，从而保证程序的逻辑正确性。

#### 与多核 (Multicore) 的区别

- **超标量**是在**一个核心 (core)** 内部，通过并行化执行单元来加速**单个**程序/线程 (single thread)。
- **多核**是通过在**一个芯片**上集成**多个独立的核心**，来并行地执行**多个**程序/线程 (multiple threads)。

#### 性能：CPI计算

因为超标量处理器每个周期能完成多于一条指令，所以它的平均 CPI 必然小于 1。例如，一个双发射 (dual-issue) 的处理器，理论上的峰值 CPI 可以达到 0.5 (即 IPC=2)

![image.png](https://pub-cc2ebc8a43754210aa734d07c4898ad1.r2.dev/2025/07/20250727102357587.webp)

但实际上没有任何一个真实程序的 CPI 能达到 0.5 的理想值。大部分程序的实际 CPI 都在 1.0 到 3.0 之间。这说明，即使有了强大的乱序执行硬件，**流水线冒险**和**内存访问延迟**仍然是限制处理器性能的最主要瓶颈。
