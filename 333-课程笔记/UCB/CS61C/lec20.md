## Case Study: Matrix Multiplication

矩阵乘法。这是一个经典的计算问题，也是许多复杂算法（比如神经网络和数据分析）的基础。所以，优化它具有非常重要的现实意义。

为了简化问题，讲师首先设定了几个前提条件：

- 我们处理的都是**方阵**（行数和列数相等）。
- 矩阵在内存中是按**行主序 (row-major)** 存储的。这意味着，内存中第一行的所有元素是连续存放的，然后是第二行的所有元素，以此类推。这对于我们后续讨论缓存（Cache）的性能至关重要。
- 我们暂时只考虑最基础的 O(n³) 复杂度的乘法算法，不涉及更高级的算法。

目标很明确：计算两个矩阵 A 和 B 的乘积 AB。

为了衡量我们优化的效果，首先需要知道如何精确地测量程序的运行时间。

### 测量程序运行时间

在 C 语言中测量运行时间的工具库 <time.h>。我们人类对时间的感知（比如闰年、闰秒）比较复杂，但在计算机中，通常使用“纪元时间 (epoch time)”，也就是从某个固定的历史时间点到现在的总秒数。最常见的纪元是 Unix 时间，从 1970 年 1 月 1 日开始计算。

> 有趣的小知识点：很多旧系统用一个 32 位的有符号整数来存储 Unix 时间，这会导致它在 2038 年的某一天溢出，这就是著名的“2038年问题”！

对于我们的任务，C 语言提供了一个非常有用的函数 clock()，它可以测量从程序开始执行到当前时刻所花费的时间。

一个通用的测量步骤：

1. **第 1 步**：在你想要测量的代码段**开始前**，调用一次 clock()，记录下起始时间。
2. **第 2 步**：运行你的代码。
3. **第 3 步**：在代码段**结束后**，再调用一次 clock()，记录结束时间。将两次记录的时间相减，就得到了程序运行的时钟周期数。为了把它换算成秒，需要除以一个常量 CLOCKS_PER_SECOND。
   - **注意**：这里一定要把结果转换成 double 或 float 类型，否则整数除法可能会导致结果不精确。

请注意：

- 由于系统可能会有随机的延迟（lag spikes），最好是**多次运行测试并取平均值**，这样结果更可靠。
- **对程序的不同部分分别计时**，这能帮助我们找到真正的性能瓶颈，也就是最耗时的部分。

#### Matrix Multiply in C

同样的无优化矩阵乘法例子：C比Python快35倍，而用C实现并且经过优化的Numpy比我们无优化的C快10倍。

### Operation Time Costs

一个经验法则，不同操作的耗时有天壤之别，从快到慢大致是：

1. **算术运算 (Arithmetic operations)**：最快的操作，理想情况下 1 个时钟周期就能完成。
2. **分支和跳转 (Branches and Jumps)**：比算术运算慢，因为可能导致流水线冒险 (hazards)。
3. **内存操作 (Memory operations)**：访问内存（RAM）比前两者慢得多，可能需要 3 到 100 个时钟周期。这是优化的重点区域。
4. **文件操作 (File operations)**：最慢的操作，因为它涉及到访问磁盘（disk），比访问内存要慢几个数量级。

这个排序告诉我们一个核心的优化思想：**要让程序跑得快，就要尽可能多地进行算术运算，而尽量减少访问内存，尤其是避免分支跳转和文件I/O**。

## Single-Threaded Optimizations

单线程优化

在考虑如何利用多个处理器核心之前，我们首先要确保单个线程上的代码已经尽可能高效。这些优化技巧是性能编程的基石。

### 第一个优化技术：Loop Unrolling和Function Inlining

**循环展开 (Loop Unrolling) 和函数内联 (Function Inlining)**。

这两种技术的核心思想都源于我们在上一个主题学到的知识：**分支和跳转是耗时的**。所以，优化的一个方向就是减少程序中不必要的跳转和分支指令。

- **函数内联 (Function Inlining)**：它的做法是，直接用函数的代码体替换掉函数调用本身。幻灯片左边的代码有一个循环，每次都调用函数 f(i)。右边的优化版本中，编译器（或者我们手动）将 f(i) 直接替换成了 i\*i。这样做的好处是什么呢？
- **循环展开 (Loop Unrolling)**：它的做法是在一次循环迭代中执行更多的工作。请看幻灯片中的 for 循环示例。左边的原始循环一次只处理一个元素。右边的优化版本一次处理四个元素（i+=4），循环的步长变大了。这意味着循环的总迭代次数减少了，从而减少了循环判断和跳转的次数。

原始版本代码：

```c
int f(int i) {return i*i;}
for(int i=0; i<max; i++) {
	arr[i]=f(i);
}
```

可以优化成：

```c
int i=0;
// 主循环：一次处理4个元素
for(; i<(max/4)*4; i+=4) {
	arr[i]=i*i;
	arr[i+1]=(i+1)*(i+1);
	arr[i+2]=(i+2)*(i+2);
	arr[i+3]=(i+3)*(i+3);
}
// 处理剩余元素
for(; i<max; i++) {
	arr[i]=i*i;
}
```

- 对于**函数内联**，它能显著减少运行时间，因为它避免了函数调用时的额外开销，比如建立栈帧（stack frame）、处理调用约定（calling convention）等。我们甚至可以用 inline 关键字向编译器“建议”进行内联，比如 inline int f(int i);。
- 对于**循环展开**，它通过减少分支次数来降低运行时间，效果有时会出奇地好。很多现代编译器（比如 gcc）会自动进行一定程度的循环展开，但有时我们手动进行展开，可以获得比自动优化更好的效果。

#### 优化的缺点

优化都不是没有代价的：

- 最直接的影响是代码和最终生成的可执行文件会**变大**。
- 如果循环体展开得过大，可能会超出硬件对分支指令跳转范围的限制，反而导致性能惩罚。
- inline 关键字仅仅是一个**建议**，编译器完全可以忽略它。
- 由于编译器可能已经做了优化，我们手动优化的效果可能微乎其微，甚至难以预测。
- **一个主要的缺点是**：循环展开会使代码变得**非常难以阅读和修改**。因此，最好的实践是在开发的最后阶段，确认性能瓶颈确实在此处时，再进行这项优化。

### 第二个优化技术：Variable Caching

**变量缓存 (Variable Caching)**。

这里的核心思想有两个：

1. **避免重复计算**：将循环中重复计算但结果不变的表达式，在循环外计算一次，并存入一个变量中。幻灯片中的例子就是将 max/4 这个在每次循环中都重新计算一遍的操作，提前存入了变量 maxoverfour。
2. **善用寄存器**：我们知道，访问寄存器比访问内存快得多。我们可以使用 register 关键字“建议”编译器将一个频繁使用的变量（比如循环计数器 i）放入寄存器中，而不是放在内存的栈上。

原始版本代码：

```c
for(int i=0; i<max/4; i++) {
	f(i);
}
```

优化后的代码：

```c
register int i=0;
register int maxoverfour = max/4;
for(; i<maxoverfour; i++) {
	f(i);
}
```

#### 变量缓存的缺点

- **寄存器的数量是有限的**。特别是像 x86 这样的架构（PC 常用），寄存器数量比 RISC-V 少，所以大部分变量最终还是得放在栈上。
- 这使得代码性能更依赖于具体的硬件架构，为一个架构优化的代码在另一个架构上可能表现不佳。
- 同样，编译器可能已经自动完成了这项工作，所以手动优化的效果可能不一致。
- register 关键字也仅仅是一个**建议**。

### 第三个优化技术：Data Caching

**数据缓存 (Data Caching)**

这个概念与刚才的“变量缓存”不同，它关注的是内存中的**数据**本身。

- 我们已经知道访问主存（main memory）非常慢（可能要几百个时钟周期）。
- **数据缓存**的核心思想，就是将常用的数据保存在离 CPU 更“近”的缓存（Cache）中，这样访问它只需要大约 10 个时钟周期。
- 更进一步，现代 CPU 还有“缓存预取 (cache prefetching)”功能，它会尝试预测你接下来需要什么数据，并提前把它加载到缓存中。

这里的关键点，也是计算机体系结构的一个核心原理，叫做**局部性原理 (Principle of Locality)**。

**访问连续的内存地址，平均速度会比访问不连续的地址快得多**。这就是所谓的“空间局部性 (spatial locality)”。

PPT**第 20 页**用一个实际的例子生动地展示了这一点。测试结果显示，访问连续地址平均耗时约 0.011 秒，而访问非连续地址则需要 0.119 秒，性能差距达到了 **10 倍**！

那么，如何将这个原理应用到我们的矩阵乘法案例中呢？

#### Data Caching for Matrix Multiplication

在一个朴素的矩阵乘法 C = A \* B 中，为了计算结果矩阵 C 的一个元素 C[i][j]，我们需要 A 矩阵的第 i 行和 B 矩阵的第 j 列。

- 访问 A 的第 i 行是**连续的**（因为矩阵是行主序存储的），这对缓存非常友好。
- 但是，访问 B 的第 j 列是**非连续的**，我们需要在内存中“跳来跳去”（从一行跳到下一行），这会导致大量的缓存未命中 (cache miss)，严重影响性能。

优化方案：**转置 (Transpose)**。  
在进行乘法计算之前，我们先把第二个矩阵 B 进行转置。转置后的 B_T，它的行就是原矩阵 B 的列。这样，当我们计算 C = A \* B_T（这里算法要做相应调整）时，就变成了访问 A 的行和 B_T 的行，两者都是连续的内存访问！这种方式极大地利用了缓存。

当然，这种优化也有其代价:

- 转置操作本身需要 O(N²) 的时间，而且是低效的内存访问。
- 但是，它将后续 O(N³) 次的低效内存访问变成了高效访问。
- 因此，对于**非常大**的矩阵，这个优化是值得的；但对于小矩阵，转置的开销可能比带来的好处还大。
- 如何兼得两者之长？我们可以设定一个**阈值 (threshold)**。当矩阵尺寸小于这个阈值时，使用朴素算法；大于阈值时，就先进行转置。这个阈值需要通过在目标机器上进行实际测试来确定。

经过了这么多优化，效果究竟如何呢？**第 27 页**的图表给出了答案。对于 1000x1000 的矩阵：

- 原始 C 代码耗时：2.1 秒
- 优化后的（非转置）版本：0.88 秒
- 优化后的转置版本：**0.417 秒**！

### Summary

我们学习了三种主要的单线程优化技术：

1. **循环展开**：在一次循环中执行更多指令，减少控制冒险（control hazard）。
2. **变量缓存**：强制变量存入寄存器。
3. **缓存阻塞 (Cache Blocking)**：重排数据访问以更好地利用缓存（我们通过矩阵转置实现）。

## Amdahl's Law

**阿姆达尔定律**

对阿姆达尔定律的正式定义。

- 这被称为“性能编程的克星 (the bane of performance programming)”，因为它为我们的优化设定了理论上限。
- **核心思想**：“我们能获得的最大加速比，受限于代码中那部分无法被加速的比例。”
- 幻灯片举了一个例子：假设我们能把 95% 的代码优化到极致（瞬间完成），但剩下的 5% 无法改动。那么，这 5% 的时间就成了我们程序的最终运行时间。因此，我们最多只能获得 1 / 0.05 = **20 倍**的加速比。
- **通用公式**：加速比 = 1 / ((1 - F) + F / S)，其中 F 是被优化的代码所占的比例，S 是这部分代码的加速倍数。不过，就像幻灯片所说，把这类问题当成应用题来思考，往往比直接套公式更直观。

### 练习计算题

- **问题**：我们有一个优化，可以把函数 foo 的速度提升 100 倍。但遗憾的是，foo 函数的运行时间只占我们原始代码总运行时间的 25%。那么，整个代码的总体加速比是多少？

**第 35 页**和**第 36 页**给出了两种解法。

**方法一（第 35 页）：使用公式**

- F = 0.25 (可优化的部分)
- S = 100 (加速倍数)
- 加速比 = 1 / ((1 - 0.25) + 0.25 / 100) = 1 / (0.75 + 0.0025) ≈ **1.329 倍**。

**方法二（第 36 页）：应用题解法（更直观！）**

- 假设原始代码运行需要 100 秒。
- 那部分无法优化的代码（75%）仍然需要 75 秒。
- foo 函数原本需要 25 秒（25%），现在速度提升了 100 倍，所以只需要 25 / 100 = 0.25 秒。
- 优化后的总时间 = 75 秒 + 0.25 秒 = 75.25 秒。
- 总体加速比 = 原始时间 / 新时间 = 100 / 75.25 ≈ **1.329 倍**。

### Summary

因此，为了有效地加速你的代码，你必须**知道哪些部分是真正的性能瓶颈**。把时间花在优化那些本来就很快的代码上是徒劳的。

阿姆达尔定律告诉我们，单线程优化的道路是有尽头的。一旦我们把最耗时的部分优化完毕，再想获得显著的性能提升就会变得异常困难。

那么既然单个线程的潜力有限，我们该如何寻求新的突破？答案就是**并行 (Parallelism)**。

## Why Parallelism?

一个根本性问题：“我们为什么要关心并行？” 讲师通过对比“我的电脑”和“超级计算机”来回答这个问题。

- 超级计算机，比如伯克利的 Savio 集群或谷歌/亚马逊的计算仓库，都是能够处理超大规模计算的大型系统。
- 而我们日常使用的个人电脑，在结构上可以看作是超级计算机的缩小版。讲师的电脑配置是 2.2 GHz 的时钟频率，16 GB 内存，以及一个 64 位的 Intel CPU。

那么，超级计算机和个人电脑最大的区别是什么呢？

- 更高的时钟速度？
- 更快的内存访问？
- 更高的晶体管密度？
- 更复杂的操作？
- 超级计算机仅仅是一堆普通电脑的集合？

**第 43 页：更高的时钟速度？**

- 答案是**否定的**。这里涉及到一个物理极限——**光速**。
- 光速大约是每秒 300,000,000 米。1 GHz 的时钟周期是 1 纳秒 (nanosecond)。简单的计算告诉我们，光在 1 纳秒内大约能传播 30 厘米（约一英尺）。
- 讲师的电脑时钟频率约为 2 GHz，这意味着时钟周期是半个纳秒。在这个时间内，电信号（速度接近光速）只能传播大约 15 厘米。
- **结论**：如果 CPU 的尺寸比手掌还大，那么在一个时钟周期内，信号甚至无法从芯片的一端传到另一端，这就破坏了“同步”这个概念。超级计算机是一个巨大的仓库，远比手大，因此它**不可能**以一个比个人电脑快得多的统一时钟速度运行。

**第 44 页：更快的内存访问或更多的晶体管？**

- 答案同样是**否定的**。
- 内存访问速度，特别是基于磁盘的访问，也已接近物理极限。
- 在芯片上集成更多的晶体管会产生大量的**热量**，甚至会导致硅片熔化。
- 虽然有小的改进空间，但不可能实现数量级（比如 1000 倍）的提升。

**第 45 页：更复杂的操作？**

- 对于 CISC（复杂指令集计算机）架构来说，这是可行的。
- 但对于我们学习的 RISC（精简指令集计算机）架构，增加复杂指令反而可能降低效率。
- 即便如此，这种方式带来的性能提升也相对有限（大约 4-8 倍），远达不到超级计算机的水平。

真正的答案是什么呢？**第 46 页**揭晓了谜底：**更多的计算机（核心）**。

- 个人电脑可能拥有 12 个可以独立运行程序的 CPU 核心。
- 而 Savio 集群拥有 **3600 个 CPU 核心**，并且每个核心的性能都和我们个人电脑的核心一样强大。
- **最大的区别在于规模**。因此，要想利用超级计算机的强大能力，我们必须学会**如何让成百上千个计算单元协同工作，共同解决同一个问题**。这就是并行的本质。

图表《48 年的微处理器趋势数据》是计算机体系结构领域最著名的图表之一。它清晰地展示了：

- **晶体管数量 (Transistors)**：在很长一段时间里遵循摩尔定律，持续指数级增长。
- **时钟频率 (Frequency)**：在 2005 年左右达到了顶峰，然后就基本停滞不前了。这就是我们刚才讨论的物理极限。
- **功耗 (Typical Power)**：同样在 2005 年左右遇到了瓶颈，因为我们无法无限制地为芯片散热。
- **单线程性能 (Single-Thread Performance)**：也随之放缓了增长。
- **逻辑核心数量 (Number of Logical Cores)**：正是在这个转折点之后，核心数量开始显著增加！

到这里我们就可以回答：“为什么需要并行计算”？

- 由于技术和经济上的挑战（散热、能耗），CPU 的时钟频率不再增长。
- **并行处理 (Parallel processing) 是目前提升性能的唯一途径**。

我们的目标变成了：如何让**一个程序/任务**通过利用更多的计算资源来跑得更快？

### 弗林分类法 (Flynn's Taxonomy)

为了系统地理解并行，我们需要一种分类方法。**弗林分类法 (Flynn's Taxonomy)**，这是 1966 年提出的一个经典的并行硬件分类系统，至今仍在使用。

它根据**指令流 (Instruction Stream)**和**数据流 (Data Stream)**的数量，将计算机体系结构分为四类：

1. **SISD (Single Instruction, Single Data)**：单指令流，单数据流。
2. **SIMD (Single Instruction, Multiple Data)**：单指令流，多数据流。
3. **MISD (Multiple Instruction, Single Data)**：多指令流，单数据流。
4. **MIMD (Multiple Instruction, Multiple Data)**：多指令流，多数据流。

如今最常见的是 SIMD 和 MIMD，它们甚至常常出现在同一个系统里。

- **第 50 页：SISD**
      - 这就是传统的**顺序计算机**，没有任何并行性。我们到目前为止在 CS61C 中学习的单核 RISC-V 处理器就属于这一类。

- **第 51 页：SIMD**
  - 用**一条指令**同时对**多个数据**进行操作。这对于可以被自然并行的操作（比如向量或矩阵运算）非常有效。

## Data Level Parallelism: SIMD

让我们深入探讨一种非常强大且广泛应用的并行技术——**数据级并行 (Data-Level Parallelism, DLP)**，也就是我们刚才在弗林分类法中提到的 **SIMD**。

我们之前学到：“处理器性能的铁律 (Iron Law of Processor Performance)”。  
`Time/Program = Instructions/Program * Cycles/Instruction * Time/Cycle`

要缩短程序的运行时间，我们可以从三个方面入手：

1. **减少每个程序的指令数 (Instructions/Program)**：这通常需要算法层面的优化。
2. **减少每条指令的平均时钟周期数 (Cycles/Instruction, CPI)**：我们之前学的流水线、缓存等技术就是为了降低 CPI。
3. **缩短时钟周期时间 (Time/Cycle)**：也就是提高时钟频率，但我们已经知道这条路已经走到了尽头。

SIMD 技术，就是从一个新的角度来优化这个公式。它关注的是**在一条指令里做更多的工作**，从而间接地**减少解决问题所需的总指令数**。

### Toy Example: Vector Sum

为了理解 SIMD 的工作原理，我们可以看一个例子：**向量求和 (Vector Sum)**。

- **问题**：我们有两个 4 元素的向量 a0 和 a1，每个元素都是 8-bit 的数字。我们的目标是计算它们的和，结果存入向量 a2。

一个**朴素 (Naive)** 的实现方法。

- 我们需要对向量的每个元素分别进行加载 (load)、相加 (add) 和存储 (store) 操作。
- 每个元素的计算需要 4 条指令（lb t0, offset(a0); lb t1, offset(a1); add t0, t0, t1; sb t0, offset(a2)）。
- 因为向量有 4 个元素，所以总共需要 4 \* 4 = 16 条指令。
- 问题是：我们能做得更好吗？

一种看似聪明的解法。

- 既然我们的 RISC-V 处理器是 32-bit 的，而每个元素是 8-bit，那么 4 个 8-bit 的元素刚好可以放进一个 32-bit 的寄存器。
- 我们可以用一条 lw（load word）指令一次性把整个向量 a0 加载到寄存器 t0，用另一条 lw 加载 a1 到 t1。
- 然后用一条 add 指令对 t0 和 t1 进行相加，最后用一条 sw（store word）指令把结果存回内存。
- 这样，指令数从 16 条锐减到了 4 条！

但是很明显，这个方法的问题是：一个元素的计算（比如第一个元素 1+5=6）产生的**进位 (carry)** 会影响到下一个元素的计算结果。

- 例如，如果 0b0000 0001 + 0b0000 0101 旁边的一个元素是 0b1000 0000 + 0b1000 0000，后者的计算会产生一个进位溢出到前者的比特位上，导致最终结果完全错误。
- **结论**：普通的 add 指令行不通。我们需要一种新的指令，它能同时对这 4 对 8-bit 数字进行独立的加法，而忽略它们之间的进位。这就是向量指令 vec_add 的由来。

### SIMD 指令正式定义

- 核心思想：**不再一次只对一个数字进行数学运算，而是在同一个时钟周期内，对多个数字执行相同的数学运算**。
- 这需要使用专门的“向量”寄存器，它们非常宽，可以存储 128、256 甚至 512 位的数据。
- SIMD 指令作为基础指令集的扩展存在。
- 一个非常重要的洞见是：SIMD 带来的大部分加速，其实并非来自同时做多个数学运算，而是来自**一次性进行大块内存的加载/存储**。回想一下，内存操作比算术操作慢得多，所以能一次性加载 4 个、8 个甚至 16 个元素，会带来巨大的性能提升。

#### 注意事项 Caveats

- 每条 SIMD 指令都需要专门的硬件电路，所以我们只能使用 CPU 提供的那些指令。
- 宽的向量寄存器和对应的计算单元很昂贵，而且可能比标准指令需要更多的时钟周期。
- 因为只有一个程序计数器 (PC)，我们**无法向量化分支或跳转指令**。
- 我们通常只能方便地加载**连续的内存块**到向量寄存器中。

#### Intel Intrinsics

在实际编程中如何使用 SIMD，以 **Intel Intrinsics** 为例。这是一种在 C/C++ 代码中直接使用 SIMD 指令的方法。

- Intel 提供了多个库（或指令集扩展），如 SSE, AVX, AVX-2, AVX-512，它们提供不同宽度（64-bit 到 512-bit）的向量寄存器和功能。

- **向量寄存器类型**：有专门的数据类型，如 **m256 (256-bit 浮点数向量), **m256d (256-bit 双精度浮点数向量), 和 \_\_m256i (256-bit 整数向量)。
- **指令格式**：通常遵循 *mm<寄存器大小>*<指令名称>\_<数据类型> 的格式。例如，\_mm256_add_epi32 就是对两个 256 位向量进行 32 位整数加法。\_mm_load_ps 则是加载 4 个单精度浮点数。
- 虽然它们看起来像 C 函数，但编程体验更接近于汇编，需要你精确地控制数据如何在寄存器和内存之间移动。

1. \_mm_load_si128(a)：加载向量 a。
2. \_mm_load_si128(b)：加载向量 b。
3. \_mm_add_epi32(...)：执行向量加法。
4. \_mm_store_si128(c, sum)：存储结果。  
   整个过程只需要 4 个核心操作，并且完全利用了硬件的并行能力。

```c
__mm128i avec = _mm_load_si128(a);
__mm128i bvec = _mm_load_si128(b);
__mm128i sum = _mm_add_epi32(avec, bvec);
_mm_store_si128(c, sum);
```

使用 SIMD 时的一些**常见错误**，这对于实际编程非常有指导意义：

- 不能直接访问 SIMD 向量中的某个元素，必须通过显式的加载/存储。
- 加载/存储时需要注意**内存对齐 (alignment)**。如果地址没有对齐，需要使用专门的 loadu/storeu (unaligned) 指令。
- 要处理**尾部情况 (tail case)**。如果数组长度不是向量宽度的整数倍，剩下的几个元素需要用普通代码来处理。
- 避免使用过多的向量变量，因为这可能导致编译器频繁地将向量寄存器溢出到栈上，反而降低性能。
