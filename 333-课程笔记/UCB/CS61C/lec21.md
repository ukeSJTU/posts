## Example: Matrix Multiplication with SIMD

我们将把刚刚学到的 SIMD 知识应用到这个实际问题中，看看性能究竟能有多大的飞跃。

先分析如何将 DLP 应用于矩阵乘法。

- 我们知道，结果矩阵中的每一个元素，都是由两个向量的**点积 (dot product)** 计算得出的。
- 点积运算（一个向量的元素与另一个向量的对应元素相乘，然后求和）天然适合用 SIMD 来加速。
- 但是，我们之前也讨论过，SIMD 指令通常只能加载**连续的内存**。在 C = A \* B 的计算中，要计算点积，我们需要 A 的一行和 B 的一列。A 的行是连续的，但 B 的列不是。
- 因此，和之前讨论单线程优化时一样，我们的第一步仍然是**转置第二个矩阵**。

**第 22 页到第 32 页**用一个非常详细的、分步骤的动画，展示了如何用 SIMD 高效地计算点积。我们假设要计算两个很长的浮点数数组 arr 和 arrtwo 的点积。

- **第 22 页 - 步骤 1: 初始化累加器**
  - 我们需要一个向量寄存器来累加乘积的结果。我们先用 _mm128_set1_ps(0) 指令将一个 128-bit 的向量寄存器 v3 的所有元素都设置为 0。这个 v3 就是我们的累加器。
- **第 23 页 - 步骤 2: 加载数据**
  - 我们进入主循环。在每次迭代中，我们用 _mm128_load_ps 分别从 arr 和 arrtwo 中加载 4 个浮点数到向量寄存器 v1 和 v2 中。
- **第 24 页 - 步骤 3: 乘加运算**
  - 现在我们需要将 v1 和 v2 中的元素对应相乘，然后把结果加到我们的累加器 v3 上。
  - 这个“先乘后加”的操作非常常见，以至于现代 CPU 提供了一条专门的指令来完成它，叫做 **FMA (Fused Multiply-Add)**。在 Intel Intrinsics 中对应的就是 _mm256_fmadd_ps(v1, v2, v3)，它计算 (v1 \* v2) + v3 并把结果存回 v3。这比分开做乘法和加法更高效。
- **第 25 到 27 页 - 步骤 4: 循环**
  - 我们不断重复步骤 2 和 3，遍历整个数组的主要部分（长度为 4 的整数倍的部分）。v3 寄存器会不断累加每个数据块的点积结果。最终 v3 中会包含 4 个部分和。
- **第 28 页 - 步骤 5: 存储结果**
  - 循环结束后，我们需要将 v3 中累加的 4 个部分和从寄存器存回内存，以便进行最后的求和。
  - 这里用到了 _mm128_store 指令。幻灯片还特别展示了如何强制内存对齐：float mem[4] **attribute**((aligned (32))); 这是一个 gcc 的扩展语法，可以确保数组 mem 的起始地址是 32 字节对齐的，从而可以使用更高效的对齐加载/存储指令。
- **第 29 到 31 页 - 步骤 6: 处理尾部**
  - 如果数组长度不是 4 的整数倍，循环结束后会剩下一些元素。我们需要用一个普通的 for 循环来处理这些“尾巴”，将它们的乘积结果累加到最终结果中。
- **第 32 页 - 步骤 7: 最终求和**
  - 最后，我们将内存 mem 中的 4 个部分和加起来，得到最终的点积结果。

整个点积计算过程的代码整合到了一起，形成了一个完整的函数：

```c
__m128 v3 = _mm128_set1_ps(0);
int i;
for(i = 0; i < arrlen/4*4;i+=4) {
	__m128 v1 = _mm128_load_ps(arr+i);
	__m128 v2 = _mm128_load_ps(arrtwo+i);
	v3 = _mm256_fmadd_ps(v1, v2, v3);
}
float mem[4] __attribute__ ((aligned (32)));
_mm128_store(mem, v3);
for(;i<arrlen;i++) {
	mem[0]+=arr[i]*arrtwo[i];
}
return mem[0]+mem[1]+mem[2]+mem[3];
```

一个**最终的优化**。

- 在计算矩阵乘法时，我们不仅仅是计算一个点积，而是要计算很多个。比如，A 矩阵的第 1 行要分别和 B 矩阵（转置后）的第 1、2、3、4... 行计算点积。
- 我们可以发现，A 矩阵的第 1 行会被重复加载 n 次，这是一种浪费。
- 一个更高级的技巧是，利用更多的向量寄存器，**同时计算多个输出元素**。例如，我们可以同时计算结果矩阵 C 中 4 个元素的值。这需要同时加载 A 矩阵的 4 行，然后分别与 B 矩阵（转置后）的一行进行 FMA 操作。
- 这样做虽然使用了更多的寄存器，但极大地减少了内存加载的次数，可以获得接近 2 倍的性能提升。

性能提升从结果来看：

- 对于一个 1504x1504 的矩阵：
  - 原始 C 代码：7.7 秒
  - 优化后的转置 C 代码：1.43 秒
  - **SIMD 版本的代码：0.644 秒**！
- SIMD 版本比精心优化的转置版本还要快了大约 **2 倍**。这个提升非常可观。

### Summary

- 在这个案例中，SIMD 版本只带来了小幅提升，是因为此时，**转置操作本身**成了新的性能瓶颈（这再次印证了阿姆达尔定律）。
- SIMD 指令在对一个大数组执行相同操作时非常有用。
- 核心优化思想是：**加载和存储到 SIMD 寄存器的操作很耗时，所以我们的目标是让数据在寄存器里待得尽可能久，做尽可能多的计算**。

## Thread-Level Parallelism

我们从利用数据并行转向利用多核处理器，让多个“工人”同时为我们工作。

### Terminology

- **程序 (Program)**：一组指令的静态集合，比如我们编译生成的可执行文件。
- **进程 (Process)**：一个正在执行的程序实例。每个进程都有自己独立的内存空间，它们之间是高度隔离的。
- **线程 (Thread)**：是进程的组成部分，是独立运行的指令序列。关键在于，**同一个进程内的多个线程共享大部分内存空间**（比如堆内存）。
- **CPU 核心 (Core)**：我们之前讨论的数据通路 (datapath) 就是一个 CPU 核心。一个核心在任何一个时刻只能运行一个线程。
- **CPU (Central Processing Unit)**：它由多个核心组成，从而可以**同时 (simultaneously)** 运行多个线程。

- **单线程程序 (Single-threaded program)**：只运行一个线程的程序。我们到目前为止写的程序都是单线程的。
- **多线程/多进程程序 (Multi-threaded/multi-process)**：使用多个线程或进程的程序。
- **操作系统 (Operating System, OS)**：负责管理哪个线程在哪个 CPU 核心上运行。
- 一个重要的现实是：在现代计算机上，活跃线程的数量通常远远大于可用的核心数量。这意味着**大多数线程在任何时候都处于空闲状态**。这也是为什么即使我们运行同一个程序，每次的运行时间也可能会有波动。

#### 从线程的角度说明为什么需要并行

- **指令/程序**：通过 SIMD，我们可以提升每条指令的工作量，但最多也只有 4-8 倍的加速。
- **周期/指令**：流水线和缓存已经优化得相当不错。
- **时间/周期**：摩尔定律放缓，时钟频率不再提升。
- **结论**：唯一的出路就是**并行化 (parallelize)**，也就是**增加单个程序可以使用的处理器（核心）数量**。

### 并行计算的目标和选择

- 我们不再满足于只有一个线程，而是要编写一个能同时运行多个指令序列的程序。
- **为什么要这样做？**
  - 我们的电脑有多个核心（比如 16 个），我们希望把它们都用上。
  - 如果一个线程因为等待内存访问而阻塞，CPU 可以切换到另一个线程去工作，从而提高核心的利用率。
  - 超级计算机拥有成千上万的核心，编写并行代码是使用它们的唯一方式。
- **两个主要选择**：
  1. **增加每个进程的线程数**：这就是**多线程 (Multithreading)**，我们今天的主题。
  2. **增加一个程序的进程数**：这就是**多进程 (Multiprocessing)**，我们明天会讨论。

### Multi-Thread vs Multi-Process

对**多线程**和**多进程**进行了非常重要的对比。

- **线程 (Threads)**：
  - 在同一个进程内，**共享内存**。
  - 因此，它们之间的通信“容易”(Easy)。
  - 但通常受限于单个计算节点（node）内的核心数量。
- **进程 (Processes)**：
  - 很大程度上是相互独立的，**不共享内存**。
  - 因此，它们之间的通信“困难”(Difficult) 且耗时。
  - 但可以扩展到任意多的核心，跨越多个计算节点。
- 幻灯片用伯克利的 Savio 集群举例，生动地展示了不同并行策略的理论加速比，从单线程的 1 倍，到多线程的 28 倍，再到多进程的 4564 倍，最后到结合 SIMD 的多进程，理论上可达惊人的 36512 倍！

**多线程框架 (Multithreading Framework)** 的基本结构。当一个进程创建多个线程时：

- **每个线程独有**：自己的寄存器（包括程序计数器 PC）和自己的栈 (stack)。
- **所有线程共享**：同一个堆 (heap)。
- **通信方式**：通过读写共享内存（比如堆上的数据）来进行。
- **执行顺序**：线程是同时运行的，我们**无法控制**它们执行的先后顺序。这是多线程编程中最核心的挑战。

一种经典的多线程模型：**Fork-Join 模型**。

- 程序开始时是**串行 (serial)**的，只有一个主线程 (master thread)。
- **Fork (分叉)**：主线程创建一个或多个子线程来执行一个并行的代码段。工作被分配给所有线程。
- **Join (汇合)**：主线程会等待，直到所有子线程都完成了它们的工作。然后，子线程被销毁，只剩下主线程继续串行执行。
- Fork 和 Join 操作本身是有开销的（相当于数千次内存操作）。因此，我们的目标是**最小化 Fork/Join 的次数**，并**最小化串行部分的耗时**（再次回到了阿姆达尔定律）。

一个生动的比喻解释了 Fork-Join 模型：**画一幅巨大的壁画**。

- **串行部分 (Step 1)**：我一个人做准备工作，比如设计草图、准备墙壁。
- **Fork (Step 2)**：我找来一群帮手（创建线程），这需要一些时间。
- **并行部分 (Step 3)**：我给每个人分配一块墙壁去画（分配任务）。
- **Join (Step 4)**：我等待所有人都画完他们那部分（同步）。
- **串行部分 (Step 5)**：我一个人做最后的清理和检查工作。

多线程编程中的核心问题和衡量标准：

- **主要问题**：最小化无法并行的部分，并**平衡负载 (balance the load)**。
- **负载平衡**：我们受限于那个做得最慢的人。如果任务分配不均，或者有些人工作效率低，那么其他人就只能等着，导致整体效率下降。在多线程中，完美地平衡负载几乎是不可能的。
- **强扩展性 (Strong scaling)**：问题规模不变，增加处理器数量，看运行时间能减少多少（理想是线性减少）。
- **弱扩展性 (Weak scaling)**：问题规模和处理器数量同时增加，看运行时间能否保持不变（理想是不变）。

## OpenMP Syntax

什么是 OpenMP。

- OpenMP 是 C/C++/Fortran 的一个**扩展**，专门用于编写**共享内存**的多线程代码。这意味着它非常适合在单台多核计算机上进行并行计算，但不适用于跨多台计算机的分布式计算。
- 使用 OpenMP 非常简单，只需要在编译时加上一个特殊的标志：gcc -fopenmp foo.c。
- 在代码中，你需要包含头文件 #include <omp.h>。
- 它遵循我们刚才学习的 **Fork-Join 框架**。
- 它的核心语法是使用所谓的**编译指导 (pragma)**，即形如 #pragma omp <command> 的代码行。这是一种给编译器下达指令的方式。

如何创建最基本的一个并行区域。

- 语法是：#pragma omp parallel { ... }
- 花括号 {...} 里的代码块就会被**所有**可用的线程**同时执行**。
- 如果并行区域里只有一行代码，可以省略花括号。
- 既然所有线程都执行相同的代码，我们怎么区分它们呢？OpenMP 提供了一些有用的函数：
  - omp_get_num_threads()：返回当前并行区域中正在运行的线程总数。
  - omp_get_thread_num()：返回当前线程的唯一 ID（一个从 0 到 总线程数-1 的整数）。

一个经典的“并行版 Hello World”的**演示代码 (Demo)**。

- 我们定义了一个**共享变量 (Shared variable)** x，它在并行区域之外声明。
- 在 `#pragma omp parallel` 区域内：
  - 每个线程首先获取自己的 ID，存入一个**私有变量 (Private variable)** tid。因为 tid 是在并行区域内声明的，所以每个线程都有自己的一份副本。
  - 每个线程都执行 x++。
  - 每个线程都打印出自己的 ID 和 x 的当前值。
  - 只有 0 号线程会打印出总的线程数。

两次运行的结果。

- **观察 1：顺序是随机的！** 两次运行，"Hello World" 打印的顺序完全不同。这印证了我们之前说的，线程的执行顺序是**不确定的 (non-deterministic)**。
- **观察 2：共享变量 x 的值很混乱！** 我们期望 x 的值会随着线程的打印有序地从 1 增加到 16。但实际上，它的值看起来是随机的，有时甚至会重复。例如，在左边的输出中，线程 9 和线程 11 都看到了 x=1 和 x=2 之后的值，但它们自己打印的 x 却不是连续的。

这种混乱的现象引出了多线程编程中最臭名昭著的问题。
