## OpenMP Syntax

关于OpenMP最基本的介绍内容放到了Lec21里面。

**共享变量 (Shared) vs. 私有变量 (Private)**。

- **默认规则**：在并行区域**之外**声明的变量是**共享的**，所有线程读写的是同一个内存地址。在并行区域**之内**声明的变量是**私有的**，每个线程都有一份独立的拷贝。
- 我们可以用 private(var) 和 shared(var2) 关键字来**覆盖**这个默认行为。
- 需要注意的是，**堆内存总是共享的**。

一个非常实际的问题：如何用 4 个线程（人）处理一个包含 100 万个元素的数组？如何划分工作？

**第 9 页**给出了两种划分策略：

1. **选项 1: 交织 (Interweaving)**
   - 线程 0 处理元素 0, 4, 8, ...
   - 线程 1 处理元素 1, 5, 9, ...
   - 这种方式在内存访问上是跳跃的。

2. **选项 2: 分块 (Blocking)**
   - 线程 0 处理元素 0 到 249999。
   - 线程 1 处理元素 250000 到 499999。
   - 每个线程都处理一块**连续的**内存。

**哪种更好？** 对于标准的多线程，**选项 2（分块）** 通常要快得多。因为“交织”会导致严重的**缓存一致性 (cache coherency)** 问题。每个核心都有自己的缓存，当多个核心频繁地写同一个缓存块（cache block）时，系统需要花费大量时间去同步这些缓存，导致性能急剧下降。而分块则很好地利用了缓存的**空间局部性**。

**选项 3**，也是 OpenMP 最优雅的解决方案：让编译器来为你做这件事！

- 我们可以使用 #pragma omp for 这个编译指导。它必须写在一个已经存在的 #pragma omp parallel 区域内。
- 它会自动将接下来的 for 循环的工作分配给各个线程。默认情况下，它使用的就是高效的**分块**策略。
- 更方便的是，我们可以将两者结合起来写成 #pragma omp parallel for，这样一行代码就能完成并行化一个循环的所有工作！

现在，让我们回到刚才“并行版 Hello World”中遇到的那个奇怪问题。**第 11 页**将这种现象命名为**数据竞争 (Data Races)**。

- 当多个线程在没有同步的情况下，同时访问（至少有一个是写操作）同一个共享内存位置时，就会发生数据竞争。
- 程序的最终结果将取决于线程执行的“运气”顺序。
- 一个多线程程序只有在**任何**可能的线程交错执行顺序下都能产生正确结果时，才被认为是正确的。

数据竞争的根源。

- **问题 (第 12 页)**：int x = 0; #pragma omp parallel { x = x + 1; }，用 4 个线程执行，x 的最终值可能是多少？
- **分析 (第 16 页)**：x = x + 1 这一行 C 代码，在汇编层面其实是三条指令：
  1. lw t0, 0(sp) (从内存加载 x 到寄存器 t0)
  2. addi t0, t0, 1 (在寄存器中加 1)
  3. sw t0, 0(sp) (将新值从寄存器写回内存)
- **最坏情况 (第 18 页)**：所有 4 个线程都先执行了第一步（加载 x=0），然后各自在自己的私有寄存器里加 1 得到 1，最后再依次把 1 写回内存。最终 x 的值是 **1**，而不是我们期望的 4！
- **最好情况 (第 17 页)**：所有线程严格按顺序执行完自己的三步操作，最终 x 的值是 **4**。
- **其他情况 (第 19-20 页)**：通过不同的指令交错，我们还可以得到 2 和 3。所以最终 x 的值可以是 1, 2, 3, 4 中的任意一个！

数据竞争这个 bug 做了总结，它非常可怕，因为：

- **罕见 (Rare)**：大部分时候它可能不出现，让你误以为程序是正确的。
- **不确定性 (Nondeterministic)**：每次运行结果都可能不同。
- **静默失败 (Silent-failing)**：程序不会崩溃，但会给出错误的结果。
- 这些特性导致它**极难调试**。

## Locks and critical segments

**如何避免数据竞争**

- 幻灯片首先重申了多线程程序正确的标准：任何交错顺序都必须产生相同的结果。
- 最简单的避免方法是**确保每个线程只在独立的数据上工作**。如果线程之间不需要共享和修改同一个数据，自然就没有竞争。
- 但现实是，很多问题**必须**进行协调。比如我们之前 x = x + 1 的例子，所有线程都需要更新同一个计数器。

用了一个非常经典的“**买牛奶**”问题来类比并发控制的复杂性。
Alice 和 Bob 想确保冰箱里总有且仅有一加仑牛奶。他们事先约定好一套指令，但之后不能再有任何交流。

- **尝试 1 (第 25-26 页)**：如果没牛奶，就去买。问题是，他们可能同时看到冰箱是空的，然后都去买了牛奶，结果冰箱里有了两加仑。
- **尝试 2 (第 27-28 页)**：引入一个“纸条”作为标记。如果没纸条，就检查牛奶，然后放个纸条去买。问题是，他们可能在检查牛奶和放纸条这两个动作之间被中断，导致两人都认为自己应该去买牛奶。
- **尝试 3 (第 29-30 页)**：更复杂的纸条逻辑。但结果显示，只要指令的执行可以被任意打断和交错，无论逻辑多复杂，都可能出现两个人要么都买牛奶，要么都不买牛奶的窘境。

- 因为没有任何一条指令能**同时**完成“检查一个值”**和**“写入一个值”这两个动作。这两个动作之间总有空隙，而并发的魔鬼就藏在这些空隙里。
- **一个能 100% 成功的策略 (第 32-33 页)**：如果你的名字是 Alice，你就负责买牛奶。这确实能保证牛奶不多不少，但问题是，如果 Alice 很忙，那么 Bob 就只能等着，可能会导致牛奶很久都买不来。这引入了**负载不均**和**性能**的问题。

- “买牛奶”问题的根本解决方案，就是创造一个**不可分割 (indivisible)** 的操作，即**原子操作**。它能在一个步骤内，完成“检查一个值并写入一个新值”的动作。
- RISC-V 的原子指令扩展（"A" extension）就提供了这样的功能。例如 amoswap.w rd, rs2, (rs1)，它能原子性地将 rs1 地址中的值读入 rd，同时将 rs2 的值写入 rs1 地址。
- 这些原子指令是构建更高级并发工具的基础。

- **锁 (Locks)**
  - 基于原子操作，我们可以构建一个更易于使用的工具：**锁**。
  - 锁就像一个卫生间的门锁：只有一个线程可以“获取 (acquire)”锁并进入“房间”（执行代码）。其他线程尝试获取锁时，必须等待，直到里面的线程“释放 (release)”锁。
  - 被锁保护起来的代码区域，被称为“**临界区 (critical section)**”。因为在任何时刻，只有一个线程能进入这个区域，所以它有效地解决了数据竞争问题。

**用锁解决买牛奶问题 (尝试 5)**

- 获取冰箱锁 -> 如果没牛奶 -> 去买 -> 放牛奶 -> 释放冰箱锁
- 这个流程是完美的。当 Alice 获取锁之后，Bob 尝试获取锁时就会被阻塞。直到 Alice 完成所有操作并释放锁，Bob 才能获取锁，这时他会发现已经有牛奶了，于是他什么也不做，直接释放锁。结果正确。

- 使用锁的代价是**性能**。当一个线程等待锁时，它实际上是在空转，没有做任何有用的工作。这使得代码的某些部分变成了**串行**执行。
- **阿姆达尔定律再次发挥作用！** 临界区的大小直接决定了程序中无法并行的部分，从而限制了总体加速比。
- 更严重的是，锁可能导致所有线程都卡住，进入一种谁也无法继续执行的状态。

**哲学家就餐问题 (The Dining Philosophers Problem)**

- 这是一个经典的并发问题，用来演示锁可能导致的严重问题——**死锁 (Deadlock)**。
- **场景 (第 39 页)**：五个哲学家围坐一桌，每人左右手之间各有一根筷子。每个哲学家都需要同时拿起左右两根筷子才能吃饭。
- **朴素的解决方案 (第 40 页)**：先拿左边的筷子，再拿右边的筷子。
- **问题 (第 41 页)**：如果所有哲学家在同一时刻都拿起了他们左边的筷子，那么他们每个人都会永远地等待右边的筷子被放下。但右边的筷子在另一个哲学家的左手上，他也在等待...于是所有人就都饿死了。这就是**死锁**。
- **解决方案 (第 42 页)**：打破这种对称性。比如，只允许四个人同时上桌，或者让其中一个哲学家先拿右边的筷子。

- **第 43 页：OpenMP 中的临界区**
  - 幸运的是，OpenMP 提供了比原始锁更安全、更易用的工具来避免死锁。
  - #pragma omp critical：它定义了一个临界区。OpenMP 保证在任何时候，只有一个线程可以进入被 critical 标记的代码块。它在底层就像一个全局的、无名的锁。
  - #pragma omp barrier：这是一个**屏障**，它会强制所有线程都运行到这里并等待，直到**所有**线程都到达这个屏障，然后它们才能继续往下执行。这是一个非常重要的**同步 (synchronization)** 工具。
  - 在这门课中，我们被强烈建议**只使用 critical 和 barrier**，因为它们能有效地避免我们自己使用锁时可能导致的死锁问题。
- **第 44 页：使用临界区修复并行版 Hello World**
  - 演示代码将 x++ 和 printf 放在了 #pragma omp critical 区域内。这样，每个线程在增加 x 和打印时都是互斥的，保证了输出的 x 值是严格递增且正确的。
  - 同时，在 `if(tid==0)` 之前加入了一个 #pragma omp barrier，确保在 0 号线程打印最终的线程数之前，所有的 "Hello World" 都已经被打印出来了。

```c
#include <stdio.h>
#include <omp.h>
int main() {
	int x=0; // Shared variable
	#pragma omp parallel
	{
		int tid=omp_get_thread_num();
		#pragma omp critical
		{
			x++;
			printf("Hello World from thread %d, x=%d\n",tid,x);
		}
		#pragma omp barrier
		if(tid==0) {
			printf("Number of threads=%d\n", imp_get_num_threads());
		}
	}
	printf("Done with parallel segment\n");
}
```

## MIMD: Multiprocess Programming

- **线程**：就像一个“蜂巢思维 (hive mind)”。它们共享资源（内存），紧密协作，但都属于同一个实体（进程）。
- **进程**：就像“一群人”。每个人都是独立的，有自己的资源（内存），他们之间的交流需要刻意为之。

**深入对比**

- **程序实例**：多线程程序是**一个**程序实例，而多进程程序会创建**多个**独立的程序实例。
- **内存共享**：进程通常**不共享内存**，但可以共享文件系统。这意味着我们之前学的锁和并发原语（primitives）在多进程中**无法直接使用**，因为它们依赖于共享内存。这也限制了多进程编程主要适用于那些可以被完全拆分成独立任务的问题。
- **容错性**：这是一个巨大的区别。在多线程程序中，任何一个线程崩溃（比如段错误），整个进程就会崩溃。而在多进程程序中，每个进程独立运行，一个进程的崩溃通常不会影响其他进程。
- 幻灯片还提到了“僵尸进程 (zombie processes)”的概念，即主进程结束后，其子进程仍然存活，这可能会持续消耗系统资源。

**多进程的“威力”与“危险”**

- 由于操作系统将每个进程都视为独立的个体，这使得多进程程序可以“绕过”操作系统为单个程序设置的许多限制。
- 这也带来了一种危险的应用，叫做“**叉子炸弹 (fork bomb)**”。它是一个会创建自己副本的程序，这些副本又会继续创建自己的副本，导致进程数量指数级增长，最终耗尽系统所有资源，导致系统崩溃。

**多进程框架概述**

- **通信**：进程间的通信（Inter-Process Communication, IPC）是通过**发送消息 (sending messages)** 来完成的。
- **开销**：发送消息的开销非常大，远远超过普通的内存操作。
- **工程挑战**：多进程编程的主要工程难题，就是如何将一个大问题，拆分成多个小的、独立的子问题，同时**最小化**进程间需要传递的消息数量和数据总量。

**Open MPI**

- 为了进行多进程编程的演示，讲师介绍了一个工具：**Open MPI (Message Passing Interface)**。
- MPI 是一个标准，定义了如何在进程间传递消息。Open MPI 是这个标准的一个流行实现。
- 它是许多超级计算机上进行分布式编程的基础。
- 它主要为 Linux 系统构建，因为绝大多数超算都使用 Linux。

**多进程版 Hello World**

- 这段 C 代码展示了 MPI 的基本结构：
  - MPI_Init()：初始化 MPI 环境。
  - MPI_Comm_size()：获取集群中的总进程数。
  - MPI_Comm_rank()：获取当前进程的唯一 ID（称为 rank）。
  - MPI_Finalize()：结束 MPI 环境。
- 每个进程都会运行这段代码，并打印出自己的 rank。

```c
int main(int argc, char** argv) {
	MPI_Init(&argc, &argv);
	int processID, clusterSize;
	MPI_Comm_size(MPI_COMM_WORLD, &clusterSize);
	MPI_Comm_rank(MPI_COMM_WORLD, &processID);
	printf("Hello World from process %d\n", processID);
	MPI_Finalize();
}
```

- **管理者-工人 (Manager-Worker) 框架**
  - 这是多进程编程中一个非常常见且有用的设计模式。
  - **角色**：
    - **管理者 (Manager)**：通常是 0 号进程。它的工作是分配任务和向用户报告进度。
    - **工人 (Worker)**：其他所有进程。它们从管理者那里接收任务，完成工作，然后请求新任务。
  - 这通常需要我们编写两种逻辑：一套给管理者，一套给所有工人。
- **第 54 页和第 55 页：管理者和工人的伪代码**
  - **管理者 (第 54 页)**：循环等待工人发来“我准备好了”的消息，然后给它分配下一个任务。当所有任务都完成后，向所有工人发送“工作完成”的信号。
  - **工人 (第 55 页)**：循环向管理者发送“我准备好了”，然后接收管理者的消息。如果收到的是新任务，就执行；如果收到的是“工作完成”，就退出循环。
- **第 56 页和第 57 页：进程间通信 (IPC)**
  - 这里总结了现实世界中几种常见的 IPC 方法：
    - **文件 (Files)**：进程可以读写同一个文件来交换数据。
    - **套接字 (Sockets)**：用于网络通信，可以在不同机器的进程间传递数据。
    - **管道 (Pipes)**：一种单向的数据通道，通常用于将一个进程的输出连接到另一个进程的输入（例如 cat file.txt | grep "dog"）。
    - **共享内存 (Shared Memory)**：主进程可以创建一块特殊的内存区域，让它的子进程也能访问。

- **将多进程应用于矩阵乘法**
  - **问题**：单个矩阵乘法很难用多进程来做，因为需要太多的数据交换和通信。
  - **适用场景**：当我们有**大量独立**的矩阵乘法任务时（比如 10 万个）。
  - **朴素方法 (第 59 页)**：静态分配任务。比如 0 号进程做前 100 个，1 号进程做接下来 100 个... 问题在于，如果任务大小不一，会导致严重的**负载不均衡**。
  - **管理者-工人方法 (第 60 页)**：这是一种**动态分配**。一个工人完成了任务，就立即从管理者那里领取下一个，这能很好地解决负载均衡问题。管理者进程虽然“浪费”了，但它保证了整个系统的协调和高效。
- **第 61 页：多进程 + 多线程？**
  - 我们可以在一个节点内使用多线程（利用共享内存的便利），在节点间使用多进程（进行扩展）。这是一种更高级的混合并行策略，但会让代码更复杂，更依赖于特定的硬件架构。

## Summary

| Optimization               | Max Speedup   | Pros                                       | Cons                                                      |
| -------------------------- | ------------- | ------------------------------------------ | --------------------------------------------------------- |
| Register/Function Inlining | <2x           | Easy change, reduces memory accesses       | Minimal effect, optimizing compiler might do this already |
| Loop Unrolling             | <2x           | Reduces Branching                          | Minimal effect, significant penalty to maintainability    |
| Cache Optimizations        | ~10x          | Surprisingly good                          | Often requires algorithmic changes                        |
| SIMD                       | ~8x           | Fairly applicable, minimal overhead        | Limited by hardware, often hit hard by Amdahl's Law       |
| Multithreading/OpenMP      | `#cores/node` | More flexible than SIMD and MPI, generally | Concurrency issues, high overhead                         |
| Multiprocess               | `#cores`      | Can be extended arbitrarily large          | Expensive communication, high overhead                    |
