## MIMD: Multiprocess Programming

**MIMD: Multiprocess Programming (MIMD：多进程编程)**

## Cache Coherency

缓存一致性，这是一个在多核处理器时代至关重要的新概念。

- **第 16 页：多处理器缓存 (Multiprocessor Caches)**
  - 我们知道内存访问是性能瓶颈，因此每个 CPU 核心通常都有自己的 **L1 缓存**，以减少对主内存的带宽需求。
  - 这张图展示了一个典型的多核系统结构：多个 CPU 核心，每个核心带着自己的私有缓存，通过一个共享的总线 (Bus) 连接到主内存和 I/O 设备。
- **第 17 页：问题出现**
  - 讲师提出了一个关键的场景：
    1. 主内存地址 0x5000 的值为 20。
    2. CPU 核心 1 读取 Mem[0x5000]，于是它的私有缓存中就有了 0x5000: 20 的一个副本。
    3. CPU 核心 2 也读取 Mem[0x5000]，于是它的私有缓存中也有了 0x5000: 20 的一个副本。
    4. 现在，CPU 核心 1 **写入** Mem[0x5000]，将其值更新为 40。这个更新操作只发生在核心 1 的私有缓存中！
  - **问题是什么？**
- **第 18 页：缓存不一致 (Out-of-sync)**
  - 问题就在于，此时 CPU 核心 1 的缓存认为 0x5000 的值是 40，而 CPU 核心 2 的缓存和主内存中的值仍然是 20。它们的数据**不再同步**了。
  - 如果此时 CPU 2 再去读取 0x5000 的值，它会从自己的缓存中读取，得到的是**错误的、过时的**值 20。
  - 这个由于多个私有缓存的存在而导致共享数据副本不一致的问题，就叫做**缓存一致性问题 (Cache Coherency Problem)**。
  - 如何解决这个问题？需要一套协议来确保所有缓存中的数据保持同步。幻灯片预告了我们将在下周学习的 **MOESI 协议**，这是一种非常重要的缓存一致性协议。

## Virtual Memory and Virtual Addresses

讲师在这里抛出了一个非常反直觉的问题：“我的电脑正在使用多少内存？”  
他看到系统报告说，正在使用 13.8 GB 的物理内存（RAM）。但当我们试着从另一个角度计算时，奇怪的事情发生了。他的电脑上有 422 个正在运行的进程。我们知道，在一个 64 位的操作系统上，每个进程都“认为”自己拥有一个巨大的地址空间。幻灯片里提到，实际的地址是 48 位的，这意味着每个进程的地址空间高达 2^48 字节。

那么，总的内存需求就是 422 \* 2^48 字节，这等于……100 拍字节 (Petabytes)！这个数字比他实际拥有的 15.7 GB 物理内存大了将近 800 万倍！这显然是不可能的。那么，魔法发生在哪里？

我们不可能给每个进程都分配一个完整的、巨大的物理内存空间。幸运的是，我们也不需要这么做。因为**大多数进程并不会用满它们整个地址空间**。一个程序通常只用到了代码段的一小块、栈的一小块，以及堆和数据段的几小块内存。

解决方案是什么呢？这就是虚拟内存的第一个核心思想：**我们把物理内存切分成许多固定大小的小块，称之为“页 (pages)”**（通常是几 KiB 大小）。我们**只为程序实际需要用到的那些页分配物理内存**。

这就引出了一个程序运行时所看到的“假象”。当一个程序在 32 位机器上运行时，它认为自己拥有 2^32 字节的完整地址空间。但这个内存空间并不完全真实存在于物理 RAM 中，它是一个“**虚拟 (virtual)**”的内存空间。只有当程序**真正需要**访问某个虚拟地址所在的页时，我们（也就是操作系统）才会为它分配一页**物理内存 (physical memory)**。

对虚拟内存做了更正式的定义。它是在内存层级结构 (memory hierarchy) 中新的一层，位于主存和磁盘之间。  
它的核心功能，就是给每个进程提供一个**它独占了全部内存地址空间的假象 (illusion)**。  
在底层，一个进程正在使用的数据页（称为工作集, working set）确实存在于主存（RAM）中，而其他暂时不用的页则被存放在**磁盘 (disk)** 上。

这种机制带来了巨大的**好处**：

- **按需分页 (Demand paging)**：使得我们可以运行比物理内存大得多的程序。
- **保护 (Protection)**：操作系统可以轻松地隔离不同进程的内存空间，防止一个程序恶意或无意地破坏另一个程序的数据。
- **隐藏机器差异**：为程序员屏蔽了底层复杂的硬件配置。

实现这种复杂的逻辑，光靠硬件是不够灵活的，因此，虚拟内存的核心管理工作由**操作系统 (operating system)** 来完成。

操作系统就像一个“管理者进程”，它的工作就是协调其他所有程序。在虚拟内存这个议题上，操作系统里的**内存管理器 (memory manager)** 扮演了中间人的角色：

- 它负责将程序看到的**虚拟地址**翻译成内存芯片上实际的**物理地址**。
- 它管理着所有进程的虚拟内存，确保它们不会互相干扰。
- 如果物理内存（RAM）用完了，它还能将一些不常用的页“挪”到磁盘上，腾出空间。当然，这个操作的性能开销非常大，因为访问磁盘比访问内存要慢得多。

节省空间：一个程序的虚拟地址空间可能非常大，但其中大部分是未使用的 (Unused)。虚拟内存系统只会为那些真正被用到的页（栈、堆、代码、数据段的页）在物理内存中分配空间。

![image.png](https://pub-cc2ebc8a43754210aa734d07c4898ad1.r2.dev/2025/08/20250801211934792.webp)

保护：假设一个银行程序和一个黑客程序碰巧想使用相同的虚拟地址来存储密码。虚拟内存系统会通过地址转换，将它们映射到物理内存中**完全不同**的位置。这样，黑客程序就无法通过简单的地址访问来窃取银行程序的密码，实现了进程间的安全隔离。

![image.png](https://pub-cc2ebc8a43754210aa734d07c4898ad1.r2.dev/2025/08/20250801211945500.webp)

更抽象的图景总结了这个过程。

- **第 37 页 (假象)**：从每个进程的视角看，它们都拥有一个从 0x0...0 到 0xF...F 的、完整且独立的虚拟地址空间。它们可以自由地使用这些地址，完全不用担心会与其他进程冲突。
- **第 38 页 (现实)**：在幕后，有一个“翻译官/内存管理者”，它接收来自不同进程的虚拟地址请求，并将它们一一映射到一块共享的、真实的物理内存上。这块物理内存使用的是另一套地址系统，即**物理地址**。

hive机器上，一个真实的系统命令 cat /proc/cpuinfo 的输出，向我们展示了现代 CPU 地址线的实际位数。在这个例子中，物理地址是 39 位，而虚拟地址是 48 位。

对这两种地址空间做了明确的定义：

- **虚拟地址空间 (Virtual Address Space)**：用户程序所能“看到”和使用的地址集合。
- **物理地址空间 (Physical Address Space)**：真正映射到物理内存位置的地址集合，对用户程序是透明的。
- 内存管理器的核心任务，就是在每个进程的这两种地址空间之间进行**翻译 (translates)**。

将虚拟内存放在了整个内存层级结构中进行考察。

- 寄存器和主存之间的管理，由**编译器**完成。
- 缓存和主存之间的管理，由**缓存控制器硬件**完成。
- 而主存和磁盘之间的管理，则主要由**操作系统**（通过虚拟内存机制）和**程序员**（通过文件操作）共同完成。地址翻译的过程会由硬件（比如 TLB，我们稍后会学）来加速。

> 一个重要的简化：为了更容易地理解虚拟内存的地址翻译过程，我们今天**暂时假设缓存不存在**。我们会在后续课程中再把缓存加回来。

## Paged Memory and Address Translations

**页式内存 (Paged Memory)** 的基本概念。

- 物理内存（DRAM）和虚拟地址空间，都不是以字节为单位进行管理的，而是被划分成固定大小的块，我们称之为**页 (pages)**。
- 当我们从磁盘加载数据到内存时，也是**一整页一整页**地加载。这样做可以摊销（amortize）磁盘访问的高昂开销。
- 在现代操作系统中，一个典型的页大小是 **4 KiB**（也就是 4096 字节）。
- 既然一个页有 4 KiB，那么为了能定位到页内的每一个字节，我们就需要 log2(4096) = 12 位地址。这 12 位，我们称之为**页内偏移 (page offset)**。

地址翻译的本质。

- 地址翻译的核心，就是将一个**虚拟页号 (Virtual Page Number, VPN)** 映射到一个**物理页号 (Physical Page Number, PPN)**。
- **虚拟地址**和**物理地址**的结构都被分成了两部分：
  - **虚拟地址 = 虚拟页号 (VPN) + 页内偏移 (offset)**
  - **物理地址 = 物理页号 (PPN) + 页内偏移 (offset)**
- 一个至关重要的原则是：**虚拟页和物理页的大小是完全相同的**。这意味着，它们的**页内偏移部分的位数是完全一样的**（在这个例子中都是 12 位）。
- 因此，地址翻译的真正工作，就是把虚拟地址的高位部分（VPN）替换成物理地址的高位部分（PPN），而低位部分（offset）保持不变！

这个 VPN 到 PPN 的映射关系是存放在哪里的呢？**第 46 页**给出了答案：**页表 (Page Table)**。

- **每个进程都有自己的一张页表**。这张表就像一个翻译词典，记录着该进程的虚拟页号到物理页号的映射。
- 页表的每一行（称为页表项, Page Table Entry, PTE）对应一个虚拟页。
- 当程序访问一个虚拟地址时，系统会：
  1. 从虚拟地址中提取出 VPN。
  2. 用 VPN 作为索引，去查询该进程的页表。
  3. 如果页表项中记录了对应的 PPN，说明数据在内存里，这就是一次**页命中 (Page hit)**。
  4. 如果页表项中没有有效的 PPN（比如标记为“在磁盘上”），说明数据不在内存里，此时会触发一个**页错误 (Page Fault)**。操作系统会介入，从磁盘中加载相应的页到物理内存，并更新页表，然后程序才能继续执行。

![image.png](https://pub-cc2ebc8a43754210aa734d07c4898ad1.r2.dev/2025/08/20250801213039045.webp)

**第 48 页到第 51 页**通过一个完整的**地址翻译示例 1**，带我们走了一遍“页命中”的流程。

- **前提**：页大小 4 KiB，我们有 4 页物理内存。
- **第 48 页 - 步骤 1**：程序试图加载虚拟地址 0xFFFF F004 的数据。
- **第 49 页 - 步骤 2**：操作系统（和硬件）开始翻译。它首先将虚拟地址 0xFFFF F004 拆分：
  - **VPN**：高 20 位是 0xFFFFF (因为 32-bit 地址减去 12-bit 偏移)。
  - **Offset**：低 12 位是 0x004。
  - 然后，它以 0xFFFFF 为索引，去查找页表。
- **第 50 页 - 步骤 3**：页表查询结果显示，VPN 0xFFFFF 对应的 PPN 是 1。这是一次**页命中**！现在，操作系统要构建物理地址：
  - **PA = PPN + Offset = 0x1(PPN) +0x004(Offset) =0x1004**。注意，这里0x1代表的是第1号物理页的基地址，所以实际地址是1 \* 4K + 0x004`，但为了简化，我们通常直接拼接。
- **第 51 页 - 步骤 4**：硬件根据计算出的物理地址 0x1004，从物理内存（DRAM）的 Physical Page 1 中读取数据（比如 0x43），并将其返回给程序。

**第 52 页到第 54 页**展示了**地址翻译示例 2**，描述了 malloc 这样的内存分配请求是如何工作的。

- **第 52 页 - 步骤 1**：程序调用 malloc(10)，C 库将其转换为一个向操作系统申请新内存页的请求，比如请求 VPN 0x60000。
- **第 53 页 - 步骤 2**：操作系统收到请求后，在物理内存中寻找一个空闲的物理页（比如 Physical Page 1）。
- **第 54 页 - 步骤 3**：操作系统**更新页表**，建立新的映射关系：将 VPN 0x60000 映射到 PPN 1。然后返回给程序，告诉它分配成功。

**第 55 页到第 58 页**则展示了最复杂的情况：**地址翻译示例 3（页错误）**。

- **第 55-56 页 - 步骤 1 & 2**：程序试图访问一个虚拟地址，操作系统查找页表后发现，对应的页表项标记为 “disk”。这意味着数据在磁盘上，而不在内存里。
- **第 57 页 - 步骤 3**：**页错误 (Page Fault)** 发生！
  - CPU 暂停当前程序，将控制权转交给操作系统。
  - 操作系统接管后，找到一个空闲的物理页（或者，如果没有空闲的，就选择一个现有的页换出到磁盘）。
  - 然后，操作系统从磁盘读取所需的数据，加载到这个物理页中（比如 Physical Page 2）。
  - 最后，**更新页表**，将 VPN 0xFFFFF 映射到新的 PPN 2。
- **第 58 页 - 步骤 4**：页错误处理完毕后，控制权交还给程序，刚才导致错误的指令被**重新执行**。这一次，地址翻译会成功命中，程序得以继续运行，就好像什么都没发生过一样。
