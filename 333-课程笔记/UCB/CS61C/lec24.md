## Page Table Details

- 页表的每一行，我们称为一个**页表条目 (Page Table Entry, PTE)**。每个条目都对应一个**虚拟页号 (VPN)**。你可以把页表想象成一个大数组，而 VPN 就是用来索引这个数组的下标。例如，VPN 为 0 的虚拟页，其翻译信息就存储在页表的第 0 个条目中。
- 每个条目里存着两样东西：一个是**物理页号 (Physical Page Number, PPN)**，这是地址翻译的核心；另一个是**状态位 (status bits)**，这些比特位提供了关于该页的额外信息，我们马上就会详细讲解。
- 一个非常非常重要的概念是：**页表不是缓存 (A page table is NOT a cache)**！这是一个常见的误区。为什么呢？
  - 缓存只存储最近使用过的一小部分数据。而页表是一个**完整的查找表 (lookup table)**，它为程序虚拟地址空间中的**所有**虚拟页都提供了一个条目，无论该页当前是否在内存中。
  - 缓存存储的是内存中的实际数据副本。而页表存储的是**地址映射关系和状态**，它不包含页内的实际数据。

一个 PTE 主要存储两部分信息：

1. 与给定 VPN 相关联的 PPN。
2. 一些状态位或元数据 (Status bits/metadata)。

在这门课中，我们将重点关注以下三种状态位：

1. **Valid Bit (有效位)**
2. **Dirty Bit (脏位)**
3. **Write Protection Bit (写保护位)**

### Valid Bit

这个位的作用和我们在缓存中学到的有效位非常相似。它用来标识一个虚拟页对应的数据**是否在物理内存 (DRAM) 中**。

- 当一个进程需要访问某个内存地址时，硬件会首先检查对应 PTE 中的有效位。
- 如果 **Valid 位为 1 (on)**，表示这个页就在主内存里。太好了！地址翻译可以继续，程序直接读写对应的物理内存。
- 如果 **Valid 位为 0 (off)**，表示这个页当前不在主内存中（它可能还在磁盘上，或者从未被使用过）。这时，硬件会触发一个**缺页异常 (page fault)**。
  - 这个异常会把控制权交给操作系统。
  - 操作系统介入处理：它会负责在磁盘上找到这个页，将它加载到 DRAM 的一个空闲物理页中。
  - 如果 DRAM 已经满了，操作系统就需要执行替换策略，选择一个现有的页把它“换出”到磁盘（如果这个页被修改过），然后把新的页加载进来。
  - 加载完成后，操作系统会更新 PTE（将 Valid 位置为 1，并填入新的 PPN），然后让程序重新执行刚才导致异常的指令。这次，因为 Valid 位已经是 1，访问就能成功了。

### Dirty Bit

类比：**主内存 (DRAM) 就像是磁盘 (二级存储) 的“缓存”**。既然是缓存，就会涉及写策略：是“写穿 (write-through)”还是“写回 (write-back)”？

- “写穿”意味着每次修改内存数据，都立刻同步写回磁盘。
- “写回”则表示只在内存中修改，直到这个页要被从内存中换出时，才一次性写回磁盘。

考虑到磁盘访问速度比内存慢了几个数量级，如果每次写操作都去访问磁盘，性能将是灾难性的。因此，所有的虚拟内存系统都采用**写回 (write-back)** 策略。

写回策略需要一个机制来判断数据是否被修改过，这就是**脏位 (dirty bit)** 的作用。

- 当一个页被加载到内存时，它的脏位被设为 0（表示“干净”）。
- 当程序对这个页执行了任何写操作，硬件就会自动将该页对应 PTE 里的脏位置为 1（表示“脏了”）。
- 当操作系统需要替换这个页时，它会检查脏位：
  - 如果脏位是 1，说明内存中的数据比磁盘上的新，必须将该页写回磁盘。
  - 如果脏位是 0，说明内存和磁盘上的数据一致，可以直接丢弃内存中的页，无需写回磁盘，从而节省了一次非常耗时的磁盘写操作。

### Write Protection Bit

这个位提供了更精细的内存保护。

- 当一个 PTE 的写保护位被设为 **on (1)** 时，这个页就是“受保护的”，或者说是**只读 (read-only)** 的。
- 任何试图向这个页写入数据的行为都会触发一个操作系统异常（比如我们常遇到的“段错误” Seg Fault）。
- 这个功能非常有用。比如程序的代码段（.text段），一旦加载到内存就不应该被修改，所以可以将其设置为只读。同样，操作系统的核心数据也需要被保护起来。
- 这正是操作系统扮演**“裁判 (referee)”**角色的体现：
  - 它隔离了不同进程的内存空间。
  - 它防止了用户程序破坏其他程序或操作系统本身。

#### 写保护用例

如果多个进程都需要使用同一个库（比如 C 语言的 stdlib），高效的做法是，只在物理内存中加载一份 stdlib 的代码。然后，在所有需要它的进程的页表中，都创建一个条目，让它们各自的虚拟页指向这**同一个物理页**！

但问题来了：如果其中一个进程有 bug，不小心修改了共享库的代码怎么办？这会影响到所有正在使用这个库的进程，导致系统范围的混乱。

解决方案就是：在映射这些共享物理页时，将它们在每个进程页表中的对应条目的**写保护位置为 1**。这样，所有进程都可以读取和执行共享库的代码，但任何一个进程都无法修改它，从而实现了既高效又安全的共享。

### Page Table有多大？

假设一个系统有：

- 32 位虚拟地址
- 4 KiB 大小的页
- 每个页表条目 (PTE) 是 32 位（也就是 4 字节）

计算一下这个页表的大小：

1. **页偏移**：页大小是 4 KiB = 2^12 字节。所以需要 12 位作为页偏移。
2. **虚拟页号 (VPN)**：虚拟地址总共 32 位，减去 12 位的偏移，剩下 20 位给 VPN。
3. **页表条目数**：有 20 位的 VPN，意味着总共有 2^20 个不同的虚拟页。因此，页表需要有 2^20 个条目。
4. **页表总大小**：总大小 = (条目数) × (每个条目的大小) = 2^20 \* 4 字节 = 4 MiB。
5. **页表占多少页**：4 MiB / 4 KiB = (2^22 字节) / (2^12 字节) = 2^10 = 1024 页。

一个进程的页表就需要 4MB 的空间，并且要占用 1024 个物理页来存储它自己！

#### 页表双倍内存访问问题

这个结果引出了一个严重的问题。

- 一个 4MB 的页表，相对于几个 GB 的主内存来说不算太大，但它对于 CPU 内部的高速缓存 (cache) 来说是**巨大**的。它根本放不进缓存里。
- **解决方案**：我们只能把页表存储在**主内存 (DRAM)** 中。

- **代价 (Caveat)**：这带来了一个巨大的性能瓶颈！如果页表在内存里，那么每次程序访问内存（比如 lw 或 sw），在缓存不命中的情况下，实际上需要进行**两次缓慢的内存访问**：
  1. **第一次访问**：访问内存，读取页表，找到 PPN 完成地址翻译。
  2. **第二次访问**：访问内存，使用翻译好的物理地址去读取或写入真正的数据。
- 这会让内存访问延迟翻倍，是不可接受的。

#### 真正的解决办法

1. 我们已经是通过缓存线(cache line)来传输数据，而不是单个字，这能利用空间局部性。
2. 更关键的是，我们可以为**频繁使用的页表条目**建立一个专门的缓存。这个缓存就是我们下一个议程要讲的 **Translation Lookaside Buffer (TLB)**。

## Translation Lookaside Buffer (TLB)

**转换旁路缓冲 (Translation Lookaside Buffer, TLB)**

一个好的虚拟内存系统，不仅要节省空间，更要保证**速度**。理想情况下，地址翻译的过程应该非常快，最好只占用一个时钟周期左右。

但是，我们上一节得出的结论是，页表是存放在主内存里的。这意味着，每次 CPU 要访问内存（无论是取指令还是读写数据），都可能需要先去访问一次主内存来查询页表，这个过程我们称之为 **“页表步进” (page table walk)**。如果每次访问都要走这么一遭，那简直太慢了。

**将一部分地址翻译的结果缓存起来**。我们为这些翻译结果专门设计一个又小又快的缓存，它的名字就叫**转换旁路缓冲 (Translation Lookaside Buffer, TLB)**。

页表和 TLB 之间的关系。

- **页表 (Page Table)**：它存储了一个进程**所有**的虚拟页号 (VPN) 到物理页号 (PPN) 的映射关系。它很全，但因为它在主内存里，所以访问慢。
- **TLB**：它就是这个页表的**缓存**。它只存储了页表中一小部分**最近被使用过**的 VPN-PPN 映射条目。

两个非常关键的点：

1. TLB 物理上离 CPU 非常近（就在 CPU 芯片上），所以访问速度极快，就像我们之前学的 L1 缓存一样。虽然它的名字听起来有点奇怪（这是历史原因），但你完全可以把它理解成一个专门缓存页表条目的高速缓存。
2. **TLB 不存储页中的实际数据**！它只缓存**地址翻译**这个“动作”的结果，也就是 VPN 和 PPN 的对应关系。它的唯一使命就是加速从虚拟地址到物理地址的转换过程。一旦通过 TLB 得到了物理地址，CPU 仍然需要拿着这个物理地址去真正的数据缓存或者主内存中获取数据。

### TLB 技术细节

- **大小**：TLB 通常都比较**小**，比如只有 64 或 128 个条目，但因为它缓存的是访问最频繁的地址翻译，所以效率非常高。
- **相联度**：TLB 通常是**全相联 (fully associative)** 的。因为条目总数少，所以硬件上可以实现将输入的 VPN 同时与所有条目进行比较，这使得冲突未命中（conflict miss）的概率降到最低，从而最大化了命中率。
- **替换策略**：使用如 FIFO（先进先出）或 LRU（最近最少使用）等策略。

- **上下文切换 (Context Switching) 的挑战**：这是一个非常重要的问题。我们知道，每个进程都有自己独立的页表。TLB 里缓存的是**当前正在运行**的进程的地址映射。那么当操作系统进行上下文切换，从进程 A 换到进程 B 时，会发生什么？TLB 里所有为进程 A 缓存的条目，对于进程 B 来说都是完全无效的！
  - **最简单的解决方案**：操作系统在每次进行上下文切换时，都**清空 (flush) TLB**，也就是把所有条目都标记为无效。这个方法简单粗暴，保证了正确性，但有性能代价——新进程开始运行时，面对的是一个空的 TLB，初期会发生大量的 TLB 未命中，直到它常用的一组翻译被重新加载进来。
  - **更复杂高级的解决方案**：为每个 TLB 条目增加一个“进程ID”字段。这样 TLB 就可以同时存储多个进程的映射。硬件在查找时就需要同时匹配 VPN 和当前进程的 ID。这样就避免了清空 TLB 的开销，但增加了硬件的复杂度。

## Address Translation: Best/Worst Case

### 最佳情况 - TLB 命中 (TLB Hit)

1. CPU 发出虚拟地址
2. 硬件会从这个虚拟地址中提取出 **VPN**。
3. 硬件拿着这个 VPN (0x00004) 去查询 **TLB**
4. **TLB 命中**
5. 这个翻译过程几乎是**瞬时完成**的（大约 1 个时钟周期）
6. 硬件立刻将 PPN (0x8C121D) 和原始的页偏移 (0xABC) 拼接起来，得到物理地址 0x8C121DABC。
7. CPU 拿着这个物理地址去访问缓存或主内存，获取数据。

### 较差情况 - TLB 未命中 + 页表步进 (TLB Miss + Page Table Walk)

1. CPU 同样发出虚拟地址 0x00004ABC，提取出 VPN 0x00004。
2. 硬件去查询 TLB，但这次**TLB 未命中 (TLB Miss)**！TLB 里没有关于 0x00004 的记录。
3. 这时，就必须启动**页表步进 (Page Table Walk)**。硬件（或在某些架构中是 OS）需要去访问存放在**主内存**中的页表。
4. 硬件根据页表基地址寄存器和 VPN 0x00004，计算出该 VPN 对应的页表条目 (PTE) 在主内存中的地址，然后发起一次**内存读取**操作来获取这个 PTE。
5. 幸运的是，这个 PTE 是有效的（Valid bit = 1），并且告诉我们 PPN 是 0x82C121D。这说明我们想访问的页面确实在内存里，只是它的翻译信息不在 TLB 中。
6. 这次访问主内存去读页表，代价是比较高的，大约需要 **~100 个时钟周期**。

### 最差情况 - 缺页异常 (Page Fault)

1. CPU 发出虚拟地址 0x00004ABC，VPN 是 0x00004。
2. **TLB 未命中**。
3. 硬件启动页表步进，去主内存读取对应的 PTE。
4. 读取 PTE 后，发现里面的**有效位 (Valid Bit) 是 0**（或者标记为 "disk"）。这意味着我们想访问的数据页**根本不在主内存中**！
5. 这时，硬件无法继续处理，它会触发一个**缺页异常 (Page Fault)**，将控制权交给操作系统。
6. 操作系统中断当前进程的执行。
7. 它在磁盘上找到虚拟页 0x00004 对应的数据（图上是那个名为 "orange" 的数据块）。
8. 操作系统在主内存中找到一个空闲的物理页（如果没有，则需要执行页面替换算法，换出一个旧的页）。
9. 操作系统将数据从**磁盘加载到主内存**的这个物理页中。这个过程是整个流程中最最耗时的，通常需要成千上万（甚至更多）个时钟周期，因为磁盘 I/O 非常慢。
10. 数据加载完成后，操作系统会**更新页表**。它将 0x00004 对应的 PTE 的有效位置为 1，并填入刚刚分配给它的物理页的 PPN（比如是 0x82C121D）。
11. 同时，这个新的翻译信息也会被**加载到 TLB 中**。
12. 最后，操作系统将控制权交还给被中断的进程，让它**重新执行**刚才导致缺页异常的那条指令。

## Caches vs Virtual Memory

- **L1 缓存**和**L2 缓存**：它们是 **DRAM (主内存)** 的缓存。数据以**缓存行 (Line)** 为单位在它们和主内存之间移动，比如 64B 或 128B。
- **DRAM (主内存)**：它本身又是**磁盘 (二级存储)** 的缓存。数据以**页 (Page)** 为单位在它们之间移动，通常是 4KiB。

| 特性               | Caches                                                  | Virtual Memory                                      |
| ------------------ | ------------------------------------------------------- | --------------------------------------------------- |
| 在内存层次中的位置 | Caches ↔ Memory                                        | Memory ↔ Disk                                      |
| 内存单位           | Block (64 bytes)                                        | Page (4096 bytes)                                   |
| 缺失类型           | Cache Miss                                              | Page Fault                                          |
| 关联性             | Direct-mapped, N-way set associative, fully associative | Fully associative (pages can go anywhere in memory) |
| 替换策略           | Least-recently-used (LRU) or random                     | LRU (most common), FIFO, or random                  |
| 写策略             | Write-through or write-back                             | Write-back                                          |

那么最终问题就是：当缓存和虚拟内存同时存在时，一个内存访问请求到底是如何被处理的？

更具体来说：

- 如果一个页不在主内存里，它对应的数据能存在于缓存中吗？（答案是不能，因为缓存是主内存的子集）
- 当 CPU 发出一个访存请求时，我们应该先访问谁？TLB？Cache？
- 虚拟地址应该在什么时候被翻译成物理地址？

本课程中我们采用的简化模型：**物理索引，物理标记 (Physically Indexed, Physically Tagged, PIPT) 的缓存**。

这个模型下的处理流程非常清晰，分两步走：

1. **第一步：翻译地址**。CPU 发出的是**虚拟地址 (VA)**。这个 VA 首先被送到 TLB（和页表系统）进行翻译。
   - 如果 **TLB 命中 (hit)**，我们立刻得到**物理地址 (PA)**。
   - 如果 **TLB 未命中 (miss)**，就需要进行页表步进，从主内存中找到 PTE，加载到 TLB，然后得到 PA。如果发生缺页，则需要更漫长的磁盘操作。

2. **第二步：访问缓存**。一旦获得了**物理地址 (PA)**，我们再用这个 PA 去访问数据缓存 (Data Cache)。
   - 用 PA 的索引位找到对应的组。
   - 用 PA 的标记位和组内的标记进行比较。
   - 如果**缓存命中 (hit)**，直接从缓存中取回数据。
   - 如果**缓存未命中 (miss)**，则需要从主内存中读取数据块到缓存，然后再返回给 CPU。

## Cache Coherency

问题的背景：

- 在一个多核 CPU 中，**每个核 (core) 都有自己独立的 L1 缓存**，有时甚至有独立的 L2 缓存。
- 我们之前学到，为了性能，大多数缓存采用的是**写回 (write-back)** 策略。这意味着一个核对数据的修改会先暂存在它自己的缓存里，并不会立即更新到主内存。
- **问题来了**：当多个线程（可能运行在不同的核上）需要访问和修改**共享内存**时，我们如何保证每个线程读到的都是最新、最正确的数据？

将多线程对共享数据的访问分成了三种情况：

1. **两个线程都读 (Two threads read)**
2. **两个线程都写 (Two threads write)**
3. **一个读，一个写 (One thread reads, one thread writes)**

### 同步读 Sync Read

这种情况是**安全**的。只要没有人修改数据，那么所有线程无论从哪里读（自己的缓存、主内存），读到的数据都是一致的。

### **同步写 (Synchronous writes)**。

- 这种情况是**非常危险**的。如果两个线程同时对同一块内存进行不同的修改，就会产生冲突的数据。我们最终应该以哪个为准呢？这很难判断，系统会陷入一个不一致的状态。

- 为了避免这种情况，我们**绝不允许**两个独立的缓存同时拥有对同一内存块的“写权限”。如果一个线程想写，系统必须先将这个内存块从其他所有缓存中**驱逐 (evict)** 出去。
- 这种因为要维持一致性而导致的缓存驱逐，会引发一种新的缓存未命中，称为**一致性未命中 (coherence misses)**。在多线程高并发写的场景下，这种未命中会导致缓存块在不同核心之间被频繁地来回传递，造成严重的性能下降，这种现象被称为**颠簸 (thrashing)**。

### 一个线程写，多个线程读

- 一种简单的处理方式是“走安全路线”：当一个线程要写数据时，强制把这个数据块从所有其他正在读它的缓存中驱逐出去。但这同样会导致一致性未命中。
- 更理想的情况是：我们允许一个线程写数据，同时让其他线程能够**读到这个刚刚被写入的新数据**。这可能意味着允许一个缓存去读取另一个缓存中的数据，或者建立一种机制，让写入方主动更新其他缓存。
- 要实现这种理想情况，就需要一套**缓存间的通信协议 (communication protocol)**。

这个协议就是我们接下来要讲的 **MOESI 协议**。

### MOESI协议

为了实现这种复杂的交互，我们不能再简单地用一个 Valid 位和一个 Dirty 位来描述缓存块的状态了。我们需要一个更丰富的状态机。MOESI 协议就是这样一个协议，它为每个缓存块定义了**五种可能的状态**

- **M - Modified (已修改)**: 这和我们之前学的 "Valid on, Dirty on" 类似。表示当前缓存块是有效的、被修改过的（脏的），并且**当前这个核是唯一持有该缓存块副本的核**。这个核有责任在未来将它写回主内存。
- **E - Exclusive (独占的)**: 这和 "Valid on, Dirty off" 类似。表示当前缓存块是有效的、未被修改的（干净的），并且**当前这个核是唯一持有该缓存块副本的核**。因为是干净的，所以它的内容和主内存一致。如果这个核想对它进行写操作，可以直接将其状态变为 Modified，而无需通知其他核。
- **S - Shared (共享的)**: 这个状态是新的。它表示当前缓存块是有效的、干净的，并且**有多个核同时持有该缓存块的副本**。处于 Shared 状态的块是**只读**的。如果任何一个核想对它进行写操作，它必须先发送一个请求，让其他所有持有该块的核都将它们各自的副本置为 Invalid。
- **O - Owned (拥有的)**: 这是最复杂的一个状态。它表示当前缓存块是**被修改过的（脏的）**，但**可能有其他核持有该块的共享（Shared）副本**。这个 "Owner" 核是“拥有者”，它持有的数据是最新版本。当其他核请求这个数据时，由 Owner 核直接提供数据，而不是从主内存读取。Owner 核最终负责将数据写回主内存。这个状态可以避免在有读者时就必须写回内存，提高了性能。
- **I - Invalid (无效的)**: 和我们之前学的 Valid bit off 一样，表示这个缓存块的内容是无效的。

**第 59 页**继续解释了 **Shared** 和 **Owner** 状态。

- **Shared**: 块在别的缓存里也有，我们没改过它，也不允许修改它。如果非要改，就得先把它从所有人的缓存里都踢出去，然后自己变成 Modified 状态。这个状态允许多个核同时安全地读取数据。
- **Owner**: 块在别的缓存里也有，但我们改过它，并且我们是唯一有权继续修改它的线程。如果我们继续修改，有责任通知其他持有 Shared 副本的缓存它们的数据已经过时了。这个状态允许一个核写，同时其他核读的场景高效进行。

**第 60 页**展示了 MOESI 协议完整的**状态转换图**。这张图非常复杂，详细描述了当本核进行读/写，或者“窥探”到其他核进行读/写时，一个缓存块如何从一个状态转换到另一个状态。我们不需要记住所有细节，但核心思想是：通过这套状态机和窥探机制，系统可以保证在任何时刻，对于任何一个内存地址，所有核看到的要么是同一个正确的值，要么能最终得到正确的值。

总结了**一致性未命中 (Coherency Misses)**。

- 因为协议规定了在任何时刻，最多只有一个核可以拥有一个“脏”的块（Modified 或 Owned 状态），所以如果两个线程交替地写同一个内存块，就会导致这个块在两个核的缓存之间来回传递，每次传递都伴随着昂贵的一致性未命中。
- 这就是为什么在并行编程实践中，pragma omp 的 interleaved（交错）调度方式可能比 blocked（分块）调度方式慢很多的原因，因为它增加了不同线程访问相邻数据（可能在同一个缓存块里）的概率。
- 因此，编写高性能多线程代码的一个重要原则是：**让每个线程尽可能在独立的缓存块上工作**，以减少核间的数据争用和一致性流量。同时，这些块又要足够近（比如能被共享的 L3 缓存容纳），以利用空间局部性。
